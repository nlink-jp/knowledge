# MCP サーバー設計

Go による MCP（Model Context Protocol）stdio サーバーの実装、および LLM エージェントから
呼ばれるツール一般の設計で確立した知見。各項目は「事象 → なぜ → 適用方法」。

---

## プロトコル・トランスポート

### MCP のキャンセル通知は受信側が無視できる — 確実に止める手段は今も子プロセス kill

**事象:** 「MCP 利用中のチャット中断が効かない」というユーザー報告。in-flight の
ツール呼び出しを中断する手段を調査した。当初の記録は「MCP 2024-11-05 仕様には
client → server のキャンセル通知が無い」と断定していたが、**これは誤りだった**
（2026-09 訂正）。仕様は最初の公開版 2024-11-05 から `notifications/cancelled`
（`requestId`, `reason`）を定義している。

**なぜ:** 誤記の原因は、仕様の一次資料（schema / 該当章）を引かず、自社 stdio
クライアントのコード注釈「ブロック中の Scan を解除する唯一の手段は Stop()」から
プロトコルの不在を推定したこと。実装事情と仕様は別物で、前者は後者の証拠にならない。
ただし結論は変わらない。仕様上、受信側は「cannot be cancelled」なら通知を **MAY
ignore** でよく、自社の stdio 骨格も他社製サーバーの多くも通知を捨てる。一度
dispatch したツール呼び出しは上流の完走まで走る前提で設計するほかない。

**適用方法:**
- クライアント側で「待つのをやめる」確実な手段は**子プロセス kill + stdin close で
  Scan を unblock する**（kill-and-respawn パターン）。`notifications/cancelled` を
  送ってから kill してもよいが、送っただけで止まると期待しない。送った直後に
  SIGKILL するなら協力的なサーバーにも行動する時間は無く、仕様は応答を定義しない
  ので待つ対象も無い — 送って意味を持たせるには kill までの猶予が要り、その猶予は
  タイムアウトごとの復帰遅延になる（2026-09、エージェントランタイム側は送らない
  判断）。context 対応ラッパーは
  `goroutine + select(ctx.Done, result)` + cancel 時に Stop() で kill。
- kill したら**当該サーバーのみ**非同期で再 spawn する責務がクライアント側に要る
  （全サーバー再起動は無関係なサーバーを巻き込む）。
- 上流の副作用（外部 HTTP / DB / 課金）は kill しても止まらない（server 側で完走し、
  client が結果を捨てるだけ）。長時間・従量課金のツールは呼び出し引数で上限を
  小さく保ち、ドキュメントで期待値を揃える。
- サーバー側で通知を無視するなら、その事実を注釈に「仕様に無い」ではなく
  「受信して無視する」と書く。

### プロキシ/中継はクライアントのリクエストを未応答で放置しない

**事象:** proxy が上流への転送失敗（期限切れ OAuth トークン）をログに出すだけで
クライアントに応答せず、クライアントが 15 秒ハング → 理由不明の
`read response: EOF` になった。

**なぜ:** 他の失敗経路（tool not found 等）は JSON-RPC エラーを返していたのに、
上流転送失敗の経路だけ応答が抜けていた。非対称な失敗経路は必ず漏れを生む。

**適用方法:**
- 不変条件:「ルーティングがエラーを返したリクエストには必ず JSON-RPC エラー応答を返す」。
  中央のディスパッチ点で `msg.IsRequest()`（id あり）なら error response を書く。
  通知（id 無し）は応答不可なのでログのみ。
- `err.Error()` に実用的理由（`access token expired ... run --login again` 等）を載せれば
  クライアントがそのまま surface できる。
- 二重応答に注意: ハンドラは「応答を書く」か「エラーを返す」の一方のみ。中央キャッチは
  未応答で伝播したエラーだけ拾う。
- タイムアウト経路が既にエラー応答に変換しているなら、send/connect 失敗経路も同じ扱いに
  揃える。

### 子プロセスの失敗は「パイプの症状」ではなく終了ステータスを surface する

**事象:** 子プロセス（MCP サーバー）が macOS に SIGKILL されていたのに、エラーは
`initialize: read response: EOF` としか出ず、環境問題がコードのバグに見えて診断に
多大な時間を要した。

**適用方法:**
- 失敗時に `cmd.Wait()` の結果（`signal: killed` / `exit status N`）をエラーに含める。
  SIGKILL なら「quarantine/同期パス配下なら macOS が kill している可能性」等の対処ヒントを
  添えると一発で切り分く。
- **os/exec の落とし穴**: `cmd.Wait()` は `StdoutPipe`/`StderrPipe` の読み取りと競合させては
  いけない。**パイプ読み取りを所有する goroutine から、読み取りループが EOF で終わった後に
  1 回だけ**呼ぶ。別の Wait 監視 goroutine を立てるのはこの競合を踏む。
- 具体形: stderr ドレイン goroutine が Scan 終了後（=プロセス終了）に
  `exitErr = cmd.Wait(); close(exited)`。失敗経路は「閉じたパイプ系エラー」のときだけ
  `exited` を短時間待って exitErr を wrap。プロセス生存中の失敗（上流の JSON-RPC エラー等）
  では待たない。Stop() は kill のみで二重 Wait を防ぐ。

### 埋め込みネイティブライブラリを持つ stdio サーバーは fd レベルで stdout を隔離する

**事象:** プロセス内に静的リンクしたネイティブライブラリ（C/CGO）が、モデルロード中に
進捗バーを **fd 1 に printf** し、JSON-RPC ストリームを破壊した。TTY では `\r` 更新の
一瞬の行なので見えず、pipe（=MCP）でだけ生バイトが残る。stub build のユニットテストでは
再現せず、実エンジン E2E で初めて発覚した。

**教訓の核:** 「コンソールで見えない ≠ stdout に出ていない」。必ず `1>file 2>file` で
ストリームを分離して実測する。

**適用方法（2 層で守る）:**
- **① 発生源を塞ぐ**: 「コールバック未登録なら自前で stdout 描画」する型のライブラリには、
  **常に no-op でもコールバックを登録**しておく。
- **② fd レベル隔離（defense-in-depth）**: 起動時に本物の stdout を dup して private handle
  を作り、fd 1 を stderr に付け替える。transport は private handle にだけ書く。

```go
saved, _ := syscall.Dup(int(os.Stdout.Fd()))
syscall.Dup2(int(os.Stderr.Fd()), int(os.Stdout.Fd()))
mcpOut := os.NewFile(uintptr(saved), "mcp-stdout") // transport writes here
```

- ログは `os.Stderr` へ（付け替え後は `fmt.Println` も stderr に落ちて無害）。
- 子プロセス方式（外部エンジンを子プロセス駆動）ではこの問題は出ない。埋め込み方式特有。
- 検証はダミー stdio クライアントによる実エンジン E2E が必須（testing.md 参照）。
  汚染の兆候はレスポンスストリーム中の空行/非 JSON 行。

### RFC 9728 のメタデータが返っても DCR が使えるとは限らない

**事象:** 上流 MCP サーバが 401 で `WWW-Authenticate: ... resource_metadata=...`
を返し、protected-resource メタデータ (RFC 9728) も正しく取得できたので、ブリッジの
「エンドポイントとクライアントを自動 discovery する」設定で繋ごうとしたが、ログインが
完了しなかった。

**なぜ:** discovery は2段階で、両者は独立している。第1段階（RFC 9728 → 認可サーバの特定
→ RFC 8414 メタデータ取得）が成功しても、第2段階の動的クライアント登録 (RFC 7591) は
メタデータに `registration_endpoint` がある場合にしか成立しない。大手プロバイダでも
これを実装していないことがあり、その場合は OAuth クライアントを自分で登録するしかない。
メタデータが「返ってくる」ことが「自動で繋がる」ことの証拠に見えるのが罠。

**適用方法:**
- 自動 discovery を試す前に、**メタデータを直接取得して `registration_endpoint` の有無を
  確認する**。無ければ事前登録経路（client_id / client_secret / 固定 redirect URI）しか
  ない。判断は curl 1回で付き、失敗したログインから推測するより速い。
- 認可サーバの issuer にパスが含まれる場合、RFC 8414 のメタデータ URL は well-known を
  パスの**前**に挿入する（issuer `https://host/login/oauth` →
  `https://host/.well-known/oauth-authorization-server/login/oauth`）。issuer の末尾に
  付ける OIDC 流儀では 404 になるので、両方の形を試す。
- `registration_endpoint` を持たないプロバイダでも、既存の CLI が保持するトークンや
  PAT を受け付けることがある。外部コマンドでトークンを供給する経路を用意しておけば、
  OAuth アプリの登録自体を回避できる。
- 実装が discovery の失敗を「未ログイン」とだけ報告すると原因が見えない。
  **どちらの段階で落ちたか**をエラーに含める。

### 子プロセスの stdin への同期書き込みは無界 — 期限の外に置くと 1 つの詰まりが全体を止める

**事象:** stdio クライアントが「要求を書く → 期限つきで応答を待つ」の順で実装されていた。
相手が stdin を読まなくなるとパイプが埋まり、`Write` から戻らない。期限は書き込みの**後**に
張られるので、この待ちを誰も監視していない。しかも書き込みロックを保持したままなので、その
サーバーへの他の呼び出しも全部そこで止まる。タイムアウト時に子を kill する処理にも到達しない
ため、自己回復しない。

**なぜ:** 「応答が来ない」テストは書かれていたが、「要求が送れない」テストが無かった。前者は
相手が要求を受け取った後の話であり、送信そのものの停止を一度も通らない。

**適用方法:** 期限は書き込みの**前**に張り、書き込みと応答待ちの両方を覆う。期限切れでは子を
kill する — 読み口が閉じるので、詰まった `Write` は EPIPE で解け、ロックが返る。修正は呼び出し
側ではなく**送信関数**に置く: 同じ穴は通知や応答など全ての送信元にあり、読み取りループから
出す応答は継承すべき期限すら持たない。テストは「stdin を読まないサーバー」と「ロック待ち」を
作る。

## エラー・スキーマ設計

### ツールエラーは {code, message, details} の構造化 JSON で返す

**事象:** エラーを平文文字列で返すと、LLM クライアントは文字列マッチングでしか
分岐できず、プロンプトも実装も不安定になる。

**適用方法:**
- `isError: true` + 単一 text content の中身を構造化 JSON にする:
  `code`（安定 slug: `"path_not_allowed"` 等）/ `message`（人間可読）/
  `details`（マシン可読の文脈: `{"requested": "bash", "supported": ["python"]}` 等）。
- Go 実装: toolerr パッケージに Error 型 + Code 定数群を集約し、`Is(target) bool` を
  Code 比較で実装して `errors.Is` 互換を保つ。sentinel は package-level 変数。
  server 側は `errors.As` → JSON marshal → text content、非構造化エラーは
  `err.Error()` フォールバック。
- 新しい code の追加は互換変更だが、**既存 code の rename は breaking change**。

### クライアントは inputSchema.enum を事前検証する — サーバー側検証は残す

**事象:** enum 違反の呼び出しがサーバーの handler に到達せず、クライアント側で
`invalid_enum_value` として拒否された（Claude Desktop で実測）。

**適用方法:**
- 列挙可能な引数は `inputSchema.enum` で必ず宣言する（往復不要で拒否される良い UX）。
- **同時にサーバー側でも明示的に検証**する — schema を検証しないクライアント・直接
  JSON-RPC を打つテストハーネスに対する defense-in-depth。
- サーバー側 enum 拒否経路のテストはダミー JSON-RPC ハーネスでバイパスして行う
  （実クライアント経由では到達しない）。

### 画像など複数 content block の返却は sentinel 型 + 明示的返却ツールで

**事象:** ツール handler の戻り値を JSON marshal して単一 text block に詰める標準経路では、
画像（PNG plot 等）を返せない。また「実行後にディレクトリを auto-scan して新規画像を
全部返す」設計は、意図しないファイルの混入・heuristic の難しさ・レスポンスサイズの
予測不能で罠が多い。

**適用方法:**
- **RawResult sentinel パターン**: 専用型（`Content []ContentBlock, IsError bool`）を導入し、
  dispatch 側で `if raw, ok := out.(RawResult); ok` なら複数 block をそのまま返す。
  既存ツールは無変更（後方互換）。
- **「何を返すか」は LLM に明示指定させる** `attach_files(workspace_id, paths)` のような
  返却専用ツールを分ける — コントロール可能・監査可能で、サイズ上限強制や path traversal
  防御（`filepath.Clean` + prefix check）も入れやすい。
- ライブラリ関数を monkey-patch して出力を hook する案は副作用が不透明で debug 困難、却下が無難。

## LLM から呼ばれるツールの設計

### 大きなデータをツール引数で渡さない（作業ディレクトリ経由にする）

**事象:** ドキュメント本文を `content` パラメータで直渡しする設計は、大きいファイルで
破綻した。LLM の function call 引数には実用上のサイズ上限がある（数百 KB 程度、
ローカル LLM ではさらに小さい）。これは**ツール設計の primary failure mode**。

**適用方法:**
- `filename` パラメータ + 共有作業ディレクトリ（/work 等）経由のファイル受け渡しを
  正規パターンにする。前段ツールでファイルを配置し、後段ツールは basename で参照する。
- **パラメータ名の曖昧さに注意**: `content` は LLM が「ユーザーの発話文」と「対象
  ドキュメント本文」を取り違える（実例あり: ユーザーのリクエスト文自体を要約対象として
  渡してきた）。`filename` のような型のはっきりした名前を優先し、説明文に
  「NOT the user's request text」等を明示する。
- **XOR 制約は寛容に解釈**: 排他パラメータで空文字列 `""` は「未指定」扱いにする。
  LLM は「使わない」を明示的な空値で表現することが多い。
- **パストラバーサル防御**: filename は basename のみ許可（`/` や `..` を含んだら拒否）。
  LLM は悪意なくとも絶対パスを生成しうる。
- ツールへの LLM ガイダンスは description フィールドのみで完結させる（ホスト側の内蔵
  プロンプトに特定ツールへの参照を入れると結合度が上がる）。description には
  「いつ選ぶか / どのワークフローで呼ぶか / パラメータの意図 / 排他制約」を書く。
- ラップする CLI が進捗を stderr に出す場合は `--quiet` 等で抑制する。

### 一覧を絞る `limit` は応答全体を制限しない

**症状:** lookup 系ツールの `limit` はレコード一覧を制限していたが、`limit: 3`
で呼んでも **162 KB の結果が返り、MCP クライアントに拒否された** — 最も調べる
価値のある入力ほど使えないという状態だった。レコード一覧は指定どおり 1.5 KB。
`limit` の管轄外だった他のフィールドが原因で、1,705 件のタグ集約（63 KB）と
232 件の参照 URL（32 KB）はいずれも「表示分」ではなく**全件**から算出されていた。

**なぜ:** `limit` は呼び出し側が「結果」と認識する対象に自然に結び付く。しかし
集約・相互参照・出典一覧は全件に対して計算され、入力の知名度に比例して増える
ので、構造上そもそも無制限である。スタブのテストでは絶対に出ない — フィクスチャ
の集約は小さいからで、この不具合には裾の長い実データが要る。

**どう適用するか:**
- 呼び出し側が名指しした一覧ではなく、**応答全体**に予算を引く。各フィールドに
  対して「これを小さく保つものは何か」を問う。
- 恣意的に切るのではなく、順位付けされた**裾**を落とす。裏付け数で降順に並んだ
  集約は、最も裏付けの弱い項目から失われる — 読み手が最初に捨てる部分である。
- **落とした件数を必ず計上する** — カテゴリ別の省略数と、平文の注記。黙って
  短縮された答えは拒否されるより悪い。部分的な眺めであることを示す信号がない。
- 計上フィールドは**何かを落としたときだけ**出す。存在すること自体が信号になる。
- 省略は**その場で解除できる**ようにする。打ち切りを引き上げるつまみ
  （`context_top` / `references_top`、`-1` で無制限）があれば、裾は同じ結果の中で
  到達可能なままになる。ここでファイルに逃がしてはいけない — 次項を参照。
- 上限は**予算を持つ面**に置く。パイプラインに流す CLI の `--json` は完全なまま
  でよく、制限が要るのはツール応答だけである。

### サーバーはモデルの context window を知り得ない

**症状:** 同一フリートの file-mediated なサーバー 7 本が、いずれも独立に
`workspace_root` 引数を持つに至っていた。閾値を超えると呼び出し側が渡した
ディレクトリへ結果を書き、パスだけを返す設計である。それらを呼ぶクライアント側は
ツール結果に上限を一切持っていなかった。つまり**存在しないガードを 7 回、それを
実装するのに最も不向きな 7 プロセスが肩代わりしていた**。

**なぜ:** 「大きすぎる」は呼び出し側の context window と、その背後のモデルの
性質であって、サーバーはそのどちらも観測できない。サーバーの閾値は、調整対象と
した 1 クライアント以外すべてに対して外れる当て推量になる。しかも逃がし方の代償が
推量より重い — **クライアントが「名前で指せる」ファイルシステムを持つこと**を
サーバーが前提にしてしまう。ディスクを共有しないトランスポート越しの MCP
クライアントは自分の結果を読めず、サンドボックス下のクライアントは自分のルート外の
パスを開けない。

**どう適用するか:**
- **1 回の応答量を抑えるのは呼び出し側の仕事、溢れた応答を退避するのは
  クライアントの仕事。** 応答量を縛るつまみ（`per_page`、`limit` + `offset`、
  `*_top`）を与え、そのつまみで全値に到達できるようにした上で、求められた分を
  丸ごとインラインで返す。
- 守るべきは**到達性**であってファイルではない。`limit` が既に取得した分しか
  保持していないファイルは、その先へ一歩も到達させていない。末尾まで辿れる
  ページングはそれを過不足なく置き換える。ファイル経路を外す前にこれを確認し、
  もしファイルの方が先へ届いていたなら、先にページングを足す。
- 上限はクライアント側に 1 箇所、ツール結果が会話へ入る境界で掛け、
  **切り捨てではなく退避する** — モデルには先頭のプレビューと、開けるパスを渡す。
  組み込みツールは切り詰めるのに MCP 結果は無制限で素通し、が最悪の組み合わせ。
- ファイルが本質的に必要なのはバイナリだけ（音声・動画・描画済み画像）。
  それでも転送量が収まるなら MCP のコンテンツブロックを優先する。サーバーの
  ディスクを読めないクライアントにとって、パスは無意味である。
- ファイル媒介の撤去は機能の喪失ではなく、依存の除去である。ただしスキーマから
  引数が消えるのは破壊的変更なので、移行手順（小さいページ + ループ）とともに
  CHANGELOG に書く。

### ツール結果に内部 ID を露出しない

**事象:** ツール結果に `[Stored as object ID: %s]` を含めたところ、LLM がその ID で
redundant なリンクをチャット応答に書き込むようになった（本体は別経路で表示済みなのに）。

**適用方法:**
- ツール結果には「LLM が後続のツール呼び出しで使う情報」だけを含める
  （次のツールで使う ID は残す）。
- ユーザー側に専用 UI で表示済みのコンテンツの ID は結果から除外する。
- 「表示はこちらで処理した」ことは最小限のステータス
  （"SUCCESS: ... displayed to the user. Reply briefly."）で伝える。

### ツール一覧はセッションごとに払うコンテキスト — 接続時に部分集合を選ばせる

**事象:** ツール 44 個を返す MCP サーバの `tools/list` 応答が約 121 KB あった。実際に
使うのは十数個で、残りは毎セッション読まれるだけのコンテキストだった。

**なぜ:** `tools/list` はセッション開始時に必ず全量が読まれ、モデルはその全文を
コンテキストとして負担する。説明文が1本あたり数百バイトでも、数十本集まればプロンプトの
主要な構成要素になる。しかも重さは本数に比例せず、**説明文の長い少数のツール**に偏る。
実測では group 単位（カテゴリ）で 44 → 38 本に絞っても 121 KB → 106 KB にしかならず、
個別指定で 12 本にすると 32 KB まで落ちた。group 単位の選択はほとんど効かない。

**適用方法:**
- ツールが 20 本を超えるサーバは、**接続時に部分集合を選ばせる手段**を用意する
  （リクエストヘッダ、URL パス、起動フラグのいずれか）。実用的な軸は allowlist /
  denylist / 読み取り専用の3つ。
- group（カテゴリ）単位だけでは足りない。**個別ツール名での指定**を必ず用意する。
- 絞るのは**上流（サーバ側）**でやる。中継やクライアントで捨てる方式はペイロードの
  転送を払い、透過中継であれば「メッセージを解釈しない」不変条件も壊す。
- 未知の名前の扱いを決めて文書化する。allowlist の未知名は起動失敗、group の未知名は
  黙って無視、のように非対称だと利用者は気づけない。
- 名前リストは上流の改名で黙って効かなくなる。**設定しっぱなしにせず見直す対象**だと
  文書に書く。

### 制御層を作る前に、対象の能力面を列挙する

**事象:** 「最悪の操作（リポジトリ削除）だけは踏めないようにしたい」という要件から、
中継側にツールを隠す機能を実装しようとした。着手前に上流の全ツール 89 個を列挙した
ところ、リポジトリ削除に相当するツールは**存在しなかった**。ブランチ・タグ・リリースの
削除も force push も無く、破壊的操作はファイル削除1個だけだった。

**なぜ:** 「その API が許す操作」と「その MCP サーバが露出しているツール」は別物で、
後者は前者よりずっと狭いことが多い。前者から想像した脅威に対して制御層を作ると、
守る対象の無い機能だけが残る。未使用機能はそれ自体が保守コストになる。

**適用方法:**
- 制御を設計する前に `tools/list` を全量取得し、**名前と説明の両方**を破壊的な語
  (delete / remove / destroy / archive / transfer) で走査する。名前に現れない削除
  （`*_write` 系のメソッド引数など）があるので説明文も見る。
- 恒久的な制限が要るなら、**ツール名の denylist ではなく資格情報の権限**で行う。
  名前リストは上流がツールを追加・改名した時点ですり抜けるが、資格情報に権限が
  無ければ実装されても実行できない。
- 列挙結果は日付とともに記録する。ツール構成は上流の都合で変わるので、
  「〜時点で存在しない」と書く。
- 中継に機能を足す前に「上流が既に同じことを提供していないか」を確認する。
  提供されているなら、実装しないのが正解。

### 必須引数の型アサーションを捨てると、欠落がゼロ値の破壊的既定になる

**事象:** 文字列置換ツールの一括形式が `m["new_string"].(string)` と書かれ、戻り値の ok を
捨てていた。キーが無い・`null`・数値のいずれでも結果は `""` になり、後段の検査はそれを拒否
しない。したがって `{"old_string": "重要な文字列"}` という引数が、その文字列の**削除**として
実行された。単発形式には必須チェックがあり、挙動が食い違っていた。

**なぜ:** モデルに渡すスキーマの `required` は実行側を守らない。そしてゼロ値が「意味のある
安全な既定」であるとは限らない — 空文字は削除、false は「一意性を要求」、0 は「無制限」に
なり得る。同じツールに解析経路が 2 本あると、片方だけが検査を持つ。

**適用方法:** 必須引数は存在と型を同時に確認する（Go なら `v, ok := m[k]` と
`s, ok := v.(string)` の両方）。ゼロ値が破壊的になる引数では、欠落・型不正・意図的な空を
区別する。そして**解析経路を 1 本にする** — 単発形式は「1 要素の一括形式」として同じ関数を
通す。2 つの実装が一致し続けることを目視で保つのは失敗する。

## 上流 API との契約

### 再試行の安全性は「トークンの意味」ではなく「自分が名付けた資源」で担保する

**症状:** BigQuery を叩く MCP サーバーで、`jobs.query` に `requestId` を付ければ
1 回の再試行は冪等だと設計した。独立レビューが Discovery ドキュメントを読み直すと、
`requestId` の重複排除は**変更系クエリにしか効かない**と書いてあった（読み取り
クエリは「データに対して nullipotent」— コストに対してではない）。リクエストが
上流に届いた後に応答だけ失われると、SELECT が 2 回走り 2 回課金される。

**なぜ:** 冪等トークンの意味論は API ごとに違い、しかも「読み取りには不要」という
文言は「読み取りは再実行しても安い」と読み違えやすい。安全性を上流の解釈に委ねる
設計は、レビューで読み直されるまで正しく見える。

**どう適用するか:**
- 再試行して困る操作は、**クライアントが名前を付けた資源**として作る（BigQuery なら
  `jobs.insert` に自前の `jobId`）。2 回目は `409 duplicate` で返り、既存資源で続行
  すればよい。名前は再試行の前に決め、同じ名前で送り直す。
- 上流の冪等トークン（`requestId` 等）は説明文を**全文**読み、対象操作と保証範囲を
  設計文書に引用する。「読み取りは省略可」は「再実行が無料」ではない。
- 読み取り専用と宣言する API でも、課金・監査・レート quota という副作用がある。
  再試行の可否は副作用の有無で決める。

### ページング応答に統計が無いなら、資源本体を読む

**症状:** 同じサーバーで、`jobs.getQueryResults`（結果ページ）の応答から課金バイト数と
スロット時間を取る設計にしていた。その応答型には `totalBytesBilled` も `totalSlotMs`
も `statementType` も無く、最初の応答が `jobComplete=false` で返った時点で値は
永遠に手に入らない。単体テストは初回応答で完了する台本だったので通っていた。

**なぜ:** 「実行 → ページ取得」という 1 本の流れに統計を乗せたくなるが、API は
「資源（ジョブ）」と「その結果のページ」を別の型で返す。ページ型は行を運ぶために
軽く作られており、資源型にしか無いフィールドがある。台本テストは設計者の理解を
写すだけで、型の欠落を検出しない。

**どう適用するか:**
- 応答に使うフィールドは**型定義（Discovery / OpenAPI）から機械的に確認**する。
  「あるはず」で読まない。
- 完了後の統計は資源本体（`jobs.get`）を 1 回読む。結果ページはページングだけに使う。
- 偽サーバーのテストには「初回応答が未完了で、完了はポーリング後」の台本を必ず入れる。
  設計者の想定どおりに返る台本だけでは、型の欠落は見えない。

### 空文字は「未指定」ではない — 省略できるフィールドは省略する

**症状:** ジョブの `jobReference.location` を設定値そのまま（未設定なら `""`）で
送ったところ、BigQuery は `Invalid value for location:  is not a valid value` で
拒否した。偽サーバーは `""` を受け入れていたので単体・結合テストは全て通り、実
プロジェクトへの live テストで初めて落ちた。

**なぜ:** Go の構造体をそのまま JSON にすると、未設定の文字列は `""` として**存在
する**フィールドになる。上流にとって「無い」と「空」は別で、省略時のみ推定
（この場合はデータセットからのロケーション推定）が働く。

**どう適用するか:**
- 上流が「省略可」と書くフィールドには `omitempty` を付け、テストで**キーが存在
  しないこと**を確認する（値が空であることではなく）。
- 偽サーバーは「寛容」であってはいけない。本物が拒否する入力を偽サーバーも拒否
  させるのは難しいので、**live テストを opt-in で必ず用意**し、リリース前に 1 回は
  通す。偽サーバーだけのテストは設計者の理解の写しである。

## サーバー実装の構成

### 新規 Go MCP サーバーは実績ある骨格を移植する

**事象:** MCP サーバーの transport / JSON-RPC / protocol routing / エラー型は
サービス内容に依存しない generic な部分で、毎回ゼロから書くのは無駄かつ品質が揺れる。

**適用方法:** 4 パッケージ構成の骨格を確立し、新規サーバーは scaffold 段階でこれを移植する:
- `internal/transport/` — stdio: `bufio.Scanner`（大きめ buffer）+ `json.Encoder` +
  mutex serialised write
- `internal/jsonrpc/` — JSON-RPC 2.0 型 + 標準コード定数
- `internal/mcpserver/` — protocol routing + `RegisterTool` API + 構造化エラー出力
- `internal/toolerr/` — `{Code, Message, Details}` + `errors.Is` by code

移植時の変更は import path、sentinel code 定数の差し替え、不要機能（RawResult 等）の削除
程度。ツールハンドラ層と上流クライアントだけを新規実装する。

### 二重状態（in-memory + disk）の mutation は必ず同じ層を経由させる

**事象:** 長寿命の in-memory セッション + disk ファイルの二重状態で、disk だけ書き換える
mutation（rename 等）が in-memory コピーをバイパスした。その後のほぼ毎アクションで走る
save が古い in-memory 値で disk を上書きし、「リネームが効かない/再起動で戻る」ように
見えた。同型の罠を 2 回踏んだ。

**適用方法:**
- per-session 状態を変更する操作は**すべて状態を所有する層（agent 層）を経由**させる。
  UI bindings から永続化パッケージを直接呼ぶのは禁止（レビュー時の赤旗パターン）。
- 状態所有層に同名メソッドを作り、mutex 保護下で in-memory も更新する。bindings は
  thin pass-through にする。
- **ガード判定の罠**: in-memory 値を読んで判定するガード（`if Title != "New Session"` 等）も
  同じ理由で誤動作する。上書き経路（Mode A）と誤判定経路（Mode B）の両方をテストで固定する。

### 巨大な上流文書は索引を先に返し、区画をページングで開く

**事象:** 1 ファイルのサンドボックス挙動サマリが 2 MB 超（数千件のリストが十数
区画）、ATT&CK ツリーが 258 KB あり、どちらもツール応答にそのまま入れられなかった
（lookup CLI+MCP プロジェクト、2026-09）。

**なぜ:** 応答全体に予算を引く原則（前出）はあっても、上流が「1 文書」で返す API
では limit の掛かる一覧がそもそも無い。順位付けされた裾を落とす方式も効かない —
どの区画が要るかは呼び出し側にしか分からない。

**適用方法:**
- 1 回目の応答は**索引**にする: 区画名と件数だけを返し、中身は返さない。スカラー
  （判定値・フラグ）だけ索引に同乗させる。
- 2 回目以降は `section` + `offset`/`limit` で **1 区画をページング**し、全項目が
  同じツールの中で到達可能な状態を保つ（到達性の原則）。
- **リストだけでなく map も区画**として扱う。実測では 63 キーの map が索引に同乗
  して予算を食い潰しかけた。map はキー順の {key, value} でページングする。
- 上流文書はまるごと 1 回だけ取得してキャッシュし、区画ページングはローカルで
  行う — ページ送りのたびに 2 MB を再取得しない。
- 木構造（ATT&CK ツリー等）は**既定を識別情報だけの圧縮版**にし、`full: true` で
  生の木を開けるようにする。何を落としたかは注記で計上する。

### アカウントの生きた設定状態はキャッシュしない

**事象:** 自アカウントの検知ルールセット一覧・詳細を結果キャッシュに載せる設計を
検討したが、この API の典型ユーザーは「コンソールでルールを有効化した直後に、
反映されたかをツールで確認する」人だった（lookup CLI+MCP プロジェクト、2026-09）。

**なぜ:** 調査対象のデータ（外界の観測）は TTL で古びるだけだが、自アカウントの
設定は**利用者自身がいま書き換えたもの**。キャッシュされた「disabled」は反映済みの
変更を「効いていない」と誤報し、利用者に自分の操作を疑わせる。

**適用方法:**
- 結果キャッシュの対象は「外界の観測」に限る。自アカウントの設定・状態を返す
  ツールは常に live で答える。
- 有効/無効のような発火条件は値を返すだけでなく**帰結を言う**
  （enabled: false → 「このルールは発火しない」）。

### 取得した文書は文字位置でページングし、ターンの間だけメモリに保持し、基準が動いたことを文書 id で伝える

**事象:** ページ本文を返す取得サーバは、MCP のテキストブロックが 20,000 バイトを超えると
作業ディレクトリへ退避するローカルモデル向けランタイムのために応答を縛る必要があった。
既定の応答サイズは rune で決めるのに上限はバイトで、TTL を過ぎたページ送りは変わった
ページの上に黙って着地しうる（web-fetch、2026-09）。

**なぜ:** 前の 2 エントリのとおり、縛るのは呼び出し側の仕事で、退避はクライアントの仕事。
残るのはページングを正直にすること — 全文字に到達でき、同じ offset が同じテキストを指し、
切れたことが報告される。モデルが推論できるのは rune の knob で、ランタイムが強制するのは
バイトの上限。既定はバイト上限と一次利用言語の 1 rune あたり最悪バイト数（CJK ≈ 3）から
導き、その後ランタイムで計測する。

**適用方法:**
- `max_chars` + `offset` は rune 単位。`total_chars` と `returned_chars` を常に返し、
  `truncated` と `next_offset` は切れたときだけ出す。末尾以降の offset は空ページであって
  エラーではない。
- 復号後本体のハッシュを `doc_id` として返す。ターンをまたいで同じ id = 同じ基準、違う id =
  0 からやり直し。ページ送りが再取得しないよう、復号済み文書を TTL の間メモリに保持する。
  エラーはキャッシュしない。ディスクには書かない。
- 既定は消費側のインライン上限と言語のバイト比から導いてから計測する（20,000 バイト上限と
  日本語なら 6,000 rune）。計測した JSON サイズはプロジェクトの Gotchas に記録する。
- ツール文言は契機と契約だけ（いつ呼ぶか、`truncated` が何を意味するか）。防御文言は
  書かない — その層はランタイムのもの。

# シェルスクリプト

Bash / zsh / sed の落とし穴。各項目は「事象 → なぜ → 適用方法」。

---

## macOS の sed は BSD sed — GNU sed とは非互換、しかも環境依存で入れ替わる

**事象:** Linux（GNU sed）で動くスクリプトが macOS で壊れる、またはその逆、という
トラブルに繰り返し遭遇している。さらに Homebrew で GNU sed（`gsed`）を導入した
マシンでは「どちらの sed が動くか」自体が環境依存になり、「自分のマシンでは動いた」が
移植性の根拠にならない。

**なぜ（主要な非互換）:**
- **`-i`（in-place）の構文が違う**。BSD sed は拡張子引数が必須
  （`sed -i '' -e 's/a/b/' f`）、GNU sed は bare `-i` が使える。
  `sed -i '' ...` は GNU では「空ファイル名」扱いで壊れ、bare `-i` は BSD では
  次の引数を拡張子として食う。
- GNU 拡張（BRE の `\+` `\|`、`s///I` フラグ、`sed -z` 等）は BSD に無い。
  `a`/`i`/`c` コマンドの行継続の扱いも異なる（BSD は `a\` + 改行が必要）。
- **alias は非対話シェル専用**: 対話 zsh で `alias sed=gsed` していても、
  スクリプト内の `sed` は PATH 解決で別物になる。逆に Homebrew の gnubin
  （`$(brew --prefix)/opt/gnu-sed/libexec/gnubin`）を PATH に入れていると
  スクリプトまで GNU sed になり、素の macOS と挙動が変わる。
  対話で動いたワンライナーがスクリプトで壊れる（逆も）のはこの構造のせい。

**適用方法:**
- スクリプトでは **`-i` を使わない**のが最も安全: `sed ... > tmp && mv tmp file`
  のパターンに統一する（コンテナ/Linux と macOS の両方で同一挙動）。
  `-i` を使うなら両実装で通る**付加形式 `-i.bak`**（+ 後で `.bak` 削除）に限定する。
- GNU 拡張が必要なら暗黙の `sed` に頼らず **明示的に `gsed` を呼び**、
  `command -v gsed` で存在確認して無ければ明確なメッセージで fail する。
- どちらが動いているかのランタイム判定は `sed --version` が使える
  （GNU のみ応答し、BSD sed はエラーになる）。
- レビュー観点: `sed -i` を見たら「どの OS で、どの sed で走るか」を必ず問う。

## zsh の変数展開は bash と別物 — 単語分割もグロブもしない

**事象:** bash 前提のワンライナーやスニペットを macOS のデフォルト対話シェル
（zsh）に貼ると挙動が変わる、というトラブルに繰り返し遭遇している。

**なぜ（主要な差分）:**
- **クォート無し `$var` を単語分割しない**（`SH_WORD_SPLIT` 既定 off）:
  `opts="-l -a"; ls $opts` は bash では 2 引数に割れるが、zsh では
  `"-l -a"` という 1 引数のまま渡る。
- **クォート無し `$var` をグロブ展開しない**（`GLOB_SUBST` 既定 off）:
  `pat='*.md'; ls $pat` は zsh ではリテラル `*.md` を渡す。
- **マッチしないグロブはエラー**（`NOMATCH` 既定 on）: bash はパターンを
  リテラルのまま渡すが、zsh は `zsh: no matches found` で**コマンド実行前に
  中断**する。`scp host:*.gz .` がローカルの glob 失敗で落ちるのが典型例。
- **配列は 1 始まり**で、`$array` は全要素に展開される（bash は先頭要素のみ）。

**適用方法:**
- **スクリプトは必ず `#!/bin/bash`（または `#!/usr/bin/env bash`）の shebang を
  付けて bash として実行**し、対話シェルの方言に依存させない。`sh file.sh` や
  `source` での取り込みは interpreter が変わるので避ける。
- zsh を対象に書く場合は明示演算子を使う: 単語分割は `${=var}`、グロブ展開は
  `${~var}`、マッチなし許容は `*.tmp(N)`（または `setopt null_glob`）。
  引数リストはそもそも文字列でなく**配列**で持つ（`opts=(-l -a); ls $opts`）。
- リモート側で展開させたいグロブ（scp/ssh）は必ずクォートする。
- ドキュメントに載せるワンライナーは「bash で実行」を明記するか、
  bash/zsh 両方で挙動が同じ形に整える。

## trap ハンドラは関数スコープ外で実行される

**事象:** cleanup 用の trap ハンドラが `local` 変数を参照しており、`set -u` 環境で
unbound variable エラーになった（同じ罠を 3 回踏んだ）。

**適用方法:**
- trap ハンドラで参照する変数は必ずグローバルに宣言する。
- `set -e` 環境では trap 前のコマンドが非 0 で終了するとスクリプトが即死する —
  `|| true` で保護する。
- `EXIT` だけでなく `INT TERM` も trap 対象にする。

## `${var//pattern/replacement}` のパターンに `$(...)` をインラインで書かない

**事象:** Makefile の `$(VAR)` 参照を解決する置換ループが**無言で**全く動かなかった。
エラーも出ないため、テストを書くまで原因が見えなかった。

```bash
s='$(OUT)'; val='dist/tool'
echo "${s//\$(OUT)/$val}"               # => $(OUT)   置換されない（エラーも出ない）
pat='$(OUT)'; echo "${s//"$pat"/$val}"  # => dist/tool 正しい
```

**適用方法:** プレースホルダ置換を bash で書くときは、パターンを変数に入れて
`${s//"$pat"/$rep}` の形にする。インライン形式の既存コードを見たら疑う。
「冗長だから」とインライン化してはいけない（コードに禁止コメントを残すのが有効）。

## 運用スクリプトはルートを $PWD から推定しない — そして検査のスキップを緑と報告しない

**事象:** 組織横断ヘルスチェックスクリプトが検査対象ルートを `$(pwd)` 既定で取って
いた。エージェントのシェルが直前の作業ディレクトリ（別リポ）のまま実行した結果、
全リポが「not found locally」— ただし警告扱い — になり、**何も検査していないのに
「Result: all checks passed.」exit 0** が出た。誤った cwd での実行は一度きりでなく
繰り返し起きていた: エージェント環境の作業ディレクトリは呼び出し間で持続する
**不可視の状態**で、実行者の信念と静かにずれる。

**なぜ:** 2 つの欠陥の合成。①スクリプトは自分の位置（`BASH_SOURCE`）からルートを
導出できるのに、呼び出し元の cwd に委ねた — 最も信頼できない入力に最重要の判断を
任せた形。②見つからないリポを警告で済ませ、エラーに計上しなかった — スキップした
検査が合格に見える fail-open。片方だけなら実害は小さい（①だけなら INCOMPLETE が
出て気づける、②だけなら正しいルートで走る）が、合成すると「検査ゼロの緑」になる。

**適用方法:**
- 検査対象ツリーの中に置くスクリプトは、ルートを **`BASH_SOURCE` からの相対で導出**
  する（`SCRIPT_DIR/../..` 等）。`$PWD` 既定は「呼び出し元が正しい場所に立っている」
  という検証されない仮定。明示引数での上書きは残してよい。
- 検査スクリプトは**スキップを合格から分離**する: 見つからない・読めない対象は
  数え、要約を「INCOMPLETE — N 件未検査」にして非ゼロ終了する。緑は「全対象を
  検査して全部通った」ときだけ — 検査は自分が検証した以上を主張してはならない。
- 運用者側の対の習慣: エージェントのシェル呼び出しは `cd /絶対パス &&` を前置する。
  ただし規律は必ずどこかで破れるので、スクリプト側の機構が本命の防壁。

## 検査の入力が「取れなかった」ことを、空の答えと区別する

**事象:** 組織横断ヘルスチェックを速くする作業の途中で、同じ形の fail-open が 3 つ見つかった。

- tap の版数照合は、リポごとの最新リリースを `$(gh release view … 2>/dev/null || true)` で
  取り、空なら「リリースが見えない = ずれではない」として飛ばしていた。gh の認証が通らない
  状態で走らせると 92 件すべてが飛ばされ、`[OK] 92 entr(ies) point at their latest release`
  と「all checks passed」が出た。
- fetch の失敗は `2>/dev/null` で黙らせていた。1 つのリポの fetch だけを失敗させると、前回
  取得した古い `origin/main` と比べて `[OK] up to date` になった。
- 組織のリポ一覧は `gh repo list --limit 300` で取っていた。gh は上限に達すると何も言わずに
  打ち切る。切れた先のリポは「未リリース・未アーカイブ」と読まれる。

あわせて、合格行の件数は比べていないエントリも数えていた（92 と表示、実際に比べたのは 91）。

**なぜ:** `$(cmd 2>/dev/null || true)` は「失敗した」を「空だった」に畳む。そして空は正当な
答え（リリース無し、ずれ無し）でもあるので、失敗が合格の経路を通る。古い ref も同じ形で、
取れなかった入力が「前に取れた値」という正当に見える姿で残る。前の項目は「対象が見つからない」
場合を塞いだが、「対象はあるのに入力が取れない」場合は別の経路だった。

**適用方法:**
- 外部から取る入力は、取った場所で 1 回だけ判定する。コマンドが無い・失敗した・空だった・
  上限ちょうど（打ち切りの可能性）のどれかなら「使えない」とし、中身を空にして一部だけを
  読まれないようにする。
- 使えないことは 1 回だけ「NOT checked」と表示して INCOMPLETE に数える。消費側の検査は、
  入力が無いときに合格行を出さない。
- 件数を名乗る合格行は、実際に比べたものだけを数える。比べなかったものは別に書く。
- fetch のような準備段の失敗は記録し、その対象の比較を「NOT checked」にする。古い ref とは
  比べない。
- 修正の前後とも、本物の対象に故障を注入して確かめる。gh は無効なトークン（`GH_TOKEN` に
  でたらめな値）で落ちる。1 つのリポの fetch だけを落とすには、そのリポの URL にだけ届かない
  プロキシを向ける（`GIT_CONFIG_COUNT=1 GIT_CONFIG_KEY_0=http.<repo-url>.proxy
  GIT_CONFIG_VALUE_0=http://127.0.0.1:9`）。リポにも設定ファイルにも手を触れずに済む。
- 「出力が前と同じ」は、この種の検査を作り替えたときの同等性の証拠にならない。入力が無くても
  合格行を出す検査は、空振りしても同じ行を出す。新旧の答えを項目ごとに直接突き合わせる。

## `&&` チェーン末尾の `|| true` は、末尾のコマンドではなくチェーン全体を許す

**事象:** リリース検証がこう書かれていた。

```sh
unzip -q "$zip" -d "$tmp" && "$tmp/$bin" --version && spctl -a "$tmp/$bin" | head -2 || true
```

`|| true` は参考情報である `spctl` のために書かれていた。ところが zip が展開できなくても、
バイナリが起動しなくても、最後に「検証 OK」が表示された。

**なぜ:** `A && B && C || true` は `(A && B && C) || true` と解釈される。`||` は直前の
コマンドではなく、それまでのリスト全体を左辺に取る。失敗を許したい 1 コマンドのために書いた
`|| true` が、必須ゲートを丸ごと飲み込む。

**適用方法:** 失敗を許すコマンドは**独立した文**に分ける。必須ゲートは 1 つずつ、それぞれの
失敗メッセージとともに `|| { echo …; exit 1; }` で止める。パイプの終端に `head` を置くと終了
ステータスが `head` のものになる点も同じ罠であり、`|| true` を足す理由にはならない。

## `set -o pipefail` 下の `cmd | grep -q` は一致したのに失敗する

**事象:** リリース検証スクリプトで、ダウンロードしたバイナリの署名を確認していた。

```sh
set -o pipefail
codesign -dvv "$bin" 2>&1 | grep -q '^Authority=Developer ID Application' || { echo "FAIL: not Developer ID signed"; rc=1; }
```

その直前の行 — `-q` 無しの同じコマンド — は `Authority=Developer ID Application: …` を
印字したばかりだった。それでも正しく署名された資産に対してゲートは FAIL を 2 回出した。

**なぜ:** `grep -q` は最初の一致で終了する。生産側にまだ出力が残っていると、次の書き込みが
閉じたパイプに当たり SIGPIPE（ステータス 141）で死ぬ。`pipefail` 下ではパイプラインの終了
ステータスは右端の非ゼロなので、出力が一致行より長いときは**一致が失敗**になる。`-q` 無しの
grep は末尾まで読むので生産側は正常終了し、隣の行は問題なく見えた。挙動は競合依存で、短い
出力はパイプバッファに収まって通ることがある。

**適用方法:** 生産側の出力を一度変数に取り、それを grep する —
`info=$(codesign -dvv "$bin" 2>&1); printf '%s\n' "$info" | grep -q …`。または全部読む形
（`grep -c … >/dev/null`）にする。乱数トークンの常套句も同じ罠で、
`LC_ALL=C tr -dc 'a-z0-9' </dev/urandom | head -c 24` は `head` がパイプを閉じて `tr` が 141 で死に、
`set -euo pipefail` ではその行でスクリプトごと止まる（spice-client の実ピアゲート、2026-09-18、
最初の `podman run` の前。この節が knowledge にある状態で踏んだ）。`openssl rand -hex 16` は
必要な分だけ読む。終了ステータスをゲートに使うパイプラインに、`pipefail`・
出力の多い生産側・早期終了する消費側（`grep -q`、`head`、`read`）を同居させない。1 行前に
印字された同じ証拠と矛盾する FAIL をゲートが出したら、資産より先に配管を疑う — そして FAIL を
理屈で片付けず、検査を直して再実行し機械の判定を取る。

## macOS の bash 3.2 では、`set -u` 下の空配列が unbound variable になる

**事象:** フィクスチャのスクリプトが任意の引数を配列で組み立て、長いコマンドの途中で展開していた。

```sh
set -euo pipefail
AUDIO_ARGS=()
[ -n "${WANT_AUDIO:-}" ] && AUDIO_ARGS=(-audiodev spice,id=a -device virtio-sound-pci,audiodev=a)
podman run ... "${AUDIO_ARGS[@]}" ...
```

オプションを off にすると、スクリプトは何もしないうちに
`AUDIO_ARGS[@]: unbound variable` で死んだ。

**なぜ:** macOS は今も `/bin/bash` として bash 3.2 を配っており、そこでは**空**配列に対する
`"${arr[@]}"` が `set -u` の下で「未設定」と見なされる。bash 4.4 以降はこれを特別扱いする。
`#!/bin/bash` のスクリプトは Homebrew でどの bash を入れていても macOS では 3.2 で動くので、
bash 5 で開発・試験していると見えない。

**適用方法:** 任意の配列は `${arr[@]+"${arr[@]}"}` で展開する。空なら何も出さず、要素があれば
そのまま展開される。引数の無い関数の `$@` も同じである。呼び出しの前後で `set +u` に頼らないこと。
その行の他のすべてについても検査を切ってしまう。同じ構文の隣にあるもう 1 つの罠も覚えておく。
バックスラッシュで継続しているコマンドの途中に `#` のコメントは置けない。継続を飲み込み、コマンドは
誤った引数で走るか、まったく走らない。

## `if` 文の直後の `$?` は条件ではなく `if` 文自身の終了状態

**事象:** 失敗を分類して再試行するヘルパを書いた。「アドレス使用中」なら再試行し、
それ以外はそのままの終了状態で呼び出し元へ返す設計である。

```sh
retry_on_port_collision() {
    while true; do
        if error="$("$@" 2>&1)"; then return 0; fi
        status=$?                       # ここが誤り
        case "$error" in
            *"address already in use"*) sleep 1 ;;
            *) echo "$error" >&2; return "$status" ;;
        esac
    done
}
```

「それ以外」の経路のユニットテストが落ちた。コマンドは 125 で失敗しているのに、
関数は 0 を返した。`error` には失敗時の標準エラー出力が正しく入っており、
`case` の分岐も正しい方に入っていた。壊れていたのは状態の受け渡しだけである。

**なぜ:** `if` は複合コマンドであり、それ自身の終了状態を持つ。条件が偽で `else` も
`elif` も無ければ、`if` 文は **0** で終わる。`fi` の後で `$?` を読むと、読めるのは
`if` 文の状態であって条件の状態ではない。これは POSIX の定める挙動で、シェルによる
差も無い。失敗を握り潰す向きに働くため、「異常系だけが静かに成功扱いになる」という
最も気付きにくい形で出る。

**適用方法:** 条件の終了状態は分岐の**内側**で読む。`else` に入った直後の `$?` は
条件の最後のコマンドの状態である。

```sh
if error="$("$@" 2>&1)"; then
    return 0
else
    status=$?
fi
```

`cmd && return 0` の形にして直後に `$?` を読む手もあるが、`set -e` 下では左辺の失敗で
`&&` リスト全体が失敗し、そこでシェルが終了するので使えない。条件式の中は `set -e` の
対象外なので、`if`/`else` の形が唯一安全に書ける形である。同じ誤りは `while`、`until`、
`case` の後にもある。条件の状態を保存したくなったら、必ず分岐の内側で保存する。

## `! grep -q` は grep のエラーも「一致しない」と読む — `-` で始まるパターンは `-e` で渡す

**事象:** 変換後のファイルに古い形が残っていないことを、テストで
`! grep -qF '--version && \' file` と確かめていた。このテストは、変換が何も書き換えなかった
場合にも合格した。

**なぜ:** パターンが `-` で始まるので、grep はそれを**オプション**として読む。知らない
オプションなので使い方を表示し、終了コード 2 で終わる。grep の終了コードは 3 値（0 = 一致、
1 = 不一致、2 = エラー）だが、`!` はそれを 2 値に畳み、2 も「不一致」として真にする。否定した
検査は、検査そのものが走らなかったときに合格の側へ倒れる。

**適用方法:**
- パターンは常に `-e` で渡す（`grep -qF -e "$pat" file`）。`-` で始まるパターンも、変数から
  来るパターンも同じ。
- 「無いこと」を確かめるときは `!` で済ませず、1 を明示的に要求する:
  `rc=0; grep -qF -e "$pat" file || rc=$?; [ "$rc" -eq 1 ]`。2 が来れば落ち、`set -e` の下でも
  安全に書ける。
- 否定の検査は一度わざと壊して、落ちることを見る。今回の手掛かりは、テストの出力に混ざった
  grep の使い方表示だけだった。合否の件数だけを見ていたら、合格として通っていた。

## `git rev-parse` は無い ref の名前を標準出力に出す — `--verify --quiet` で読む

**事象:** サブモジュールのポインタ照合が
`latest=$(git -C "$sub" rev-parse origin/main 2>/dev/null || echo unknown)` と書かれ、
`unknown` なら「取得できず」と警告する分岐を持っていた。この分岐は一度も動かない。
`origin/main` が無いと `latest` は `origin/main` と `unknown` の 2 行になり、その 2 行を
「最新コミット」として並べた「out of sync」の失敗が出る。同じスクリプトの別の検査は
`remote=$(git rev-parse origin/main 2>/dev/null || git rev-parse origin/master 2>/dev/null)`
で、どちらも無いと `set -e` の下でスクリプト全体がその場で終わり、最終判定の行も出なかった。

**なぜ:** `--verify` なしの `git rev-parse` は、解決できなかった引数をそのまま標準出力に書き、
エラーを標準エラーに出して終了コード 128 で終わる。`2>/dev/null` が消すのはエラーだけで、
名前は `$(...)` に入る。代入文 `x=$(…)` の終了状態はコマンド置換の終了状態なので、`||` の
右辺も失敗すれば `set -e` が効く。

**適用方法:**
- ref の値は `git rev-parse --verify --quiet "$ref^{commit}"` で読む。無ければ何も出さず、
  終了コード 1 で終わる。
- 代入は失敗しない形に閉じる（関数の中で候補を順に試し、最後に `return 0`）。空は「ref が
  無い」として、呼び出し側が明示的に扱う。
- `|| echo unknown` のようなフォールバック値で分岐する書き方は、左辺が失敗時に何も出力しない
  ことを前提にしている。その前提を、ref の無いリポで一度実測する。

## xargs は空の入力の扱いが実装ごとに違う — `git -C ""` と組むと呼び出し元で動く

**事象:** リポの一覧を `xargs -0 -n 1 -P 8 sh -c 'git -C "$1" fetch …' _` に流して並列に
fetch するようにした。一覧に空行があるときや一覧が空のときの動きを確かめると、xargs の実装に
よって答えが違った。

**なぜ:** GNU xargs は、入力が空でもコマンドを引数なしで 1 回実行する（`-r` で止まると
文書化されている）。macOS の xargs は実行しないうえ、`-0` の空の項目を捨てる（実測）。
そして `git -C ""` は文書どおり「カレントディレクトリのまま」になるので、空の引数が渡れば、
呼び出し元のリポで fetch が走る。macOS で試す限り、この経路は一度も起きない。

**適用方法:**
- xargs に呼ばれる側で空の引数を弾く（`[ -n "$1" ] || exit 0`）。どの xargs でも効く。
- そのガードは xargs 経由ではテストできない — macOS の xargs は空の引数を渡さない。
  呼ばれる側の処理を変数に置き、`sh -c "$worker" _ ""` と `sh -c "$worker" _` を直接呼んで
  テストする。GNU xargs が渡しうる入力を、手元の xargs を介さずに再現する。
- ガードを外した版でテストが落ちることを確かめる。最初に xargs 経由で書いたテストは、
  macOS ではガードを外しても合格していた。

## Go の `font.Drawer` は無い文字を豆腐で描き、描画の失敗を黙って捨てる — 字形の有無は自分で判定する

**事象:** mermaid の図を画像にするエンジンの設計（2026-09）で、`golang.org/x/image` v0.46.0 の
振る舞いを独立検証パスが実測した。

- `font.Drawer` の `DrawString` / `MeasureString` は、`GlyphAdvance` などが返す `ok`（字形の番号が 0 で
  ないこと）を見ない。フォントに無い文字は `.notdef`（豆腐）で描かれ、`LoadGlyph` が失敗した文字は
  何も描かれず、どちらもエラーにならない。
- 読み込み（`ParseCollection` → `Font` → `NewFace`）には成功するのに、特定の文字の `LoadGlyph` で
  失敗する書体が実在する。macOS のシステムフォントで 9 書体（ITFDevanagari 8 書体と KohinoorTelugu 1 書体、
  `unrecognized CFF 2-byte operator (12 37)`）。ITFDevanagari の 2 書体では数字の `1` が描けない。
- Apple Color Emoji は字形の番号は 0 でないのに輪郭が無い（sbix 形式のビットマップで、`x/image` は描けない）。

**なぜ:** `font.Drawer` は「その書体が文字列をすべて持っている」前提の便利関数で、欠けや失敗を
呼び出し側へ返す経路を持たない。読み込みの成功は、個々の字形が描けることを保証しない。

**適用方法:**
- 文字ごとに書体を選ぶループを自前で書く。字形の番号が 0、または `LoadGlyph` がエラーなら、その書体には
  「無い文字」として次の書体へ回す。どの書体にも無ければ、欠けた画像を出さずにエラーにする
  （ラベルの文字が欠けた図は、見た目の問題ではなく間違い）。
- 字形を持たない制御的な文字（異体字セレクタ U+FE00–FE0F、ZWJ U+200D、ZWSP U+200B）は、描かずに
  読み飛ばす。これを「無い文字」と判定すると、`⚠️` のような文字列が不当にエラーになる。
- 書体を混ぜた行の高さは、使った書体の最大 ascent ＋ 最大 descent で決める。書体ごとに ascent/descent は
  大きく違う（28px で、ヒラギノ角ゴ 24.6/3.4、Helvetica 21.6/6.4、Avenir Next 28/10.25。ヒラギノの
  行送りは 1.5em）。
- 検査は読み込みの時点だけでは足りない。描く時点の失敗も同じ「無い文字」の経路に乗せる。

## `.ttc` は書体ごとに読めたり読めなかったりする — 読めるかはファイルではなく書体の単位で判定する

**事象:** 同じ設計で、手元の macOS のフォントファイル 535 個を `x/image` v0.46.0 で読んだ。
フォントの拡張子を持つファイルは `ParseCollection` が**すべて成功**した（中身は遅延評価される）。失敗は
`Collection.Font(i)` で初めて出て、12 ファイル・32 書体が読めなかった。HelveticaNeue は 14 書体中 5 書体、
Songti は 8 書体中 5 書体しか読めない。原因は cmap の形式が未対応、kern・CFF・head テーブルの不正。

**なぜ:** コレクションの解析はヘッダを読むだけで、各書体のテーブルは取り出すときに検査される。
同じファイルの中でも書体ごとに作りが違う。

**適用方法:**
- 読めるかどうかの判定とエラーは書体の単位で行う。「このファイルは使える」とは言わない。
- 利用者にフォントを選ばせるなら、選ばれた書体を起動時に取り出して検査し、読めない理由（どのテーブルか）を
  付けて返す。描く時点の失敗は、上の項目の経路で扱う。

## `sfnt.Name` は言語を選べない — 書体名で選ぶなら name テーブルを自前で走査する

**事象:** 同じ設計で、`.ttc` の中の書体を名前で選ばせる仕様を「Font Book に出る名前と同じ」と書いた。
検証パスの実測では、`x/image` v0.46.0 の `sfnt.Name` は Mac Roman か Windows UCS-2 の**最初の**レコードを
言語に関係なく返し、ヒラギノ角ゴ W6 では `Hiragino Sans W6` になる。日本語環境の Font Book
（`NSFont.displayName`）は「ヒラギノ角ゴシック W6」を出す。name テーブルには日本語の名前もあるが、この API
では取れない。さらに、ファミリ名（ID 1）が Mac 側では `Hiragino Sans`、Windows 側では `Hiragino Sans W6` と
食い違う。

**なぜ:** name テーブルは同じ ID を言語・プラットフォームごとに複数持つ。`sfnt.Name` はそのうち 1 つを
返す便利関数で、利用者が画面で見ている名前と一致する保証は無い。

**適用方法:**
- 名前で選ぶなら、フル名（ID 4）と PostScript 名（ID 6）の**全言語の値**と、大文字小文字を区別せずに照合する。
- 推奨する指定値は PostScript 名（例: `HiraginoSans-W6`）。言語に依存しない。
- 見つからないときは、そのファイルにある書体名の一覧をエラーに付ける。利用者は一覧から選び直せる。
- 「画面に出ている名前と同じ」と書く前に、利用者の言語環境の画面で確かめる。

## Core Text の行分割は、渡した文字列が長いほど遅くなる — 長い段落は窓に分けて組む

**事象:** report-studio-mcp で、`CTTypesetterCreateWithAttributedString` → `CTTypesetterSuggestLineBreak`
の繰り返しで段落を行に分けていた。独立レビューが、2 MiB の 1 段落の原稿で 487 秒かかると実測した。
自分の側の行ごとの位置計算（UTF-16 の位置から文字の番号への変換を毎回先頭から数えていた）も 2 乗だった。
それを定数時間にしても、Core Text 自身の行分割が遅かった（実測、2026-11-04）。

**なぜ:** 1 回の `SuggestLineBreak` の費用が、渡した文字列全体の長さとともに増える
（測った振る舞い。Core Text の内部は文書に書かれていない）。1 行ずつ全体を渡すので、全体として 2 乗になる。

**適用方法:**
- 段落を UTF-16 で数千単位（ここでは 4096）の窓に分けて、窓ごとに組む。窓の最後の行は窓の端で切られて
  いる可能性があるので捨て、次の窓をその行の頭から始める。サロゲートペアの途中では切らない。
  上の原稿は 0.9 秒になった。
- 行の切れ目はその行の中身だけで決まる、という前提に立っている。窓を分けずに組んだ結果と行の切れ目が
  同じになることを、テストで比べる（窓の大きさを変数にして小さくする）。行の幅も、実際に描く線の幅と
  一致することを確かめた。
- 自分の側の位置の変換や装飾の計算も、行ごとに先頭から数えない。1 行につき 1 回だけ問い合わせる形にする。

## Core Text は表のセルの数値を、離せない単位が列より広いと文字の途中で折る — 全角の数字は幅に関係なく折れる

**事象:** 組版 MCP サーバ（2026-11）で、幅の広い表の数値が `1,234,5`／`67`、`12.34`／`%` のように割れた。
数値 10 種を文脈 13 種・行の位置 14 通り・列の幅 3 段階で組んで測った（macOS 27.2）。

- 半角の数値（`1,234,567`、`12.34%`）には中に折れ目が無い。それでも、Core Text が数値から離せない
  まとまり — 前の開き括弧、後ろの閉じ括弧と句点、前に続く英字、`-` で始まるときは直前の 1 文字 — が
  列より広いと、折れ目が見つからず文字の途中で折る。
- 全角の数字（`１，２３４`）は、文字の間で改行できる。列の幅を数値の 1.3 倍にしても割れた。

**なぜ:** 行分割の規則（UAX #14 に相当）では、半角の数字・区切り・`%` の間は分割禁止で、括弧類は数値に
付く。全角の数字は和字と同じ扱いで、どこでも改行できる（測った振る舞い。Core Text の内部は文書に無い）。

**適用方法:**
- 列の最小の幅を、その列で最も広い「数値と、数値から離せないもの」の幅以上にする。
- 数値の文字の間に WORD JOINER（U+2060）を入れる。全角でも割れなくなり（0/42）、幅は変わらず、
  PDFKit で取り出した文字にも残らない（実測）。
- .docx には入れない。Word の中では本物の文字として残り、数値をコピーすると混ざる。
- 英字が数字より前にある語（ハッシュ値・UUID・CVE 番号）は数値として扱わない。最小の幅に数えると、
  ハッシュの列が広がって本物の数値が割れる。ただし、数字の後ろの英字（`100mg`）は単位として数値に含める。
- 収まらないときは警告して、どの列かを示す（割れたまま黙って出さない）。

## 「次と一緒に置く」は、測る処理と置く処理で同じ計算を使う — 使い回しの鍵には書式も含める

**事象:** 同じサーバで、見出しを次のブロックの冒頭と同じページに置く規則を作った。冒頭の高さを別に
数えると、置いたときの高さと食い違った（段落の孤立行の規則で、3 行の段落は割れないのに「2 行」と
数えていた）。計算を共有するために段落の行を鍵（ブロックと幅）で使い回したら、見出しの直後の引用の
1 段落目が本文の色で描かれた。測るときは本文の書式、置くときは引用の書式だったのに、鍵に書式が
無かった（独立レビューで発見）。

**なぜ:** 「冒頭」は置く処理の規則（孤立行、表の見出し行と最初の行、図の縮小）で決まる。別に数えると
規則が 2 か所に分かれ、片方だけが変わる。使い回しは、計算の入力（幅・書式）をすべて鍵に含めて初めて
正しい。

**適用方法:**
- 冒頭の高さは、置く処理と同じ関数から得る。測るためだけに別の組み方をしない。
- 使い回しの鍵には、結果を変える入力をすべて入れる（ブロック・幅・書式）。置くときに取り出して消す。
- 入れ物（引用・リスト）の中の冒頭は、入れ物が子に渡す書式と幅で測る。
- 同じ結果を守る仕組みが 2 つある（鍵と、測るときの書式）なら、試験はそれぞれ単独で壊して確かめる。

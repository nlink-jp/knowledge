# 組み込み（M5Stack / ESP32）

M5Stack デバイス開発の知見。各項目は「事象 → なぜ → 適用方法」。

---

## 旧 M5Stack ライブラリから M5Unified への移行

**事象:** 旧ライブラリ（M5Stack.h / M5Core2.h）は ESP32 ボードパッケージ v3.x と非互換
（`rom/miniz.h` 欠落）。M5Unified が後継。

**API 対応表:**
- `M5.Lcd` → `M5.Display`
- `M5.begin(lcd,sd,serial,i2c)` → `auto cfg = M5.config(); M5.begin(cfg);`
- `TFT_eSprite(&M5.Lcd)` → `M5Canvas(&M5.Display)`
- `M5.Axp.GetBatVoltage()` → `M5.Power.getBatteryLevel()`（0–100 を直接返す）
- `M5.Rtc.SetTime/SetDate` → `M5.Rtc.setDateTime(m5::rtc_datetime_t)`
- `M5.IMU.Init()` → `M5.Imu`（自動検出）

**注意点:**
- ESP32 v3.x に `NetworkManager` クラスがある — 同名クラスを定義すると再定義エラー。
- M5Stack Basic v2.7 は **PSRAM なし** — フルスクリーン `createSprite(320,240)`（150KB）は
  確保失敗して画面が真っ暗になる。直接描画 + 背景色上書きで対応。Core2 は PSRAM ありで
  Sprite ダブルバッファ可。Wi-Fi・mDNS・TCP の待ち受けを動かした後の実測（arduino-esp32 3.3.8、
  M5Unified 0.2.14、2026-09-26、1 台）: 空き約 155 KB、連続して確保できる最大は 59,380 B。
  320×80・16 ビット（51,200 B）の帯なら確保できた。
- SD 初期化は自動で行われる場合とそうでない場合がある（Core2 は `SD.begin(4)` が必要）。
- `M5.begin()` が Serial2 を初期化する場合がある — GPS 等で Serial2 を使うなら
  `end()` → 再 `begin()`。
- **RTC の二重 offset 問題**: `configTime(offset,...)` + `getLocalTime()` + RTC 書込は
  offset が二重適用される。NTP は必ず `configTime(0,0,...)` で UTC 取得し、表示時のみ
  offset を適用する。

## M5 GPS Module v2.1（AT6668）はデフォルト 115200 baud

**事象:** ネット上の情報の多くは旧版 AT6558（9600 baud）前提。v2.1 の AT6668 を 9600 で
接続すると、バイナリに見える文字化けデータが流れる（= ボーレート不一致のサイン）。

**適用方法:**
- `Serial2.begin(115200, SERIAL_8N1, 16, 17)`（M5Stack Basic v2.7 で TXD=G17, RXD=G16、
  ディップスイッチでピン選択可）。
- コールドスタートは 5–15 分。fix 前でも GSV の in-view 衛星数は取得できる。
- TinyGPS++ の `satellites.value()` は GGA の fix 衛星数のみ。in-view は `TinyGPSCustom`
  で GSV フィールド 3 を取る。マルチコンステレーションでは GN プレフィックスが使われ、
  GSV は GP/BD/GL 別に流れる。

## M5Module-GNSS ライブラリは M5Unified と共存不可

**事象:** M5Module-GNSS（公式ライブラリ）は Bosch BMI270 API を内蔵しており、M5Unified の
IMU ドライバとシンボル競合して `M5.begin()` がハングする。旧 ESP-IDF i2c ドライバを使って
いるため ESP32 Core v3.x の新ドライバとも `abort()` で競合する。

**適用方法:** M5Module-GNSS は使わない。IMU は M5Unified 内蔵の `M5.Imu`（BMI270）を使い、
BMM150 は BMI270 の AUX レジスタパススルーで Wire 直接読み取り、BMP280 は独立ライブラリで
使う。

## ESP32 Arduino コアで `--output-dir` を使うと、スケッチのフォルダに絶対パス入りのビルド生成物が書かれる

**事象:** `arduino-cli compile --output-dir <dir>` で esp32:esp32 コア（3.3.8 で実測）の
スケッチをビルドすると、指定した `<dir>` とは別に `<スケッチ>/build/<fqbn>/` ができ、
`.bin`・`.elf`・`.map`・`sdkconfig`・`build.options.json` などがコピーされる。`.map` と
`build.options.json` にはビルド機の絶対パス（ホームディレクトリ）が入っている。
スケッチのフォルダはソースツリーの中なので、`git add` でそのままコミットに入った
（push 前にホームディレクトリ検査で発覚）。

**なぜ:** コアの `platform.txt` にある `recipe.hooks.savehex.postsavehex.*` が、バイナリを
書き出す（エクスポートする）たびに `{sketch_path}/build/` へコピーする。arduino-cli の
`sketch.always_export_binaries` が `false` でも止まらない — コピーしているのは
arduino-cli ではなくコア側のフックだから。

**適用方法:**
- `--output-dir` や `-e` を使わず、`--build-path <dist 配下の絶対パス>` でビルド
  ディレクトリそのものを成果物置き場にする。書き出しをしないのでフックは走らない。
  書き込みは `arduino-cli upload --input-dir <同じパス>`。
- ビルド後に `<スケッチ>/build` が存在したら失敗させる検査を Makefile に置く。
  `.gitignore` に足して隠すのではなく、作らない側で止める（成果物の置き場は `dist/` だけ、
  という規約とも合う）。

## arduino-cli の `--build-property` で文字列マクロを渡すときは、フラグ全体を単引用符で囲む

**事象:** 版数をファームウェアに埋め込もうとして、
- `compiler.cpp.extra_flags=-DFW_VERSION=\"v1\"` はバックスラッシュごと gcc に届き
  `stray '\' in program` になる。
- `compiler.cpp.extra_flags=-DFW_VERSION='"v1"'` は単引用符ごと届き、`'"v1"'` が
  複数文字の文字定数（`int`）になって `invalid conversion from 'int' to 'const char*'`
  になる。

**なぜ:** arduino-cli はレシピの文字列を自前で引数に分割する。引用符が特別なのは
**引数の先頭にあるときだけ**で、対応する引用符までを 1 つの引数にまとめる。引数の途中の
引用符とバックスラッシュは、そのまま渡される（arduino-cli 1.5.1 で実測）。

**適用方法:**
- フラグ全体を単引用符で囲む。Makefile なら
  `--build-property "compiler.cpp.extra_flags='-DFW_VERSION=\"$(VERSION)\"'"`
  （シェルの二重引用符の中で `\"` が `"` になり、arduino-cli には
  `'-DFW_VERSION="v1"'` が届く）。
- **フラグが複数あるときは 1 つずつ囲む。** `'-DA=0 -DB=0'` は 1 つの引数として届き、
  `A` が `0 -DB=0` と定義された（実測）。`'-DA=0' '-DB=0'` と書く。Makefile では
  `$(foreach d,$(DEFINES),'$(d)')` で並べる。
- `build.extra_flags` はボード定義が使っているので上書きしない。`platform.txt` が
  利用者向けに空で用意している `compiler.cpp.extra_flags` を使う。
- 効いたかは推測せず、`strings <.bin> | grep -F <版数>` で埋め込まれたことを確かめる。**行全体の一致（`grep -x`）は
  使わない**: 版数だけの文字列リテラルが、それで終わる長い文字列（例 `"<名前> <版数>"`）の末尾にリンカがまとめる
  ことがあり、そのとき版数だけの行は `strings` の出力に現れない（2026-09-26、esp32 コア 3.3.8、実測）。

## M5Stack BASIC v2.7 への書き込み・読み出しは、macOS では 230400 baud に落とす

**事象:** Arduino の `m5stack_core` ボード定義は、書き込み速度の既定値がメニュー先頭の
1500000 baud になっている。BASIC v2.7 の USB シリアル（WCH CH9102F、`1a86:55d4`、
macOS 標準ドライバ、Thunderbolt ハブ経由）で esptool を使うと、921600 baud では
`The chip stopped responding`、460800 baud では `Invalid head of packet` で途中停止した。
230400 baud では 4MB の読み出しも書き込みも通り、ハッシュ照合も一致した
（2026-09-24、esptool 5.2.0 で実測。この 1 構成での結果）。

**適用方法:**
- Makefile で `arduino-cli upload --board-options UploadSpeed=230400` のように速度を
  明示し、既定値に任せない。上げるのは実測してから。
- 書き込みでファームウェアを上書きする前に、`esptool read-flash` で控えを取る。
  まず `read-flash 0x8000 0xC00` でパーティション表を読み（`gen_esp32part.py` で
  読める）、使われている範囲だけを控えると速い（標準の 4MB 構成なら先頭 4MB）。
  控えには NVS（Wi-Fi 設定などが入り得る）も含まれるので、扱いに注意する。

## macOS に BLE キーボード（HID over GATT）として接続させるなら、HID の読み取りを暗号化必須にする

**事象:** ESP32（Arduino-ESP32 3.3.8 同梱の BLE ライブラリ）で HID キーボードを作り、ペアリングに
番号入力（Passkey Entry）を使った。macOS 27.0 では、ペアリングは成功して「キーボード」として接続
済みになるのに、キーがまったく効かなかった。macOS の入力デバイスの一覧（`hidutil list`）にも出ず、
機器を再起動しても自動では再接続されなかった。

**なぜ:** macOS で BLE の HID を受け持つ `BTLEServer` は、接続するとすぐにレポートマップなどを読む。
それらが暗号化なしで読めると、利用者が番号を入力している間に読み終え、
「Not creating HID device as the link is not encrypted」と記録して HID 機器を作らない。30 秒後に
サービスの初期化が時間切れになり、再試行しない。そのうえ、この機器を自動接続の一覧から外す。
`/usr/bin/log show --predicate 'process == "BTLEServer"'` で読める。

**適用方法:**
- HID サービスのレポートマップ（0x2A4B）、HID 情報（0x2A4A）、プロトコルモード（0x2A4E）の権限を
  `ESP_GATT_PERM_READ_ENC_MITM` にする。最初の読み取りが「認証が足りない」で失敗するので、macOS は
  ペアリングを先に済ませ、その 1 秒後に HID 機器を作った（2 回中 2 回）。
- 一度失敗した機器は、Mac の Bluetooth 設定から削除し、機器側のペアリング情報も消してから、
  ペアリングし直す。
- 一度 HID 機器ができた後は、機器を再起動すると 1〜2 秒で自動的に再接続・再暗号化された。

## macOS は BLE の HID 機器の接続条件を自分で決める — 周辺機器への書き込みは、受信中に通知を出し続けると速くなる

**事象:** macOS 27.0 が BLE キーボードとして接続した ESP32 に、アプリから応答なし書き込みで
データを送ると、毎秒約 0.28 KB しか出なかった。

**なぜ:** macOS は HID 機器の接続を、間隔 15 ms・スレーブレイテンシ 22・データ長 90 に設定する。
機器から別の値を求めても、1 秒以内に元へ戻した（5 回。初回ペアリング直後に 1 度だけ、
レイテンシ 0 のままにしたことがある）。レイテンシ 22 では機器は約 345 ms ごとにしか受信しない。
受信中の機器が接続間隔ごと（15 ms）に通知を出すと、毎秒 4.1〜4.2 KB になった（30 ms ごとなら 2.5、
60 ms ごとなら 1.6）。周辺機器は、送るものがない間だけ接続の機会を飛ばせる、というのがこちらの読み
（規格の条文は確認していない）。

**適用方法:**
- 接続条件の変更要求は、当てにしない。見積もりはレイテンシ 22 で立てる。
- 大量に受け取る間は、機器が 15 ms ごとに状態の特性を通知し、ホストはそれを購読する。
- 完了は通知と読み取りの両方で確かめる。最後の通知を取りこぼしたことがある（10 回中 3 回）。
- ホスト側に書き込みを大量にためない。約 30 秒分の書き込みがたまった状態で読み取りを出すと、
  応答がないまま約 30.5 秒後に接続ごと切れた。ATT 要求の 30 秒の時間切れという仮説。
  機器の通知に合わせて、少しずつ送る。
- 計測では、接続条件を接続の時点から記録し、機器からは何も求めない版で測る。途中で条件が
  変わったことに気づかないと、結果の説明がつかなくなる（最初の計測でこれが起きた）。

## CoreBluetooth のアプリは、システムがキーボードとして接続中の BLE 機器の独自サービスを使える

**事象:** 機器の BLE 接続は、macOS 自身が HID キーボードとして持っている。その同じ機器にある
独自の GATT サービスを、アプリから読み書きしたかった。

**なぜ:** `retrieveConnectedPeripherals(withServices: [独自サービスの UUID])` が、システムが接続中の
その機器を返した。そこに `connect` すると、システムの接続を共有したまま、MITM 付きで暗号化された
独自の特性を読み書きできた（42 回中 42 回、macOS 27.0）。HID サービス（0x1812）はアプリからは
見えず、`withServices: [0x1812]` では何も返らない。

**適用方法:**
- 独自サービスの UUID で探す。0x1812 では見つからない。
- ペアリングは HID の時点で済んでいるので、アプリ側で 2 度目のペアリングは起きない。
  アプリに要るのは Bluetooth の利用許可だけ。許可はアプリ単位なので、CLI のような裸の
  バイナリではなく .app として動かす。

## ペアリング済みの Mac は GATT の構成を覚えている — Bluedroid は Service Changed を送れなかった

**事象:** ファームウェアを書き換えて、独自の特性に「通知」を足した。ペアリング済みの Mac からは、
古い構成のまま（読み取りのみ）に見えた。

**なぜ:** 接続のたびに構成を調べ直すのではなく、覚えた構成を使っている。構成の変更を知らせる
Service Changed を機器から送ろうとしたが、Arduino-ESP32 3.3.8 の Bluedroid は状態 0x82 で
送信そのものを拒んだ（8 回中 8 回）。Bluedroid の AUTO モードが送るのは、接続中にサービスを
足し引きしたときだけ、と読んでいる。機器側のスタックが送らないので、macOS がそれを受けて
どうするかは確かめられていない。

**適用方法:**
- 独自サービスの構成は、HID の定義と同じく、リリースごとに固定する。変えたら互換性を壊す変更として扱い、
  再ペアリング（Mac から削除し、機器のペアリング情報も消す）を求める。
- 固定するのは UUID だけでなく、ハンドルを含む属性表全体。同梱ライブラリは購読の設定（CCCD）を相手と
  ハンドルごとに NVS に保存するので、コアの更新やコードの整理でハンドルがずれるだけで食い違いうる。
  サービスを決まった順に、決まったハンドル数を確保して作り、起動時に表を出力して、固定した表と実機で比べる。
- 「構成の版」を形式（プロトコル）の版とは別に持たせる。壊れ方が違うため。アプリは Info の版に加えて、
  見えている特性の UUID とプロパティも照合する（古い記憶のまま読むと、別の属性を読むことがある）。
- 機器側では、構成の版をペアリング情報の横に保存し、起動時に違っていれば（**保存されていない場合も**）
  ペアリング情報をすべて消してから版を保存する。ペアリング情報がなかったときも版は書く。書かないと、新品が
  最初のペアリングの後、2 回目の起動でそのペアリングを消してしまう。削除は非同期に完了するので、一覧が空に
  なるのを待つ。

## Arduino-ESP32 で BLE だけを使うなら、先に Classic 用のメモリを解放する

**事象:** PSRAM のない ESP32（M5Stack BASIC v2.7）で、BLE の HID と独自サービスと画面描画を
同時に載せると、空きヒープが心配になる。

**なぜ:** Arduino-ESP32 3.3.8 の ESP32 向けビルド済み設定では Classic Bluetooth が有効で、
`BLEDevice::init()` はコントローラを BTDM（Classic と BLE の両方）で起動する。

**適用方法:**
- `BLEDevice::init()` の前に、`esp_bt_controller_mem_release(ESP_BT_MODE_CLASSIC_BT)` と
  `btStartMode(BT_MODE_BLE)` を呼ぶ。`BLEDevice::init()` は、すでに起動しているコントローラを
  そのまま使う。空きヒープは 21,036 B 増えた（広告開始後 92,084 → 113,120 B）。
- それでも、画面全体の圧縮画像（67 KB）を丸ごとメモリに溜めると、空きは 22,748 B まで下がった。
  大きなデータは届いたそばから展開する。

## Arduino-ESP32 の BLE ライブラリの `notify()` は、暗号化を確かめずに接続中の相手全員に送る

**事象:** BLE キーボード（HID over GATT）の入力レポートを `notify()` で送る作りだと、ペアリングしていない
相手がつながっている間にボタンを押すと、その相手にもキー入力が送られうる。

**なぜ:** Arduino-ESP32 3.3.8 の `BLECharacteristic::notify()` は、`getPeerDevices()` の全員に
`esp_ble_gatts_send_indicate` を呼ぶ。相手ごとの暗号化も購読も確かめない（ソースで確認）。特性の読み取りに
暗号化を求めても、通知には効かない。スタック自身が暗号化されていない接続への送信を止めるかどうかは
確かめていない。

**適用方法:**
- 秘密にすべき通知（キー入力など）は `notify()` を使わず、ペアリング済みの鍵で暗号化された接続を
  接続番号で指定して `esp_ble_gatts_send_indicate` で送る。
- 「暗号化済み」は、ペアリング済みのアドレスについて認証完了のイベントが成功で届いた時点から、切断までと
  みなす。ライブラリは切断の後にだけ広告を再開するので、接続は同時に 1 つ。

## Arduino-ESP32 の BLE ライブラリは、CCCD への書き込みを相手を問わず NVS に保存する

**事象:** ペアリングしていない相手でも、購読の設定（CCCD）を書き込めば、機器の NVS に項目が増える。

**なぜ:** 3.3.8 の `BLEDescriptor` は、UUID が 0x2902 の書き込みを受けるたびに `BLE2902::persistValue()` を
呼ぶ。コメントは「ペアリング済みの機器のため」だが、ペアリングも暗号化も確かめない。キーは相手のアドレスの
末尾 2 バイトとハンドル（ソースで確認）。`BLEHIDDevice` は入力レポートと電池残量の CCCD を暗号化なしで
書けるように作る。アドレスを変えて接続し直す相手は、ペアリング情報やアプリの設定が入る NVS を
埋められる（推測。実機では試していない）。また、保存した購読の設定は、ペアリング情報を消しても残る。
`BLE2902::deleteAllPersistedValues()` があるが、ライブラリは自分では呼ばない。

**適用方法:**
- CCCD はすべて、書き込みに暗号化を求める（`ESP_GATT_PERM_READ | ESP_GATT_PERM_WRITE_ENC_MITM`）。
  HID の CCCD まで閉じても、macOS 27.0 はペアリングしてキーボードを登録し、キーボードとメディアキーの
  レポートも届いた（2026-09-24 に実測。ライブラリのコメントは「HID の登録に開いている必要がある」と言うが、
  macOS では当たらなかった）。
- ペアリング情報を消すときは、必ず `deleteAllPersistedValues()` も呼ぶ。

## Bluedroid は、ペアリングや暗号化に失敗した相手のペアリング情報を消す

**事象:** ペアリング済みの機器でも、ある相手とのペアリングや暗号化が失敗すると、その相手のペアリング
情報が消えることがある。

**なぜ:** Arduino-ESP32 3.3.8 に同梱の `libbt.a` の認証完了の処理は、失敗の理由が「pairing not supported」
以外なら、その相手のペアリング情報を消す（逆アセンブルして読んだ。ソースでの確認ではない）。近くの機器が、
ペアリング済みの Mac のアドレスを使って失敗するペアリングを仕掛ければ、ペアリング情報を消させられる
（推測）。

**適用方法:**
- 「ペアリング情報がない」ことを、ペアリングを受け付ける理由にしない。受け付けるのは、利用者の操作
  （起動時にボタンを押し続けるなど、普通のキーボードのペアリングモード）で入った間だけにする
  （security の「信頼の窓は状態の不在ではなく、記録した操作で開く」）。
- **（2026-09-25 訂正）** 以前ここに「セキュリティのコールバック（`onSecurityRequest()` が false）で拒めば
  pairing not supported になり、ペアリング情報も消えない」と書いていたが、ライブラリの既定のままでは
  このコールバックは一度も呼ばれない（次の項目。実機で確認）。断り方は次の項目に従う。

## Arduino-ESP32 の BLE ライブラリは、書き込まれた値を `onWrite` の前に特性へ入れ、書き込みを必ず受理する

**事象:** 読み書きできる特性に不正な値を書くと、機器がそれを拒んで保存しなくても、直後の読み取りは
書かれた値を返す。

**なぜ:** 3.3.8 の `BLECharacteristic` は、Bluetooth のタスクの中で `setValue()` を呼んでから `onWrite` を呼び、
その後、必ず成功で応答する（ソースで確認）。`onWrite` から ATT のエラーを返す手段はない。

**適用方法:**
- 書き込みの結果（受理・拒否）は、ATT の応答ではなく、別の特性（状態の通知など）で知らせる。
- 読み書きできる特性は、書き込みを処理するたびに、メインループが値を保存済みの内容に戻してから結果を
  知らせる。

## macOS から ESP32（Bluedroid）への応答なし書き込みは、最後の断片が 1 バイトになる長さだと届かない

**事象:** macOS 27 の CoreBluetooth から、BLE キーボードとして接続中の ESP32（Arduino-ESP32 3.3.8 の
Bluedroid）へ応答なし書き込みでデータを送ると、特定の長さの書き込みだけが、毎回、機器の `onWrite` に
届かなかった。Mac の bluetoothd は送り出したと記録している。エラーはどこにも出ない。

**なぜ:** 14〜252 バイトと 488〜500 バイトの長さを 1 回ずつ送ると、届かなかったのは 84・174・245・
496 バイトだけだった。中身は関係なかった（詰め物で試した）。どれも、L2CAP のパケット（長さ + 7）を
90 バイトまたは 251 バイトの断片に分けたとき、最後の断片が 1 バイトになる長さである
（91 = 90 + 1、181 = 180 + 1、252 = 251 + 1、503 = 502 + 1）。経路のどこかに 90 と 251 の 2 種類の
区切りがあり、1 バイトだけの最後の断片が失われる、というのがこちらの読み。Mac と ESP32 のどちらが
落とすのかは確かめていない。

**適用方法:**
- 書き込みを 244 バイトまでにする（ATT と L2CAP の見出しを足して 251 バイトの 1 パケットに収まる）。
- それでも区切り 90 には当たるので、(長さ + 7) を 90 または 251 で割った余りが 1 になる長さは使わず、
  1 バイト短くして残りを次に回す。
- 区切り方は Mac や接続で違いうる。書き込みが止まったら、機器が消化しなかった最初の書き込みの長さを
  覚えて、以後は避ける（機器に消化量を報告させておけば分かる）。
- 見た目は「ときどき止まる」なので、長さの規則だと気づくまで時間がかかる。止まった書き込みの長さを
  記録し、長さを 1 つずつ送る計測で確かめる。

## BLE 機器が状態を通知するときは、送信の余裕を見て控え、受信の後もしばらく続ける

**事象:** ESP32 が、受信中は 15 ms ごとに状態を通知する作りで、macOS の接続が 1.5〜2.5 分ごとに切れた
（機器側の理由 0x13）。直したら今度は転送が約 0.2 KB/s まで落ちた。

**なぜ:**
- 機器は「指示を途中まで受け取って待っている間」も通知を出し続けていた。送信の列が埋まり
  （`esp_ble_get_cur_sendable_packets_num()` が 0、`ESP_GATTS_CONGEST_EVT`、送信失敗）、Mac の読み取りへの
  応答が送れなくなった。応答のない読み取りのちょうど 30 秒後に、macOS が接続を切った（ATT の時間切れ）。
  応答を待つ要求があると、Mac はその後の書き込みも先へ進めなかった。
- 「値が変わったときだけ」通知すると、書き込みと書き込みの間に機器が眠る（macOS はスレーブレイテンシ 22
  を設定する）。512 バイトの書き込みは何パケットにも分かれるので、眠った機器に最初の書き込みが届くまで
  約 1.1 秒かかった。

**適用方法:**
- 空き送信バッファが少ない（3 未満）間は、通知を出さない。応答のための余地を必ず残す。
- 受信中と、最後に受け取ってから 2 秒間は、15 ms ごとに通知して機器を起こしておく。それを過ぎたら、値が
  変わったときだけ通知する。毎秒更新する画面なら、これで起きたままになる。
- ホストは、前の更新を機器が消化してから次の更新を作る（送り残しが 0 になるまで待ち、その時点の最新の
  状態を送る）。通信が更新より遅いと、積み上がった更新で画面が何分も遅れる（実際に 8 分遅れた）。
- 通知を控えても、ホストは 1.5 秒通知が来なければ状態を読みに行く作りにしておく。

## BLE キーボードの PnP ID：macOS は再接続で新しい値を使い、キーボードの種類をこの組で覚える

**事象:** ESP32（Arduino-ESP32 3.3.8 の同梱 BLE ライブラリ）の BLE キーボードで、PnP ID を仮の値から正式な値へ
変えた。ペアリングを残したまま書き込んで再接続させると、macOS 27.0 はペアリングし直していないのに新しい
ベンダー ID・製品 ID を使い、新しいキーボードとみなしてキーボード設定アシスタントを開いた。

**なぜ:**
- macOS は PnP ID（Device Information の 0x2A50）を、ペアリングのときだけでなく再接続でも読んだ。システム情報
  と IORegistry の HID 機器は、再接続の直後から新しい値を示した（書き込み後の 1 回の観察）。
- キーボードの種類（ANSI・ISO・JIS）は、製品 ID・ベンダー ID・HID の国コードの組ごとに
  `/Library/Preferences/com.apple.keyboardtype.plist` に記録される（キーは `製品-ベンダー-国コード` を 10 進で）。
  組が変わると、種類をもう一度尋ねる。
- 同梱の `BLEHIDDevice::pnp()` は ID を上位バイトから詰める。macOS はリトルエンディアンで読むので、そのまま
  渡すと上下の入れ替わった ID になる。多くの ESP32 キーボードが使っている `pnp(0x02, 0xe502, 0xa111, 0x0210)`
  は、入れ替えを見込んだ値で、読むと USB-IF の出所に Espressif の Bluetooth 企業識別子 0x02E5 が入っている。
  同じ値の機器どうしは、キーボードの種類の設定を共有する。

**適用方法:**
- PnP ID は 7 バイトを Mac が読む並び（リトルエンディアン）で特性に直接書き、`pnp()` は使わない。バイト列を
  テストで固定し、上下を入れ替えると落ちることを確かめる。
- 自前の企業識別子が無いなら、出所 0x01（Bluetooth SIG）と、チップのメーカーの識別子（Espressif は 0x02E5。
  SIG の一覧で確かめる）に、独自の製品 ID を組み合わせる。pid.codes は USB の口を持つ機器が条件で、
  Bluetooth だけの機器には合わない。試験用の ID（pid.codes の 1209/0001 など）は配る機器に使えない。
- PnP ID を変えると、利用者は種類をもう一度尋ねられる。キーが 3 つしかない機器ではアシスタントの求める
  キーを押せないので、「手順を飛ばして種類を選ぶ」と案内する。
- 新しい値が使われたのを見たのは 1 回、macOS 27.0 の PnP ID だけ。レポートマップや GATT の構成はペアリング時の値を
  使い続けうるので、それらの変更は引き続き再ペアリングが要るものとして扱う。

## M5Stack BASIC のバックライトは 44.1 kHz の PWM では暗くならない — 1 kHz・14 ビットと 2.2 乗の曲線で使える

**事象:** M5Unified/M5GFX の `M5.Display.setBrightness()` で明るさを下げても、BASIC v2.7 では 1%（255 段の 2）
でもまだ十分に読める明るさで、50% でもかなり明るかった。暗い側が無かった。

**なぜ:** M5GFX はこの機種で、バックライトの端子（GPIO32）を 44.1 kHz・9 ビット・オフセットなしで動かす
（`_set_pwm_backlight(GPIO_NUM_32, 7, 44100)`）。同じチャネルを 1 kHz・14 ビットに移すと、暗い側まで
効いた。点灯の短さでは説明できない（1% の点灯は 44.1 kHz で 0.18 マイクロ秒、1 kHz の 1 カウントは 0.06
マイクロ秒で、後者は暗く見えた）。測っていないが、点灯のたびに幅より少し長く光り、点灯の回数が 44 倍だと
その分が積み重なる、というのがありそうな原因。

**適用方法:**
- `M5.begin()` の直後に `ledcChangeFrequency(32, 1000, 14)` で、M5GFX が割り当てたチャネルをそのまま移す
  （Arduino-ESP32 3.x の公開 API。チャネルを増やさず、M5GFX も変えない）。以後は `ledcWrite(32, duty)` で書き、
  `M5.Display.setBrightness()` は呼ばない（9 ビットの値を書いてしまう）。
- 明るさの割合は `(percent/100)^2.2` を全点灯（16383）に掛けて丸める（1% は 1 カウント）。実機
  （2026-09-25、1 台・1 人の判断）で、1% はぎりぎり見える程度、段の変わり方はおおむね均等、ちらつきも音も
  無かった。
- 44.1 kHz のまま補正の曲線だけ入れても、1% より下は 1 段しか無いので、暗い側は増えない。まず周波数を疑う。
- 機種の判定（`M5.getBoard()`）と `ledcChangeFrequency` の戻り値を見て、だめなら M5GFX の比例の対応に戻す。

## Arduino-ESP32 の BLE ライブラリは、既定で、つないできたすべての相手にペアリングを要求する

**事象:** Arduino-ESP32 3.3.8 の BLE で作った周辺機器（パスキー表示・MITM・Secure Connections）に、Mac が
つないだだけで（アプリが特性を読もうとした、一覧で「接続」を押した）、その Mac に番号入力のポップアップが
出た。機器がペアリングを受け付けない状態でも、機器は番号を作ってペアリングを進めており（画面には出さない
ので誰も入力できない）、機器が接続を切るまで宙に浮いた。拒否のために用意した `onSecurityRequest()` は
一度も呼ばれなかった。

**なぜ:** `BLESecurity::m_forceSecurity` の既定が true（ソースのコメント：「互換のため。v4.0.0 で false に
変える予定」）で、`setAuthenticationMode()` でセキュリティを有効にすると、ライブラリは
`ESP_GATTS_CONNECT_EVT` のたびに `esp_ble_set_encryption()` を呼ぶ。機器（ペリフェラル）が相手に Security
Request を送り、相手がペアリングを始める。Bluedroid はその Pairing Request を
`ESP_GAP_BLE_SEC_REQ_EVT` を出さずに受け入れ、拒否のコールバックは呼ばれない（2026-09-25、
`setCustomGapHandler` で全セキュリティ事象を記録して確認：security request の事象は無く、ペアリング待ちの
外で passkey notify が出た）。

**適用方法:**
- ペリフェラルでは `BLESecurity::setForceAuthentication(false)` にする。Apple の指針も「ATT の要求を
  Insufficient Authentication で断るまで、アクセサリはペアリングを要求しない」（Accessory Design Guidelines
  R31 §58.10）。暗号化とペアリングは相手（セントラル）が始める。
- ペアリングを受け付けない状態での規格どおりの断り方は Pairing Failed「Pairing Not Supported（0x05）」
  （Core 6.3 Vol 3 Part H §2.3）。`setForceAuthentication(false)` の後に `onSecurityRequest()` の false が
  実際にこの理由コードで断るかは**測っていない**（プロジェクトを中止した）。測ったのは一時しのぎで、
  受け付けない間だけ IO 能力を NoInputNoOutput にする方法（MITM と SC を必須、
  `ESP_BLE_SM_ONLY_ACCEPT_SPECIFIED_SEC_AUTH` 有効）：ペアリングは即座に失敗し（ESP の理由 0x50）、
  番号は作られない。ただし規格の断り方（0x05）ではない。
- コールバックで振る舞いを決める設計は、先に `setCustomGapHandler` で GAP のセキュリティ事象をすべて
  記録し、そのコールバックが本当に呼ばれることを確かめてから信じる。

## BLE の HID 周辺機器を作る前に：状態ごとに規格が求める振る舞い

**事象:** ペアリング待ち・拒否・再接続・切断後の振る舞いを現物合わせで積み上げた結果、機器が一般的な
Bluetooth 機器と違う振る舞いになり（受け付けないのに Mac の一覧に出る、番号を求められるのに機器に出ない、
切断してもすぐ戻る）、プロジェクトが収束しなかった（m5-notify-deck、2026-09-25 中止）。

**なぜ:** 状態（未ペア・ペアリングモード・ペアリング済みで未接続・切断後）ごとの振る舞いは、Bluetooth の
規格と Apple の指針がかなり具体的に決めている。それを先に表にせず、ライブラリの既定と独自の仕組みで
組んだ。

**適用方法:** 状態遷移を先に文書にし、各行を次の要求と突き合わせてから作る（原文を読んで確かめた要点）。
- ペアリングモード：LE **Limited** Discoverable の印、最長 180 秒（Core 6.3 Vol 3 Part C §9.2.3.2、HOGP 1.0
  §5.1.1）。見つけられる間は受け入れの制限をかけない（同 §9.2.3.2）。HID サービスの UUID・名前・外観
  （0x03C1）を載せる（HOGP §3.1.3–3.1.5、ADG §58.4・§58.13）。
- それ以外：見つけられる印を立てない（§9.2.2.2）。ペアリング要求は Pairing Not Supported（0x05）で断る
  （SMP §2.3）。「non-bondable」は断ることではない（ペアリングはするが保存しないだけ、§9.4.2.2）。
- 機器からペアリングや暗号化を要求しない（ADG §58.10）。HOGP は Security Request を勧める（1.1 §7.1）が
  Apple の指針と食い違う。Mac が相手なら Apple に従う。
- 片方だけが鍵を失ったとき：鍵の無い周辺機器は暗号化を拒み（LL の 0x06 PIN or Key Missing）、接続は残る
  （Core 6.3 Vol 6 Part B §5.1.3.1）。ペアリングし直すかどうかは、ホストが利用者に確かめて決める
  （Vol 3 Part C §10.3.2）。周辺機器の画面から「Mac 側の登録を消せ」と指示しない（どの登録か機器には
  分からない）。
- HID 情報の NormallyConnectable=1 は「つながっていない間、常に接続可能な電波を出す」約束（HIDS 1.0 §2.10、
  HOGP 1.1 §3.1.7）。0 なら、アイドル中は電波を止め、送るものがあるときだけ出す（HOGP 付録 A）。
- キーボードとして動く機器は Boot Keyboard の入出力レポートが必須（HIDS 1.0 表 2.1）。
- HOGP 1.1 は 1.0 の §5（発見・再接続・受け入れ一覧・切断の手順）を丸ごと削っている。Apple の指針は 1.0 を
  参照している。
- macOS 27.0 の実測：名前を載せた接続可能な電波は、見つけられる印が無くても Bluetooth 設定の一覧に出る。
  ペアリング済みの BLE の HID 機器が電波を出していれば、「接続解除」してもすぐつなぎ直す。

## ESP32 で Wi-Fi・mDNS・TCP を動かすだけで、既定のアプリ領域の 9 割を使う — BASIC v2.7 は 16 MB を積んでいる

**事象:** M5Stack BASIC v2.7 向けに、Wi-Fi への接続・mDNS でのサービスの公開・TCP の待ち受けだけを載せた
試験用のスケッチ（暗号も画面のページも無し）をビルドしたら、既定のアプリ領域 1,310,720 バイトの 88 %
（1,156,815 バイト）を使った（`esp32:esp32` 3.3.8、`esp32:esp32:m5stack_core` の既定の設定、2026-09-26 に実測）。

**なぜ:** ボード定義の既定は「4 MB のフラッシュ・アプリ 1.25 MB（OTA 用に 2 つ）」の配置で、実機のフラッシュ容量に
合わせていない。BASIC v2.7 のフラッシュは 16 MB だった（`esptool flash-id` が `Detected flash size: 16MB` を返した。
同じ個体で実測）。

**適用方法:**
- Wi-Fi を使うスケッチでは、最初からボードの設定でフラッシュ容量と配置を決める。例:
  `--board-options FlashSize=16M,PartitionScheme=huge_app`（アプリ 3 MB・OTA なし）。compile と upload の両方に渡す。
  この設定で同じ足場のスケッチは 3,145,728 バイト中 15 % になった（実測）。
- OTA を使うなら、`default_8MB`（アプリ 3 MB × 2）など OTA の枠がある配置を選ぶ。
- 配置を変えると、以前の書き込みとは領域の位置が変わる。書き込みは消去からやり直す前提にする。
- 容量は機種の表記ではなく、`esptool flash-id` で個体から読む（読み取りだけ。ただしポートを開くので ESP32 は再起動する）。

## ESP32 の乱数が真の乱数になるのは、無線が動いている間だけ — 鍵は Wi-Fi を起動した後に作る

**事象:** 設定のときに鍵と使い捨てのパスワードを M5（ESP32）で作る設計で、`esp_random()` をいつ呼べば
よいかを確かめた。

**なぜ:** ESP-IDF v5.5 の文書（API Reference › System › Random Number Generation）によると、ハードウェアの
乱数生成器が真の乱数を出すのは、Wi-Fi か Bluetooth が有効な間、または `bootloader_random_enable()` で内部の
雑音源を有効にしている間だけ。アプリが動き出してから無線を初期化するまでは、擬似乱数でしかない
（文書で確認。実機で乱数の質は測っていない）。

**適用方法:**
- 鍵・パスワード・ナンスの種は、`WiFi.mode(...)` や周辺の Wi-Fi の探索で無線を起動した**後に**作る。
- 無線を使わない機器で真の乱数が要るなら、文書の手順（`bootloader_random_enable()` と、ADC・I2S・無線を使う前の
  `bootloader_random_disable()`）に従う。

## arduino-esp32 3.3.8 の mbedTLS には ChaCha20-Poly1305 が入っていない — 暗号の部品は sdkconfig と記号で確かめてから選ぶ

**事象:** ESP32（M5Stack BASIC）とコンパニオンの間の暗号を ChaCha20-Poly1305 で設計したが、arduino-esp32 3.3.8 の
ビルド済みライブラリでは使えなかった。`tools/esp32-libs/3.3.8/sdkconfig` は `CONFIG_MBEDTLS_CHACHA20_C` と
`CONFIG_MBEDTLS_POLY1305_C` が無効で、`libmbedcrypto.a` にも `mbedtls_chachapoly_encrypt_and_tag` が無い。
ヘッダ（`chachapoly.h`）はあるので、ヘッダを見ただけでは気づけない（2026-09-26、実測）。

**なぜ:** Arduino 向けの ESP-IDF ライブラリは設定済みの sdkconfig で作られていて、スケッチからは組み込む部品を
選べない。同じ版で `CONFIG_MBEDTLS_GCM_C`・`CONFIG_MBEDTLS_HARDWARE_AES`・`CONFIG_MBEDTLS_HKDF_C` は有効で、
`mbedtls_gcm_*` は `port/include/gcm_alt.h` のマクロでハードウェア AES の `esp_aes_gcm_*` に置き換わる（実測）。

**適用方法:**
- 暗号（や他の mbedTLS の部品）を設計に書く前に、`sdkconfig` の `CONFIG_MBEDTLS_*` と、
  `xtensa-esp32-elf-nm -g --defined-only libmbedcrypto.a` の記号の両方で、実体があることを確かめる。
- 両側を一次提供物で揃えるなら AES-256-GCM（Mac は CryptoKit の `AES.GCM`）が使える。HKDF は
  `mbedtls_hkdf_expand` が単独で呼べる（K が一様な鍵なら RFC 5869 §3.3 どおり Expand だけでよい）。
- 部品の使い方は、NIST CAVP・RFC の既知解を実機のテストスケッチで照合する（ヘッダの名前の一致は動作の保証ではない）。

## ESP32 の loop タスクのスタックは既定 8 KB — 溢れると「Double exception」になる。低水位を測って決める

**事象:** 暗号の復号・行の解析を 1 行ごとに数 KB のスタックバッファで行うライブラリを実機のテストスケッチで動かしたら、
`Guru Meditation Error: Core 1 panic'ed (Double exception)` で再起動を繰り返した。バックトレースは mbedTLS の
メモリ確保と `_xt_alloca_exc` を指していた。テストごとに `uxTaskGetStackHighWaterMark(nullptr)` を出すと、落ちる直前の
テストの前で残りが 2,028 B だった（2026-09-26、esp32 コア 3.3.8、実測）。

**なぜ:** Arduino-ESP32 は `setup()`/`loop()` を 1 つのタスクで動かし、そのスタックは既定 8 KB
（`CONFIG_ARDUINO_LOOP_STACK_SIZE=8192`）。スタックが尽きると、原因の場所ではなく次の例外の処理中に落ちるので、
「Double exception」としか見えない。

**適用方法:**
- `SET_LOOP_TASK_STACK_SIZE(16 * 1024);` をスケッチのファイルの先頭で書くと、loop タスクのスタックを広げられる
  （コアの `Arduino.h` にあるマクロ。弱いシンボル `getArduinoLoopTaskStackSize` を上書きする）。16 KB で残りの最小は
  約 5 KB だった（実測）。
- 推測で広げず、テストの各段階で `uxTaskGetStackHighWaterMark` を出して、どこで何バイト使うかを測る。
- 大きな構造体（数 KB の記録用バッファなど）はローカル変数にせず、`static` かグローバルに置く。

## `.ino` の中でテンプレートを書くと、Arduino の前処理が壊す

**事象:** テスト用スケッチの `.ino` に配列の要素数を返すテンプレート関数を書いたら、`'N' was not declared in this scope`
でコンパイルに失敗した（2026-09-26、arduino-cli 1.5.1、esp32 コア 3.3.8、実測）。

**なぜ:** Arduino のビルドは `.ino` の関数の前方宣言を自動で作る。テンプレートの宣言はこの処理で正しく扱われない（推論。
エラーの内容と、マクロに替えると通ったことからの判断）。

**適用方法:** `.ino` ではテンプレートを使わない。要素数は `#define COUNT(a) (sizeof(a) / sizeof((a)[0]))` のような
マクロにするか、テンプレートは `.cpp`・`.h` に置く。

## M5Unified の既定では BASIC の起動時にスピーカーがポップする — 音を使わないなら `internal_spk = false`

**事象:** 音を一切使わないファームウェアで、M5Stack BASIC の起動時（電源を入れたとき・書き込み後の再起動）に、ときどき
スピーカーから「ポン」と鳴った。`M5.config()` の `internal_spk` を `false` にして `M5.begin(config)` すると、電源の入れ直し
5 回で 1 回も鳴らなかった（2026-09-27、M5Unified 0.2.14、1 台、利用者が聞いて判断）。

**なぜ:** M5Unified は BASIC でスピーカーを使う設定（既定）のとき、`begin()` の中でスピーカーの端子（GPIO25）を
Low に駆動する（M5Unified.cpp の `board_M5Stack` のスピーカー設定。ソースで確認）。浮いていた端子の電圧が段差で
変わるのが、アンプの入力に乗ると読める（推論）。

**適用方法:**
- 音を使わないファームウェアでは `auto c = M5.config(); c.internal_spk = false; M5.begin(c);` とする。
- 鳴る頻度が「ときどき」の現象は、直したあとに回数を数えて確かめる（例: 電源の入れ直し 5 回）。

## `arduino-cli monitor` は入力（stdin）が閉じるとすぐ終了する — 読み取りの道具は stdin を開けたまま持つ

**事象:** 実機のテスト結果をシリアルから読むために、`arduino-cli monitor -p <port> --config baudrate=115200 --quiet` を
スクリプトから起動したら、何も出力せずにすぐ終了した（`< /dev/null` でも同じ）。一度目は読めたのでタイミングの問題に
見えた（2026-09-26、arduino-cli 1.5.1、実測）。

**なぜ:** monitor は入力側が EOF になると終了する（観測から。ソースは読んでいない）。親の stdin が閉じていたり
`/dev/null` だったりすると、起動直後に EOF になる。

**適用方法:**
- 子プロセスとして起動するなら stdin を開いたパイプにして（Python なら `stdin=subprocess.PIPE`）、決めた時間だけ読んで
  から終了させる。
- ポートを開くと ESP32 が再起動する（最初に ROM の起動メッセージが別の速度で出て文字化けする）。結果を一定間隔で
  繰り返し出すテストにしておけば、いつ開いても読める。

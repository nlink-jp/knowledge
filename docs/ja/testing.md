# テスト

テスト設計と、ユニットテストでは届かない欠陥をリリース前に捕まえる手法。
各項目は「事象 → なぜ → 適用方法」。

---

## ユニットテスト全パスでも、実データ E2E と実機シミュレーションは別に必要

**事象（3 種の実例）:**
- ユニットテスト 47 件全パスのメール分析ツールが、実メール 12 通の E2E で 6 件のバグを
  露呈した（未登録の正規クラウド URL による偽陰性、サブドメイン一致の考慮不足、壊れた
  Base64 ヘッダのデコード失敗、認証結果単独判定の偽陽性など）。
- ビルド済みバイナリの実機シミュレーションで、データファイル不在時のエラー、フラグ無し
  実行の失敗、出力の日付未表示が発覚した。出力フォーマットや UX の問題はユニットテスト
  では原理的に見つからない。
- MCP サーバーはユニットテスト green + 台本 E2E 全 PASS の状態から、**実際に MCP
  クライアントとして使った途端に 3 件の欠陥が露出**し、その後も「使ってみて初めて出た
  欠陥」由来のリリースが続いた。台本 E2E は「自分が想定した手順」しか通らない。

**適用方法:**
- `testdata/samples/` に gitignored の実データ置き場を作り、リリース前に E2E を実行する。
- ビルド済みバイナリで基本操作を手動で一巡する: 正常系 → 設定なし起動 → 空の状態 →
  出力フォーマットの目視。
- **MCP/ツールは公開前に自分のクライアントに繋いで一巡する**。台本ではなくその場で
  考えた操作で（想定外を踏むのが目的）。第三者に依頼できればさらに良い。
- GUI のエラー表示は「エラーを意図的に起こして実機で出ること」を確認するまで信用しない。

## モックはエラー経路を「通す」が、そこで組み立てられた文言は誰も読まない

失敗経路の**分岐**はモックで網羅できる。網羅できないのは、その経路の末端で
**人間に渡る一文が意味をなしているか**である。アサーションは部分文字列一致で
緑になり、実際に読むと誤誘導になっている文言をそのまま通す。

**実例（2026-08-23, mcp-bridge v0.1.0 リリース前検証）。** 実 Slack MCP サーバに
失効トークンで接続して、ユニットテストが 1 つも落とさなかった欠陥が 2 件出た。

1. **原因が経路の途中で消える。** 401 を受けて資格情報を無効化 → 再試行 →
   「トークンが無い」で失敗、という順序のため、ユーザーに届く最終文言が
   `no access token` だけになっていた。事実としては正しいが、それは無効化の
   *結果*であって原因ではなく、読んだ人は「空のトークンファイル」を探しに行く。
   401 という原因・更新手段が無いという理由・実行すべきコマンドの 3 つを
   末端まで持ち回るよう修正した。
2. **成功したのにエラー行が出る。** 自己署名証明書のループバックコールバックでは、
   ブラウザの最初の接続が必ずハンドシェイクに失敗する（その失敗こそが、ユーザーが
   クリックスルーする警告を生む）。`http.Server` の既定 ErrorLog がそれを
   `tls: bad certificate` として毎回出力しており、しかも自前の「警告は想定内です」
   という案内の直後に出ていた。**成功したログインが失敗に見える**状態。

どちらもモックは同じ分岐を通っていた。違いは、実行して**出力を人間が読んだか**だけ。

**How to apply:**

- リリース前の実データ検証では、正常系だけでなく**失敗系を意図的に起こして
  端末の出力をそのまま読む**。無効な資格情報を1つ用意するだけで足りることが多い。
- エラー文言のテストは部分文字列一致だけにせず、**「出てはいけない語」も否定形で
  固定する**（上記1では `no access token` が出ないことをテストに入れた）。
- 使用しているライブラリが**自前のロガーを持つ**場合（`http.Server.ErrorLog` など）、
  それが本番経路で何を出すかを一度実行して確認する。自分が書いていない出力は
  自分のテストには現れない。

関連: [[all-green-unit-tests-still-need-real-data-e2e]]

## 配信で終わるパイプラインは、実際に配信するまで検証できていない

**症状:** フィードダイジェストのツールで、ユニットテスト 315 本と、収集から
ファイル生成までの実データ 1 巡がすべて通っていた。以下はそのすべてを
通り抜け、実際に送信して初めて現れた。

- インラインの `[title](url)` が、**タイトルだけでアドレス無し**で相手側に
  届いた。配信先の変換器にインラインリンクが無く、変換ではなく URL の破棄が
  起きていた。読むべきものを選ぶツールが、読む手段だけを落として配っていた。
- 文字数上限を測ったあとで、2 通目以降に `*(continued)*` を前置していた。
  実メッセージは**上限を 7 文字超過**。配信先は切り詰めずに拒否する。
- 4 分割だった前回のあとに 2 分割の実行をすると、`msg-03` と `msg-04` が
  ディスクに残る。送信側は連番で辿るので、今回の 2 通のあとに前回の 2 通が
  続いて送られる。

いずれもフィクスチャからは到達できない。1 つ目は配信先の変換器そのものが要り、
2 つ目は実長のマルチバイトテキストが要り（日本語は 1 文字約 3 バイトなので、
バイト基準の上限は両方向に静かに間違う）、3 つ目は「分割数が減る遷移」が要る。

**適用方法:**
- 「正しく描画された」と「正しく届いた」は別の主張として扱い、後者をリリース
  前に立てる。配信先から**読み返す**こと。そこに保存されている文字列が読み手の
  見るものであり、送った文字列と同じとは限らない。
- 各欠陥をケースではなく、パイプライン出力に対する不変条件にする——
  *全項目の URL が配信テキストに現れる（全フレーバーで）*、
  *全パートが上限内（マーカー込みで）*。不変条件はフレーバーやマーカーが
  増えても成立し続ける。
- 可変個数のファイルを書く前に、前回の出力を消す。列挙して消費する側は
  残骸も消費する。

## 訓練 runbook は書いた時点では未完成 — 1 回通すまで「何も検証していないステップ」が混ざる

**事象:** フォールバックツールの月次訓練 runbook を 7 ステップ書き、初回実行したら
**3 ステップが書き換わった**。(1) 「このプロジェクトは何をするもの？ ビルド/テスト
コマンドは？」で読み取り経路を検証しようとしたが、エージェントは指示ファイルを
システムプロンプトに注入しているのでツールコール 0 回で正解が返った — 正解が返る
ので合格に見えるが、検証したかった経路を通っていない。(2) 自動承認が設定既定で ON
で、承認ゲートの検証ステップが無人実行になるところだった。(3) 「プロジェクト外に
書いて」とモデルに頼んで sandbox 封じ込めを検証しようとしたら、モデルは制限を読んで
試行自体を断った（＝何も検証していない）。同じ要求の別実行では試行し、ゲートが先に
出た。

**適用方法:**
- **書いたら必ず 1 回通す。** ステップが書き換わるのは正常な結果である。書き換わら
  なかったときは「本当に通したか」を疑う。runbook を編集したら、変えたステップだけ
  でも実行する（AGENTS.md 等に明文化して強制する）。
- **「合格に見えるが何も検証していない」の 3 パターンを疑う**:
  検証対象の経路を通らずに正解が出る質問（別の経路に答えが置いてある）/ 被験体の
  協力に依存する検査（→ 直接経路に置き換える）/ 実行ごとに結果が変わる検査
  （→ それは検査ではない）。
- **状態依存の既定値は手順の先頭で固定する。** 「たまたま ON だった」で検査が骨抜きに
  なる。
- チェックリストとは別に **「実タスク 1 件を対象ツールだけで完了させる」ステップ**を
  置く。チェックリストは「動く」を示すが、「使える」は実タスクでしか出ない。
- **判定は「合格 or issue」の 2 値**にする。「だいたい動いた」を許すと記録が意味を
  失う。スキップは「スキップした」と記録する — 無記録の欠落は合格として読まれる。

## 実装済みなのに一度も発火しない機能は、単体テストを全部通る

**事象:** 会話履歴の自動圧縮を実装した。単体テストは全部緑。実運用では**一度も発火せず、
警告も出なかった**。原因は 2 つ重なっていた。(1) 閾値判定が使うコンテキストウィンドウ値は
起動時に非同期解決していたが、解決を仕掛けていたのは対話パスだけで one-shot パスには配線が
無く、値 0 のまま判定が常に false になっていた。(2) 切断点の不変条件を「ユーザー発言の境界
のみ」と定めていたが、長いエージェントループにはユーザー発言が先頭に 1 件しか無く、
**その機能が存在する理由そのものである事例を構造的に排除**していた。

**適用方法:**
- **単体テストは条件を直接与えるので、「その条件が実運用で成立するか」を検証しない。**
  閾値・条件付き発火のある機能は、閾値を極端な値へ振った設定で実機実行し、**発火ログを
  目で確認する**まで「実装した」と言わない。
- 非同期解決値に依存する機能は、入口（対話 / 単発 / スクリプト / 再開…）ごとに配線を数える。
  値が未設定のとき黙って no-op になる設計そのものを疑い、通知を出す設計に変える。
- 不変条件は「最も典型的な使い方」に当てたテストを 1 本必ず持つ。安全側に寄せた規則が
  本命ケースを排除していないかは、規則を読んでも気づけない。
- 発火しない状態が起こり得るなら、その事実を通知する。**無言の no-op は「機能が無い」と
  区別できない。**

## 外部依存は最初からモック可能に設計する

**事象:** テスト実行中に実ブラウザが起動してしまった。後から関数変数に差し替えたが、
最初からそう設計すべきだった。

**適用方法:** ブラウザ起動、外部 HTTP、時刻取得などの外部依存はパッケージ変数または
インターフェースで注入可能にし、テストで差し替える。

## xattr 書き込み失敗は deny ACL で「実注入」できる

**事象:** `setxattr` が失敗する経路（quarantine を付けられないボリューム等）をテスト
したい。モック seam は本番コードに可変グローバルを持ち込み、実 syscall の失敗経路を
通らない。ディスクイメージは遅く環境依存。

**適用方法:** 展開先ディレクトリに継承付き deny ACL を張ると、自分が所有するファイルでも
実際に EPERM を起こせる:

```sh
chmod +a "$(id -un) deny writeextattr,file_inherit,directory_inherit" <dir>
```

新規作成されるファイルが ACL を継承するので、配下すべてで xattr 書き込みが失敗する
（xattr 非対応ボリュームへの展開と同じ形）。速く（実測 0.13 秒）、本物の失敗経路を通る。
テストからは chmod を実行し、失敗したら skip する（環境差の保険）。

## MCP サーバーの自動 E2E はダミー JSON-RPC クライアントで

**事象:** LLM をループに含めるテストは非決定的・遅い・トークンコストが掛かる。一方、
プロトコルレベルの round-trip / エラーパス / タイムアウト / ワークスペース分離は
すべて固定 JSON-RPC で検証可能。

**適用方法:**
- テストから子プロセスを spawn して stdin/stdout で JSON-RPC を打つ Harness
  （`Start / Call / Notify / CallTool / Close`）を実装する。
- `//go:build e2e` タグで通常の `go test ./...` から隔離。コンテナ等の実環境を要求する
  テストは env var で skip 制御。
- 最低限のシナリオ: lifecycle / errors / timeout / 連続ワークスペース分離。
- LLM 実機（Claude Desktop 等）での確認は最終段階だけでよい。ただし「自分でクライアント
  として使う」段は別途必要（上記 E2E の項参照）。
- 埋め込みネイティブライブラリの stdout 汚染は stub build では再現しない — 実エンジンで
  E2E すること（mcp-server-design.md 参照）。

## テストが緑でも、期待値そのものが誤っていれば何も担保しない

**事象:** 外部 API の状態を UI の挙動へ写像するコードにユニットテストを書き、全て緑だった。
それでも機能は誰も使えない状態で出荷され、ユーザーが実機で触って初めて発覚した。

**なぜ:** テストは「私が正しいと思った写像」を忠実に検証していただけだった。写像そのものが
間違っていたので、テストは誤りを固定する役にしか立たなかった。外部 API のセマンティクス
（どの状態値がどういう意味か）は**こちらの想像であって、テストでは検証できない**。

**適用方法:**
- 外部 API の状態値を UI 挙動へ写像するときは、**そのテストを「仕様の確認」と見なさない**。
  ドキュメントの読み違いはテストを通過する。
- 特に「その状態のときコントロールを無効化する」ような**能力を奪う分岐**は、
  誤ると機能全体が到達不能になる。実機確認の対象として明示的に挙げる。
- 実機でしか分からない領域を**作業計画の時点で列挙**し、「ここは確認してもらう」と
  宣言しておく。後から気づくと、それまでの「テスト緑」が判断を誤らせる。

## 「実測済み」を名乗る前に、プローブ入力が実物の代表かを問う

**事象:** 端末 Markdown レンダラが幅超過のコードブロック行をどう扱うかを、132 セルの
**空白を含まない**罫線 1 行で実測し、「切り詰めも折り返しもしない（無加工で通す）」と
結論して設計文書に「実測済み」と記載した。独立レビューが実物の罫線アート — ボックスの
間に**空白を含む** — で再測定したところ、レンダラはコードブロック行を**空白で語折り返し**
しており、幅超過の図は端末に届く前に断片の交互列に粉砕されていた。プローブがたまたま
その機構（語境界）を運ばない入力だったため、存在する挙動が観測不能だった。

**なぜ:** 合成した最小入力は「測りたい性質を運ぶ成分」を欠きうる。n=1 のプローブで
一般命題（「このレンダラは折り返さない」）を主張すると、欠けた成分の数だけ偽の
「実測済み」が生まれる。しかも「実測済み」の札が付いた主張は再検証されにくく、
本人の仮説に最適化されたプローブの欠落は本人には見えない。

**適用方法:**
- プローブ入力は**本番でその経路を流れる実物**（実レンダラ出力・実モデル出力・実ログ）
  から取る。合成するなら、測りたい性質に効きうる成分（空白・全角・制御文字・長さ）を
  意図的に含める。
- 文書に「実測済み」と書く主張には**入力の素性を併記する**（何を・どう流したか）。
  再測定者が代表性を判定できる形でだけ、実測は主張になる。
- 独立検証パスに「主張は全件コード/プローブで再検証してから採用」を課す。この事例を
  捕捉したのはその指示だった。同型の先例に「手書き期待値が実レンダラの装飾を含まず
  偽陰性を出荷」がある — 期待値もプローブも、実物から作る。

## GUI は「見えている部分」と「動いている部分」が独立していることを前提に検証する

**事象:** メニューバー常駐アプリで、バーのラベルが正しく表示されているのを確認して
「動作している」と判断した。実際にはクリックで開くパネルの中身が初版からずっと空だった。

**なぜ:** メニューバーのラベルとパネルの内容は別のビュー階層で、片方が正常でももう片方が
壊れていることがある。またパネルはプログラムから開きにくい（アクセシビリティ権限の
プロンプトが出る、クリックが前面プロセスに飛ぶ等）ため、自動確認から漏れやすい。

**適用方法:**
- 「ラベルが出ている」は動作確認ではない。**UI の各面を個別に確認対象として数える**。
- 自動で開けない面があるなら、**そこは人が見る前提で計画に書く**。曖昧にしたまま進めると、
  確認していない面を確認したつもりになる。
- 長時間稼働でしか出ない挙動（タイマー凍結、日付跨ぎのリセット）は、
  一晩置いた後の実データで検証する。

## メニューバー常駐（LSUIElement）アプリの E2E は CGEvent + CGWindowList + ウィンドウ単体 screencapture で駆動する

**症状:** メニューバー常駐アプリのパネルをテストスクリプトから開けず、各状態が
未検証のまま残った（上の項目を参照）。AppleScript は役に立たない —
`System Events` の `key code` は Carbon `RegisterEventHotKey` のハンドラに届かず、
`NSStatusItem` の action も AppleScript の click では発火しない。

**なぜ:** パネルにはスクリプト可能な面が無い。しかしグローバルホットキーと
ウィンドウは持っており、どちらもより低いレイヤから到達できる。

**適用方法:** ハーネスが一度コンパイルする小さな Swift ヘルパで 3 点。

- **開く** — ホットキーを `CGEvent` として post する
  （`CGEvent(keyboardEventSource:virtualKey:keyDown:)` →
  `post(tap: .cghidEventTap)`）。post する側のプロセスが Accessibility 許可済み
  である必要がある（`AXIsProcessTrusted()`）。
- **開いたか確認する** — `CGWindowListCopyWindowInfo([.optionAll], kCGNullWindowID)`
  を owner 名で絞り、`kCGWindowIsOnscreen` と `kCGWindowNumber` を読む。
- **見る** — `screencapture -x -o -l <windowid>` でそのウィンドウ単体を撮る。
  全画面キャプチャより必ずこちらを使う。無関係なウィンドウ（他人とのチャット、
  メール、チケット）が画像に一切入らない。

ホットキーは既定値を仮定せず、**アプリ自身の `UserDefaults` から読んでから**送る。
保存値はたいてい `NSEvent.ModifierFlags`（shift `0x20000` / command `0x100000` /
option `0x80000`）であって **Carbon マスクではない**。違う組み合わせを送ると
「ホットキーが壊れている」ようにしか見えず、誤った不具合報告を招く。

**想定しておくべき失敗モード:** 合成キー入力は key status を持つウィンドウに
届く。そしてそれは**テスト対象とは限らない** — non-activating panel は key status
を安定して取らないし、macOS の focus-stealing 防止は起動後 ~30 秒 activation を
拒否しうる。外れた打鍵はすべて**ユーザーの前面アプリに入り**、余計な文字列を
打ち込み警告音を鳴らす。したがって、打つ前にウィンドウが key であることを確認し、
送る文字列は短く無害なものにし、**入らなくなった時点でこの手法をやめる**こと。
リトライこそがユーザーの他のウィンドウに届く。この方法は「ウィンドウを開いて
状態を撮る」用途には向くが、**信頼できるテキスト入力ドライバではない**。

**ステータス項目そのものは、ウィンドウ一覧では観測できない（macOS 27.0、2 回観測）:**
上の確認手順が見ているのは、アプリが開く**パネルのウィンドウ**である。メニューバーの項目が
出ているかを同じ方法で確かめようとすると、誤った結論になる。`NSStatusItem` を 1 つ持つアプリを
起動しても、そのアプリの pid が所有するウィンドウは 0 件で、ウィンドウ一覧の総数も起動の前後で
変わらなかった — どのプロセスにも新しいウィンドウは増えていない。項目は目視では表示されていた。
空の結果は「項目が出ていない」の証拠にならない。項目の表示は、目視、アクセシビリティツリー、
またはアプリ自身に自分の座標を報告させる方法で確かめる。あわせて、プローブが window server を
見られていること自体を確かめておく。一覧の総数を同時に出力しておけば、「見えていない」と
「存在しない」を取り違えない。

**代替ではなく補完:** この方法で到達できない状態（IME 変換中、初回のモデル
ダウンロードなど）は、純関数のユニットテストと、人が一度目視する工程が引き続き必要。

## レイアウト崩れは、アプリを起動せずテストターゲットからのオフスクリーン描画で見る

**症状:** 純関数のユニットテストは文字列と数式しか触れないので、「その文字列が
実際の幅に収まるか」は原理的に検出できない。表示行を 1 本増やしただけの変更でも、
最長の分岐で truncation が起きるかどうかは机上では決まらない。かといって合成イベントで
実アプリを駆動する方法（前項）は、外れた入力がユーザーの前面アプリに漏れるため、
レイアウト確認のたびに使うには重い。

**なぜ:** SwiftPM の実行可能ターゲットはテストから `@testable import` できる。
ビューを `NSHostingView` に載せればアプリを起動しなくてもレイアウトが確定し、
`bitmapImageRepForCachingDisplay(in:)` + `cacheDisplay(in:to:)` で PNG に落とせる。
実アプリと同じレイアウトエンジンと実フォントが走るので、折り返し・truncation・
実際の文字幅がそのまま出る。ユーザーの画面には何も起こらない。

**適用方法:**

- テストターゲットに使い捨てのレンダラを置く。`NSHostingView(rootView: TheView().environmentObject(model))`
  を作り、**本番と同じ幅**（例: popover の内容幅 + padding）を与えて `layoutSubtreeIfNeeded()`。
- 高さは `fittingSize.height` を使い、決め打ちで押し込まない。収まらない状態を見たいのだから、
  高さを固定すると証拠のほうが消える。
- 状態は `@Published` に直接値を入れて作る。表示の検証なので、外部プロセスや
  ネットワークは呼ばせない。
- **分岐ごとに 1 枚ずつ出して全部見る**（正常 / 警告 / 超過 / データ不足）。崩れるのは
  たいてい最長の文字列を持つ分岐で、それは平常時の分岐ではない。
- 確認が済んだらレンダラは消す。スナップショットを回帰テストとして残すと、OS の
  フォント更新やシステム配色の変更で無関係に落ちる。残すなら意図して選ぶこと。
- 合成イベントで実アプリを駆動する手法は、**本物のアプリでしか起きないこと**
  （許可ダイアログ、メニューバー上の実配置、起動直後の挙動）に取っておく。

## 二重の防御があるとき、片方だけで説明のつく観測を両方の証拠にしない

**事象:** MCP サーバーの stdout 汚染対策を 2 層で入れた — ①発生源でランタイムのログ
コールバックを差し替える ②本物の stdout を dup して transport 専用にし fd 1 を stderr へ
向ける。実 E2E で「stdout は JSON のみ・stderr は 0 行」を観測し、**両方が効いている証拠
だと読みかけた**。

**なぜ:** stderr が 0 行だったのは①のログハンドラが info レベルを落としていたからで、
**①だけで観測結果が完全に説明できる**。②が実際に機能したかどうかについて、この観測は
何も言っていない。②が壊れていても同じ観測になる。

**適用方法:** 防御を多層で入れたら、**層ごとに独立した検証を用意する**。この件では
機構を直接叩くユニットテストに置き換えた:

```go
protocol, _ := claimStdout()
protocol.Write([]byte("PROTOCOL\n"))   // transport 側に出るべき
os.Stdout.Write([]byte("STRAY\n"))     // stderr 側に出るべき
// → protocol ストリームに "STRAY" が無いことを assert
```

一般則として、**「観測 O は防御 A でも防御 B でも説明できる」なら、O は A の証拠でも
B の証拠でもない**。統合テストが緑であることは、各層が生きている証明にならない。

## コードを疑う前にフィクスチャを検証する

**事象:** 話者分離の検証で `say -v Kyoko` と `say -v Otoya` の 2 音声から会話音声を合成し、
「2 話者のはずが 1 話者と判定される」と実装を疑って数十分を溶かした。原因は
**`Otoya` が未インストールで、`say` が無言のまま既定音声にフォールバックしていた**こと。
4 クリップ全部が同一話者だったので、話者分離の「1 話者」判定は正しかった。

**なぜ:** 生成系のコマンドは、指定したリソースが無いときエラーではなく**もっともらしい
別物**を返すことがある。`say` の voice、フォント指定、モデル名、ロケール指定などが典型。
出力ファイルは正常に生成されるので、フィクスチャが壊れていることに気づく手がかりがない。

**適用方法:** 合成したフィクスチャは、**期待した性質を持っているかを別手段で確認**して
から実装の検証に使う。最低限、指定したリソースが実在するかを事前に確かめる
（`say -v '?'`、フォント一覧、モデル一覧）。テストが「正しい答え」を返しているのに
それを不具合と読む方が、実装バグより高くつく。

## 「該当なし」は、全ソースが実際に答えたときだけ答えになる

**何が起きたか:** ある lookup ツールは、上流が名前を `domain` と `hostname` の
どちらか一方にしか索引せず、しかも**どちらも 200 を返す**ため、2 つの型で照会する。
実 API 検証中に片方が 429 で落ち、もう片方が 0 件を返した結果、ツールは
**「どの報告もこの IoC を挙げていない」と表示して exit 0 で終了した** — 一時的な
上流エラーから「シロ判定」を捏造したことになる。スタブによるテストは全て通っており、
実 API を叩いて初めて露見した。

**なぜ:** 「一致が無い」と「訊けなかった」は**データ上は同一**で、意味は正反対である。
失敗したソースを空の結果集合に畳み込むコードは、後者を前者として報告する。しかも
否定的な答えは誰も再確認しない — 偽陽性は対応する人間が精査するが、偽陰性は綴じられて
忘れられる。片方が失敗し片方が成功したときにしか存在しない不具合なので、モックでは
原理的に捕まらない。

**どう適用するか:**

- 結果に `incomplete` フラグを明示的に持たせ、「空 **かつ** 不完全」を独立した状態
  として名前を付ける。呼び出し側が 2 つの真偽値を毎回思い出す設計にしない。
- 出力に書く。利用者に見える `INCONCLUSIVE` は、黙った 0 件よりはるかによい。
- 終了コードに載せる。スクリプトは exit 0 を「シロ」と読む。未検証の否定は 0 で終わらせない。
- 失敗したソースを名指しする。「何か失敗しました」では、答えをどこまで信じてよいか
  読み手が判断できない。
- 上流が同一の論理オブジェクトに複数の endpoint を持ち、**そのどれもが 200 を返す**
  場合、取り違えはエラーにならず静かな空結果になる。代替も引き、どちらが答えたかを併記する。

## 揺らぐ系の指標を 1 回の実行で語らない

**何が起きたか:** ローカル推論エンジンで 2 つのモデルを比較し、片方が「49 分の
音声中に 48 セグメント連続の反復ループを起こす」と報告した。後日まったく同じ
バイナリ・同じモデル・同じ音声・同じ設定で回し直したところ、最大連は 19 だった。
3 回ずつ回して初めて分かったのは、**出力量そのものは安定している**（文字数の振れは
±1%）のに、**破綻の構造は大きく振れる**（最大連 19 / 45 / 48）ということだった。
マルチスレッドの簡約順序が生む微小な浮動小数差が、確率的な分岐点で決定を反転させる。

**なぜ:** 「決定的な処理だから 1 回測れば足りる」という前提が、並列化された数値計算では
崩れる。しかも崩れ方が一様でない — 平均的な量は安定するのに、閾値近傍の離散的な判断
（ループに入るか、話者を分けるか、フォールバックするか）だけが揺れる。**最初の 1 回が
分布の裾だった場合、報告した数値は再現せず、それを見た人はこちらの測定全体を疑う。**

**どう適用するか:**

- **系が揺らぐかどうかを、比較を始める前に確かめる。** 同じ入力を 2 回通すだけでよい。
  出力が違えば以降の全指標は n≥3 で幅として扱う。
- **報告は点ではなく範囲で書く。** 「48 連続」ではなく「19〜48（3 回）」。
- **判定に閾値を置くなら、2 群の範囲が重ならないことを根拠にする。** 上の例では
  「ループを起こす側 19〜48」対「起こさない側 2〜3」なので、閾値 6 は隙間に置ける。
  片方の 1 標本の隣に閾値を置くと、次の実行で誤判定する。
- **量が安定していることを、構造も安定している証拠に使わない。** 上の例では文字数が
  ±1% で一致していたが、それはループの再現性について何も言っていない。

## 正解が無い出力は、構造の健全性で測れる

**何が起きたか:** 39 分の実音源で 2 つの文字起こしモデルを比較したかったが、
参照テキストが無いため誤り率は測れなかった。代わりに**正解を要さない指標**を測った —
セグメントの被覆率、同一テキストの連続反復、セグメント間の最大空白、話者ラベルの偏り。
これで「一方は 1.45 倍の文字を出す」「一方だけが反復ループに落ちる」という、
選択を左右する差が定量化できた。

**なぜ:** 正解の無いデータは「測れない」と諦められがちだが、**壊れ方には形がある**。
反復ループ、取りこぼし、過分割は、内容を読まなくても構造だけで検出できる。しかも
そういう破綻は往々にして**出力が完全に整形式のまま**起こる（JSON は妥当、全フィールドが
埋まり、エラーも出ない）ので、構造を測らなければ誰も気づかない。

**どう適用するか:**

- 正解の要る指標（精度）と要らない指標（構造）を分け、後者だけで先に比較する。
  多くの場合それだけで候補が絞れる。
- **範囲が重ならない差だけを結論に使う。** 構造指標は代理指標なので、僅差は
  意味を持たない。
- **指標スクリプトは本文を一切出力しない設計にする。** 件数と率だけを出すなら、
  秘密情報や私物のデータにそのまま向けられる。正解の無い実データは、たいてい
  「外に出せないから正解が無い」のであって、この制約と正解の欠如は同じ根を持つ。
- 被覆率のような指標は**単独では両義的**であることに注意する。被覆が高いのは
  取りこぼしが少ないからかもしれないし、無音や音楽に対して幻覚しているからかもしれない。
  独立した第三の観測（この例では VAD）で切り分ける。

## 列挙ツールが返した対象は、目的の対象と照合してから証拠にする

**事象:** USB 接続の外付け SSD から SMART 情報が読めるかを調べていた。診断ツールの
自動列挙モード（`--scan`）が返したデバイスに対してコマンドを実行し、返ってきた I/O
エラーを「この SSD では読めない」証拠として報告した。実際には列挙は**調査対象の 2 台を
1 台も拾っておらず**、別系統のハブにぶら下がった**中身の入っていない空のドライブケース**を
1 件だけ返していた。そのエラーは「メディアが無い」ことでも説明がつき、調べていた制約の
証拠には全くなっていなかった。対象 2 台をデバイスパスで名指しして測り直すと、別のエラーが
出た（結論そのものは変わらなかった）。

**なぜ:** 列挙ツールは「見つかったもの」を返すのであって「こちらが指したもの」を返さない。
結果が 1 件だと、それが目的の対象だと錯覚しやすい。さらにこの件では**結論が偶然正しかった** —
「USB 経由では読めない」という答えは別の証拠でも裏づけられていたため、**証拠の方が
間違っていることが最後まで表面化しなかった**。正しい結論を誤った証拠で支えると、前提が
変わったとき（別のハードウェア、別の OS 版）に何が崩れたのか追跡できなくなる。

**適用方法:**

- 列挙の出力は、**独立した識別子**で目的の対象と照合してから使う（デバイスパス、
  シリアル、容量、論理名）。ツールが付けたラベルだけを信じない。
- **列挙件数と、自分が知っている対象の件数を突き合わせる。** 2 台繋がっているのに 1 件しか
  出ないなら、その時点で列挙自体を疑う。ゼロ件より、数の合わない非ゼロ件の方が危険。
- 対象を名指しできる経路があるならそちらで測り直す。**自動列挙は探索の道具であって、
  検証の道具ではない。**
- 「結論が合っているから証拠も正しい」は成り立たない。結論と証拠は別々に点検する。

## 論理ツリー上の位置から物理的な配置を推定しない

**事象:** 同じ調査で、対象 SSD が OS のデバイスツリー上で SoC 内蔵の USB コントローラ配下に
いることを根拠に「本体の USB 専用ポートに挿さっている」と判定し、利用者に
「Thunderbolt ポートへ挿し替えよ」と指示した。**実際は最初から Thunderbolt ポートに
挿さっていた。** その環境では Thunderbolt ポートの USB トラフィックも同じ USB コントローラに
現れる設計で、ツリー上の位置からポート種別は原理的に判別できない。利用者の
「いや、そちらに挿さっている」の一言で覆った。

**なぜ:** 抽象化層のツリーは「そのデバイスがどう扱われるか」を表すのであって、
「どこに挿さっているか」を表さない。さらに同じ物理ポートが複数のプレーンに別々に現れる系
（この例では USB プレーンと Thunderbolt プレーン）では、片方のプレーンだけを見ると
「そこには何も無い」ように見える。

**適用方法:**

- 物理配置は、**位置が確定しているデバイスを基準点にして較正する。** この件では
  「Thunderbolt ハブは Thunderbolt ポートにしか挿さらない」→ そのハブが問題の USB
  コントローラ配下に現れている → このコントローラは Thunderbolt ポートも含む、と 1 手で
  確定できた。推定を積み上げるより、**既知の 1 点を探す方が速い。**
- **片方のプレーンの「デバイスなし」を不在の証拠にしない。** 逆に、この非対称性自体は強い
  診断信号になる — 上の例では Thunderbolt バス側が「未接続」と言い張ることが、その機器が
  PCIe リンクを張らない純粋な USB ブリッジである証拠になった。
- **目の前の人間が数秒で答えられる物理的事実を、ツール出力から推定しない。** 聞く方が速く、
  確実で、外したときの手戻りも小さい。推定してよいのは、聞ける相手がいないときだけ。

### 並行性の懸念は読解ではなく並行テストで検証する — バグは疑われた層の隣で出る

**事象:** 「タイムスタンプ由来のセッション ID は並列実行で衝突するのでは」という
指摘を受けた。コードを読むと疑われた層は安全だった（O_EXCL + サフィックス再試行 +
flock）。だが「安全であること」を示すために書いた 16 並行の実測テストは、**隣の層**
（状態ディレクトリのマーカー書き込み）の実レースを約 50% の頻度で検出した。読解に
よる「安全です」という回答なら、このバグは残っていた。

**適用方法:**
- 並行性への疑義には、結論がどちらでも**まず並行回帰テストを書く**（同時スタート用の
  start チャネル + `-race` + 複数ラウンド）。テストは疑われた仮説だけでなく経路全体を
  通すので、隣接層の欠陥も浮く。
- goroutine テストで見つけ、**実プロセス同時起動でも確認する**（O_EXCL・flock・rename
  はカーネル語彙なので同型だが、E2E は配線の見落としを拾う）。
- 「該当なし（安全）」と答える前に測る — 否定的回答の完全性義務は並行性にも適用される。

### 依存注入した機能は「本番の 1 呼び出し箇所」が最弱点 — 配線は AST テストで固定する

**事象:** UI 言語カタログ機能を実装し、ユニットテストは全部 green、非対話モードの
E2E も通した。だが本番唯一の TUI 構築箇所がカタログ引数を渡し忘れており、TUI 全体が
1 リリースの間、黙って英語フォールバックで動いていた。テストは依存を自分で注入する
ので配線漏れを検出できず、E2E は配線されている側の面だけを見ていた。

**適用方法:**
- 「実装済みでも黙って発火しない」の第 3 のパターン: **オプション構造体のフィールドは
  nil 既定で静かに退化する**。nil 許容 + 良識的フォールバックは、まさにその親切さの
  ぶんだけ配線漏れを不可視にする。
- 巨大な初期化関数の中のリテラルには挙動テストが届かない。**go/ast で本番ファイルを
  パースし、構築リテラルに必須フィールドが並んでいることを検証するテスト**が配線を
  固定する（数十行で書ける・整形に頑健・フィールド消滅で確実に落ちる）。
- E2E は「新機能が効いた面」ではなく「新機能が通る全ての面」で 1 回ずつ。今回は
  非対話（cmd 側）だけ実測し、対話（TUI 側）を実測しなかったのが敗因。
## ログから時刻の結論を出す前に、そのログの時刻表現の素性を確定させる

**事象:** 日次のログ要約レポートが「昨日ディスクの I/O エラーが発生」と報告した。カーネル
ログの内容（ATA コマンドのタイムアウトとリンクリセット）を読み解いてドライブ故障の診断まで
組み立てたが、実体は **2 年前の同月同日**のログだった。`/var/log/messages` が 2.7 年
ローテートされておらず、RFC 3164 形式が年を持たないため、レポートの日付一致が過去年の
同じ日付文字列を拾っていた。

**なぜ:** 中身の解釈は正しかった。誤っていたのは**前提の時刻**で、それが偽だったので診断
ごと無効になった。時刻表現の曖昧さは何段階もある — 年の有無、タイムゾーンの有無、表示側の
再解釈、事象時刻か取り込み時刻か、相対時刻の変換。どれもログを読む段階では見えず、結論を
出した後に効いてくる。

**適用方法:** 中身を読む前に、次を確定させる。

1. **カバー期間** — `ls -la`（サイズ）→ `head -1` / `tail -1`。静かなサーバのログが
   数十 MB なら、それだけで異常のサイン。
2. **年を持つか** — RFC 3164（`Aug 22 06:37:29`）は持たない。**年なし形式は、ファイルが
   1 年を超えた時点で日付一致が壊れる**。
3. **タイムゾーン** — 記録側（RFC 3164 はオフセットも持たない）／表示側（`journalctl` は
   閲覧者の TZ でレンダリングするため、同じ事象がテキストログと違う時刻に見える）／混在
   （コンテナが UTC、ホストがローカル時刻）。**DST のある地域では年 1 回「重複する 1 時間」
   と「存在しない 1 時間」が生じ、文字列ソートも日付一致も壊れる**。
4. **事象時刻か取り込み時刻か** — 転送やバッファリングを挟むと後者になる。
5. **単調性を仮定してよいか** — 「追記順＝時系列」は複数書き手・NTP のステップ調整・
   マージされたファイルで壊れる。
6. **相対時刻の変換** — `dmesg` の `[12345.678]` は起動からの経過秒。`dmesg -T` は
   起動時刻＋単調時計から絶対時刻を計算するため、**時刻がステップ調整されるとずれる**。

曖昧な時刻表現しか持たないログで日付を判断せず、明示的な情報源に当たる:

```
journalctl -k --since "YYYY-MM-DD" --until "YYYY-MM-DD" -o short-iso
```

journald は UTC マイクロ秒の実時刻と boot ID を保持しており、年・タイムゾーン・起動回数の
いずれも曖昧でない。要点は「別の情報源と突き合わせる」ではなく、**時刻表現の素性が良い
情報源に当たる**こと。

年なしログで年を割り出すには、日付文字列の出現行番号を見る:

```
grep -n "^Aug 22 " /var/log/messages | cut -d: -f1   # 出現行番号
grep -n "^Jan  1 00:0" /var/log/messages             # 年境界
```

同じ日付文字列が遠く離れた行番号に現れたら、そのファイルは複数年にまたがっている証拠。
年境界の行番号で挟めば各クラスタの年が確定する（5 の単調性仮定に依存する）。

### 利用から学ぶ機能は、利用の形をしたデータでテストする

**症状:** 承認ルールの学習器を、ユニットテスト・E2E・「3 つの別セッション
で承認」という閾値とともに出荷した。最初の実セッション — 25 回の
エスカレーションを全部承認 — は提案ゼロを生んだ。E2E は閾値を満たす
ためにちょうど 3 セッションを仕込んでおり、機構が動くかは測ったが、
**閾値が到達可能かは一度も測っていなかった**。

**なぜ重要か:** 閾値を満たすために書かれた fixture は、その閾値を反証
できない。テストは緑で、機能は動き、欠陥は実データが来るまで不可視
だった — 「発火しない機能」と同じクラスだが、沈黙ではなく**合格して
いるテストの背後**に隠れている。

**適用方法:**
1. **少なくとも 1 つの fixture を、閾値ではなく本番の形にする。**
   学習器なら、実利用が生む分布のこと: 1 セッションに集中した作業、
   1 回限りの項目が多数、ロングテール — そのドメインの実際の姿。
2. **「これは動くか」と「このハードルは届くか」を別々に問う。** 別の
   問いであり、実分布が要るのは前者だけである。出荷前に、数字で
   答える。
3. **実報告が来たら、診断の前に再現する。** 報告された形の合成
   トランスクリプトが、もっともらしい物語を 1 回のテスト実行で 2 つの
   実測された原因に変え、そのまま回帰テストになった。
4. **そもそも摩擦が、数えている形をしているか確認する。** 今回は半分が
   カテゴリの問題だった: ツール単位の頻度では「毎回違うツールを 1 回
   ずつ」という形の摩擦は見えない。そのカウンタ上の閾値は安全かつ
   到達可能にはならないので、変えるべきはルールの**単位**であって
   数値ではなかった。

## 機能を区切る定数は、実利用でその窓が覆う母集団を数える

**事象:** エージェントのリスク評価器に「オペレータ指示を証拠として同梱する」機能を
付けたとき、対象を**ターン先頭 3 ラウンドのみ**と直感で区切った（「序盤のコールは依頼に
遡れる、深部は依頼が名指さないサブゴールに仕える」）。数週間後、全セッション記録から
ラウンド位置を再構成して実測すると: モデル評価の **70%** が窓の外、ターン**終端**の
ゲート対象コール — 送信・保存など、整合を最も知りたいアクション — は **63%** が窓の外
だった。窓外で起きたエスカレーションは、記録のある範囲でオペレータが事後に全件手承認
しており、実態は読み取り専用の調査コールへの誤警報だった。

**なぜ重要か:** カットオフ定数は設計時点の想像上の利用形に基づく。実利用の分布は裾が
重く（ラウンド 8〜48 に評価の半分があった）、**どの定数も裾とは合わない** — 「現実に
合う数字」が存在しないことが実測の答えになる場合がある。これは「発火しない機能は
適合率では検出できない — 分母を数える」の変種で、**窓の守備率も分母を数えないと
見えない**。機能は動いていて、テストも通り、窓内では正しく働くので、なおさら気づけない。

**適用方法:**
- 機能をカットオフ定数（ラウンド数・件数・サイズ・経過時間）で区切ったら、リリース後に
  実ログで**その窓が覆う母集団の割合**を測る。守備率が少数派なら、定数の調整ではなく
  カットオフ自体の要否を問い直す。
- 測れる形で記録を残す: 判定イベントに位置情報（ラウンド番号等）を含めるか、メッセージ
  列から位置を再構成できるトランスクリプトにする。今回の実測は後者で可能だった。
- 窓外の「機能なし」経路が誤警報を生んでいるかは、エスカレーション→直後の人間の判断
  （承認/拒否）の対応で測る。全件承認されているエスカレーションは摩擦であって防御ではない。

## 外部 API の語彙と可視範囲はライセンス階梯で変わる — 文書ではなく手元のキーで実測する

**事象:** 公式ドキュメントに載る filter 語彙（ハイフン形式）を実 API が 400 で
拒否し、受理される語彙（アンダースコア形式）は文書のどこにも無かった。受理される
型でも中身は階梯依存で、上位ライセンス限定の型は**エラーではなく空**を返した。
ベンダー自身の公開参照実装も文書側の語彙を使っており、そのままでは動かなかった
（lookup CLI+MCP プロジェクト、2026-09）。

**なぜ:** API の応答は「エンドポイント仕様 × キーのエンタイトルメント」の積で
決まる。文書は最上位ライセンスの視界で書かれがちで、参照実装の存在は正しさの
証拠にならない。空応答・400・403 はどれも「使えない」だが意味が違う —
区別しないと「存在しない」と「（この階梯からは）見えていない」を取り違える。

**適用方法:**
- 統合前に**手元のキーで**仕分けの実測を行う: 400（語彙・構文の拒否）/
  403（エンドポイント単位の拒否）/ 空（内容の階梯ゲート）。結果は日付とキーの
  階梯を添えて記録する。
- 権限一覧を返すエンドポイント（privileges 等）があれば最初に読む。挙動からの
  推測より 1 リクエストで確定する。
- **手元で実測テストできない機能は出荷しない**。上位ライセンスで動くはずの機能を
  推測実装で残すと、検証不能なコードパスが恒久化する。スコープを「検証可能な
  機能セット」で切り、その判断と理由を利用者向け文書に明記する。
- 階梯ゲートされた空応答をツール結果として返す面では、利用者向け文書に
  「空 = 不存在ではない」ことを書く。

### golangci-lint は同一メッセージの指摘を 3 件で打ち切る — 一括修正の前に全件を出す

**事象:** `defer x.Close()` の errcheck 指摘が「8 件」と表示されたが、実体は 18 箇所
あった。golangci-lint は `max-same-issues`（既定 3）で同一テキストの指摘を、
`max-issues-per-linter`（既定 50）で linter ごとの件数を打ち切る。受信者名ごとに
3 件ずつ出ていたため、表示分だけ直して再実行すると次の 3 件が「新たに」現れる。

**適用方法:**
- 一括修正の前に `golangci-lint run --max-same-issues 0 --max-issues-per-linter 0 ./...`
  で全件を出し、件数を把握してから機械的に直す（正規表現で
  `defer x.Close()` → `defer func() { _ = x.Close() }()` 等）。
- 同型の指摘が 1 件でも見えたら、その型で全ファイルを grep する。表示件数は下限で
  あって全数ではない。

### フィクスチャ向け E2E スクリプトは、引数が空でも自分のリポジトリで走らない形にする

**事象:** E2E スクリプトを unquoted heredoc（`<<EOF`）で生成したため、本文中の
`$1`/`$P` が生成時に空文字へ展開された。スクリプトは `cd ""`（no-op）の後に
`printf ... > AGENTS.md` を実行し、カレントだったリポジトリの `AGENTS.md`（700 行）を
2 行のフィクスチャで上書きした。機能コミットに混入し、レビューで初めて見つかった。

**なぜ:** 「フィクスチャに向いている」はスクリプトの前提であって、スクリプトが確認して
いる事実ではない。引数が空になる経路（heredoc の展開・呼び出しミス）はいくつもあり、
空引数の `cd` は失敗せず何もしない。

**適用方法:**
- スクリプトは `set -u` で始め、対象ディレクトリを**パターンで検証**してから動く
  （`case "$P" in */scratchpad/e2e-*) ;; *) exit 1;; esac`）。`cd "$P" || exit 1` だけ
  では空引数を止められない。
- 生成側は quoted heredoc（`<<'EOF'`）か python の raw 文字列で書き、生成物を一度
  `cat` して `$` が残っていることを確認する。
- エージェント向け説明ファイル（`AGENTS.md` 等）は**必須セクションの存在を `make check`
  で固定**する。無くなった瞬間に検査が落ちる方が、レビューで気づくより早い。
- コミット前に `git diff --stat` を見る。文書ファイルの数百行削除は、意図した変更では
  まず起きない信号。


## 別プラットフォーム用のテストハーネスは、最初に自分自身の欠陥を検出する

**事象:** macOS/arm64 の開発機から Linux 用テストをコンテナで走らせるハーネスを作り、
GOOS 分岐を持つ 21 リポに当てた。5 リポが「macOS では通るが Linux で失敗」と出たが、
そのうち 3 件はハーネス側の既定値が原因だった。

- ローカルに残っていた amd64 イメージが暗黙に選ばれ、**全リポが qemu 上で走っていた**。
  警告は `image platform (linux/amd64) does not match` の 1 行だけで、症状は
  `qemu: uncaught target signal 11 (Segmentation fault)` — 本物のクラッシュに見える。
- コンテナ内は root なので **DAC を素通り**する。`chmod 0500` で書き込み不能を作り警告が
  出ることを期待するテストが、「書けてしまう」ために失敗した。
- 公式 golang イメージは `GOTOOLCHAIN=local` 固定で、go.mod がより新しい Go を要求する
  リポが「Linux で落ちる」形で現れた。

**なぜ:** 3 つとも「黙って別のことをする」既定値であり、**ハーネス自身の誤りは対象コードの
欠陥とまったく同じ顔で出る**。差分が出た時点で「別プラットフォーム固有のバグを見つけた」と
読んでしまい、実在しないバグを追うことになる。

**適用方法:**
- `--platform linux/<arch>` を明示する。アーキの取り違えは警告 1 行しか出さない。
- rootless podman なら `--userns=keep-id` で呼び出しユーザとして走らせる。**権限に依存する
  テストは root では意味を持たない**。
- `GOTOOLCHAIN=auto` を渡す。イメージの Go 版で go.mod を判定させない。
- **両プラットフォームで走らせて差分を取る形にする。** 片側だけだとハーネスの欠陥が対象の
  欠陥に見える。ハーネスの誤りは「多数のリポで一斉に失敗」として出るので、差分の広さが
  最初の判定材料になる。
- 差分が出たら反復して揺らぎを測る。1 回の実行で「そのプラットフォーム固有」と断じない。
  実例では残った 2 件が 5 回中 3 回失敗と 3 回中 3 回失敗で、競合と決定的欠陥という別物だった。
- ビルド/モジュールキャッシュは bind mount ではなく名前付き volume に置く。virtiofs 上は
  遅く、unix socket も通らない。
- qemu のコアダンプは bind mount したソースツリーに落ちる（1 個 100MB 超）。実行後に作業
  ツリーが汚れていないか確認する。


### 独立検証は「直した直後」に本物を出す — 修正の場所が次の欠陥の場所

**事象:** CLI エージェント（2026-09）の 1 リリース（68 ファイル・ADR 3 本）で、
リリース前の独立検証を全面 5 回＋絞り 1 回回した。**毎回、前回の修正が持ち込んだ**
本物の欠陥が出た: 「除外設定が保存されない」を直したら「サーバーを再度オンにすると
手書きの除外が消える」（修正で導入したリストが原因）、それを直したら「設定パネルが
古い値を出す」、そこで足した 1 行が「4 状態のうち 2 状態で誤る」。並行して ADR の
断定文 14 件が偽だった — 存在しないコマンド名、実装していない永続化モデル、やって
いない作業を Consequences に列挙、「生成物がバナーを見せる」と書いて見せていない。

**なぜ:** 修正は検証済みの領域を直すのではなく、**新しい面を作る**。その面はまだ誰も
見ていない。文書の断定文は書いた本人には疑えず、本人の読了は防壁にならない。レビュー中
にツリーを触ると、レビュワーは動く対象を再検証する羽目になり、指摘が「もう直っている」
と「まだ」の混在になって次パスの精度が落ちる。一方で severity は単調に下がった
（機能破綻 → データ喪失 → 表示の陳腐化 → 特定状態の文言）。これが収束の証拠であり、
「もう 1 回全面」か「絞って終える」かを決める材料になる。

**適用方法:**
- レビュー brief に「**前回の修正が何を持ち込んだか**」を明示的に問う。修正コミットを
  「直したと仮定された変更」ではなく、変更そのものとして読ませる。
- ADR・README・CHANGELOG の断定文を**コミット前に機械照合する**: 名指された
  `/command`・サブコマンド・`[section].key`・型名・`$ENV` をソースに grep（当該
  リリースで 138 件）。ただしそれは名前の存在しか見ない — 「X は Y を見せる」の意味は
  レビュワーに「名前があるかではなく意味が合うか」として課す。
- 機械照合を通すために名前を置換するとき、**置換先が同じ事実を運ぶか**を問う。存在
  しないコマンド名を「存在するが事実を運ばない」コマンドに替えれば、照合は通り意味は
  偽になる。
- **レビュー実行中はツリーに触らない。** 指摘が返るまで待ち、まとめて直し、次のパスに
  回す。
- 収束判定は **severity の推移**で。最悪指摘が「特定状態の文言」まで降りたら、次は
  最後のコミットだけに絞った短いパス 1 本 → 出なければタグ。
- 操作者向け文言は**モード中立**に。対話 TUI・非対話 REPL・one-shot のどれかで偽になる
  語（「尋ねる」「フッタ」「`/auto`」）は、全モードで真の語（「ゲートされる」）に置き換える。
  文言欠陥のうち再発したのはすべてこの形だった。

## 手で 1 回しか動かさないゲートには、ゲート自身のテストが要る

**事象:** リリース検証ターゲットが、展開失敗と起動失敗を吸収したまま「OK」を出す状態で出荷
されていた。そのターゲットの直上のコメントには、過去に「公証プローブが fail open して未公証の
zip が緑のまま出荷された」事故が記録されていた。同じ形が、その次の行で繰り返されていた。

**なぜ:** ゲートはリリース時に人が 1 回動かすだけで、しかも通常は**正常な入力**しか与えられ
ない。異常入力で試す機会が構造的に無いので、壊れても緑のままになる。事故を記録しても、記録
自体はゲートを試さない。

**適用方法:** ゲートに対する自己テストを書き、常用の検査（`make check` など）に組み込む。合成
した不正な入力 — 壊れた成果物、起動しないバイナリ、別バージョンの成果物、マーカー欠落 — を
与えて**非ゼロ終了することを検査する**。正常な入力も 1 件入れる: 何でも落とすゲートを「動いて
いる」と誤認しないため。そして修正前のゲートに対して自己テストを走らせ、実際に取りこぼしを
報告することを確認してから採用する。

### モデル比較ベンチは構成をケース毎に交互実行し、コール毎にタイムアウトし、進捗を即時出力する

**事象:** 同じモデルに 3 つの thinking 構成を並列で当てたら互いに絞り合い、中央値が
本番実測の 4 秒に対して 30 秒超になって比較にならなかった。逐次実行に変えたら 1 コール
が 515 秒ストールして全体の 25 分予算を食い潰し、4 構成中 3 構成がデータゼロで終わった。
出力は `t.Log` にバッファされていて、25 分間なにも見えなかった（2026-09、エージェント
ランタイムのリスク評価モデル選定）。

**なぜ:** API 側の状態（混雑・再試行・ストール）は分単位で変わる。構成ごとにまとめて
走らせると、構成間の差に時間帯の差が混入する。全体タイムアウトだけだと 1 件のストール
が残り全部を道連れにする。バッファ出力は「終わらない」と「壊れている」を区別させない。

**適用方法:**
- **ケースを外側、構成を内側**にして交互実行する。時間帯の変動が全構成に等しく当たる。
- **コール毎に `context.WithTimeout`**（例: 90 秒）を切り、ストールは 1 件の ERR として
  記録して次へ進む。全体の deadline はその上に置く。
- 判定行を**その場で `fmt.Printf`**（タイムスタンプ付き）し、`t.Log` は末尾の要約にだけ
  使う。`go test -v` は終了までログを出さない。
- 同一モデルへの並列は避ける。並列化するなら別モデル同士に限る。
- 集計は決定単位（複数ラウンドを 1 判定に）と per-call の両方を出し、再試行回数も数える。

### inline TUI の行計算は tmux と script で実測する — レンダラーはティック毎に最新の View しか描かない

**事象:** Bubble Tea の inline レンダラーで、パネルを閉じた後に古い出力が 1 行だけ画面
最上段に残った。理屈で追った 2 度の修正（フレームを height-1 に詰める／View 毎に
残り行数から配置を決める）はユニットテストを通ったが実機では効かなかった。
`tmux new-session -d -x 100 -y 30` で既知サイズの擬似端末を作り、`send-keys` で操作、
`capture-pane -p` で画面を取り、さらに `script` で生バイト列を録って判明: ①printed+1
行目から N 行のフレームを描くと端末は printed+N−height 行しかスクロールしない
（height-1 行では 1 行残る）。②レンダラーは Update 毎の View を溜め、ティック時に
最新の 1 枚だけ描く — 全高フレームがカウンタを修復した直後の次の View で配置判定が
反転し、端末に届いたのは反転後の短いフレームだった（2026-09、エージェントの TUI）。

**なぜ:** モデル内の行会計は「自分が返した View」を前提にするが、描かれる View は
その後の Update に上書きされうる。View 毎に再導出する状態は、修復のような自己参照の
更新があると発散する。ユニットテストは View の戻り値しか見ないので、この差を検出
できない。

**適用方法:**
- 行位置・スクロール量に関わる修正は**実機で数える**: tmux（サイズ固定・
  `capture-pane`）と `script`（生バイト。`<CSI nA>` の戻り行数と `\r\n` の数を数える）。
  スクリーンショットの目視は最後。
- レイアウトの選択（全画面／残り行に収める等）は**開いた時に 1 度決めて閉じるまで
  保持**する。View 内でカウンタから再導出しない。
- 「モデルが返した行数」のトレースは描画の証拠にならない。描かれたかは生バイトで
  確かめる。

### inline TUI で N 行を占めるものは、自分の下を消してから描く — レンダラーの掃き出しは 1 行しか消さない

**事象:** inline TUI に端末インライン画像を実装し、行数会計は正しかった（宣言した行数
を行カウンタに告げる設計で、テストも通る）。それでも実機の端末で画像 3 枚に対しフッタ
の残骸が 3 個、画面に残った。ユニットテストも、ソースを読む独立検証パス 4 本も、これを
見つけられなかった（2026-09、エージェントの TUI）。

**なぜ:** Bubble Tea の inline レンダラーはキューに積まれた行を自分のフレームの先頭から
吐き、`EraseLineRight` を付ける。消えるのは**カーソル行の右側 1 行だけ**である。画像は
そこから宣言した幅で N 行下へ描かれるので、画像より右にある旧フレームのセルは、画像が
覆う全ての行で生き残る。画像が 40 桁、フッタがそれより広ければ、差分の桁が全行に残る。
行数の会計とは独立した欠陥であり、会計が完全に正しくても起きる。

**適用方法:**
- inline レンダラーの下で**複数行を占める出力**（画像・sixel・自前の箱）は、ペイロード
  の直前に画面末尾までの消去（`ESC[J` 相当）を 1 つ置く。カーソルより上は触らない。
  レンダラーはそのすぐ下を描き直すので、消しても失われるものは無い。
- 「行数さえ合っていれば画面は合う」は成り立たない。**幅**も宣言した分だけ占有され、
  消去は行単位で行われるからである。
- このクラスは**実機でしか判定できない**。ソースを読む検証パスは何本当てても届かない。
  実機で A/B（修正あり／修正を 1 行だけ外したツリー）を同条件で撮り、残骸の個数を数える。

### 端末の能力プローブは「どの端末も必ず答える質問」を併せて投げる

**事象:** 端末がインライン画像を描けるかを APC のグラフィックスクエリで問い、答えが
無ければタイムアウトで「不可」と判定していた。Apple Terminal では**毎起動 2.001 秒**
止まり、さらに APC を解さない端末はクエリ本文をそのまま印字するので、画面に
`Gi=31,s=1,v=1,a=q,t=d,f=24;AAAA` のような文字列が残った（2026-09、エージェントの TUI。
環境変数で分類できるのは tmux/screen・kitty 系・iTerm2 だけで、残りは全てこの経路）。

**なぜ:** そのクエリには**否定の答えが無い**。知らない端末は黙るだけで、沈黙は「遅い」
と区別できない。判定に使える事象がタイムアウトしかないので、描けない端末が必ず全予算を
払う。

**適用方法:**
- 能力クエリの直後に **DA1（`ESC[c`）** を続けて送る。VT 互換の端末はこれには必ず答える
  ので、「グラフィックスの返答が無いまま DA1 が来た」ことが確定的な否定になる。実測で
  2.001 秒 → 1ms 未満。タイムアウトは「どちらにも答えない端末」用の保険として残す。
- エスケープを解さない端末は**本文を印字する**。プローブの後に自分が汚した行を消してから
  UI に渡す（`\r` + 行消去）。
- 効果は**同じ計器で前後を測って**記録する。プローブの所要時間と画面の汚れは、どちらも
  実機でしか測れない。

## 一度の観測を規則として書かない — 回数付きで書く

**事象:** 検索 API の回答で「言語が ja だと引用が返らない」を 2 回観測して
「引用は `language=en` のときだけ返る」と README・マニュアル・結果への注記に
断定で書いた。3 回目の ja で 24 件返った。5 回の内訳は en → 29, 29 / ja → 0, 0, 24。

**なぜ:** 2 回の一致は規則に見える。しかも「原因の切り分け」（国か言語か）を
1 回ずつ変えて確かめた分、確信が増した。だが観測は非決定的な系（LLM を挟む API）
に対するもので、2 回はサンプルとして小さすぎた。断定はマニュアルと結果の注記
（利用者が読む面）まで一気に広がり、訂正も同じ面すべてに要った。

**適用方法:**
- 非決定的な系（LLM・検索・外部サービスの応答内容）の観測は、**回数と内訳を
  そのまま書く**（「5 回: en 29, 29 / ja 0, 0, 24」）。「〜のときだけ」「常に」は
  同じ入力で 10 回以上一致してから。
- 利用者向けの文言は観測に忠実な形にする（「非英語では不安定」）。結果に付ける
  注記も同様で、空の値を「存在しない」と読ませない一文を添える。
- 切り分け実験（変数を 1 つずつ変える）は原因の候補を絞るが、**規則を証明しない**。
  切り分けが済んだ後にこそ、同条件の反復が要る。
- 断定を訂正するときは、断定を書いた全ての面（README・マニュアル・結果の注記・
  ADR・CHANGELOG）を機械的に grep して一括で直す。1 面だけ直すと drift になる。

### 新しい境界を足したら、本物を本物の檻で駆動するテストを同時に書く — スタブと権限シミュレーションは本番が壊れたまま通る

**症状:** ファイルツールの読取を、資格情報を deny した専用プロファイルの子プロセスへ移した。ユニットテストも `make check` も全緑で出荷し、独立検証が実測で Critical を出した。**`.env` が 1 つあるだけで `search_files` が "no matches (0 files scanned)" を返していた**（例外も警告も無い偽陰性）。同じ検証で High が 4 件続いた。読取が無言で 85KB に切れる、`file_info` が権限エラーを「not found」に潰す、中断時に部分結果が消える、約束した注記が到達不能、である。

**原因:** テストが**本物を駆動していなかった**。子プロセスは全てスタブ（`SetFileChild` に関数を差す）で、カーネルの拒否は `chmod 000` で代用していた。`chmod 000` は `open` を拒むが `lstat` は通す。Seatbelt の `file-read*` は両方を拒む。その 1 点の差が欠陥の正体で、代用テストは本番が通らない経路を固定していた。カーネル側のテストも `/bin/bash` 経由で、実際に走る Go の子を一度も動かしていなかった。起動時プローブも同じくシェルを検証していたので、walk が全滅している間ずっと緑だった。

**適用:**
- 新しい境界（サンドボックス・別プロセス・別権限）を足したら、**その境界を通る本番の成果物を、本番の境界設定で駆動するテスト**を同じコミットで書く。ビルドしたバイナリを実際のプロファイル下で起こし、実際の要求を流す。遅くてよい（ここでは 2〜4 秒）。
- **権限の代用を疑う。** `chmod`・`root` で走らない・ネットワーク切断は、カーネルの deny と**別の操作集合**を拒む。代用でテストを書くなら、代用と本物の差分を 1 行で書けるか自問する。書けないなら代用は使えない。
- **起動時プローブは、ランタイムが実際に行う操作で検証する。** 別のプロセス・別のプロファイル・別のライブラリで検証したプローブは、緑のまま本番の破綻を通す。プローブが「一覧」も含めて本番の一連の操作をなぞること。
- **境界を「有効化する経路」も本番の形で通す。** 同じ設計の次のリリースで、本物を本物の檻で駆動するテストは書いたのに、その檻を**インストールする関数**を一度も通していなかった。プローブが対象外のツールを子に要求していたため、プローブは毎回失敗し、檻は一度もインストールされず、機能全体が無効のまま出荷された。テストは「境界の中で正しく振る舞うか」だけでなく「境界がそもそも入るか」を固定する。後者はインストーラ・配線・起動時検証という、本番にしか無い 1 本の経路である。
- スタブを使うテストには、それが**本番の経路ではない**と明記し、本番を覆うテストの名前を書く。

関連: 「独立検証は『直した直後』に本物を出す」。修正が新しい面を作るのと同じ理屈で、**新しい境界はその瞬間が最も未検証**である。

### 「全ての N に適用する」と設計文書に書いたら、N を数え上げるテストを同じコミットで書く

**事象:** エージェントランタイムの ADR に「関数 1 つを**全ての spawn 地点**に適用するので、子プロセスを足したときに規則を継がないことが起きない」と書いた。規則は「ランタイム自身の設定変数（API キーを含む）を子に渡さない」。ビルドは green で、名前空間の分割を固定する AST テストも通っていた。実際には 4 種類の子が規則を通っていなかった。サンドボックスを無効化した起動のシェル（ここに API キーが届いていた）、起動時の検証プローブ 2 種、クリップボード取得である。半年後ではなく、その ADR を書いた当日に別作業で見つかった。

**なぜ:** 既存のテストが固定していたのは**名前の一覧**（どの変数が「自分のもの」でどれが「子に渡すもの」か）であって、**適用地点の網羅**ではない。名前の分割はいくら厳密でも、その関数を呼び忘れた `exec.Command` を 1 つも見ない。設計文書の「全ての X」は、書いた人が当時知っていた X の集合を指しているだけで、コードの中の X 全部を指していない。両者は書いた瞬間から乖離する。

**適用方法:**
- 設計文書に「全ての X に適用する」「X は必ず Y を通る」と書いたら、**X を列挙して Y を確かめるテスト**を同じコミットに入れる。書けないなら、その文は「今のところそうなっている」と弱める。
- テストは AST で書く。`exec.Command` を組み立てる関数がヘルパを名指していなければ落とす、パスを開くパッケージが `os.Open` を直に呼んでいれば落とす、といった形で**クラスごと**閉じる。個々の地点を allowlist で数え上げる形にするなら、**使われていない allowlist 項目も失敗**させる（消えた地点が残骸として残らない）。
- 例外は必ずコードの中に理由付きで書く。上の例では、ランタイムを**起動する側**のベンチハーネスが正当な例外だった（親であって子ではない）。除外はディレクトリ名ではなく理由で選ぶ。
- 修正のとき、直した直後に**その修正を打ち消す行**が無いか見る。上の例では、プローブに規則を足した 2 行下で、一時ディレクトリを設定するために環境を親から組み直しており、放置すれば同じコミットで修正が消えていた。

関連: 「境界を『有効化する経路』も本番の形で通す」。あちらは境界が入るかを、こちらは境界が**全部の入口に**入るかを固定する。

### 撤回した機構は、コードから消しても**文面**からは消えない — モデルが読む文字列を照合するテストを書く

**事象:** ファイル媒介の結果返却を 2 サーバーから撤去してリリースした。実装もスキーマも
テストも正しく、`work_dir` の綴りを固定する arch テストまで通っていた。それでもリリース
された成果物は、`run_query` の **Description** で「大きい結果は workspace_root の下に JSONL
で書く」とモデルに言い、`get_usage` のエラー表では「workspace_root を付けて再試行するか
inline_row_threshold を上げろ」と勧めていた — どちらもサーバーが拒否する操作である。
別サーバーでは `describe_runtime` が返すコンテナ manifest が「結果は /work 下のファイル」と
言い続け、さらに別のサーバーではセットアップ手順書が削除済みの config キーを「ここに書け」と
案内していた。同じ掃討で、スキーマが `work_dir` を**任意**と宣言したままハンドラが必須に
していたサーバーも出た（モデルは省略してよいと読み、呼び出しは落ちる）。

**なぜ:** arch テストが固定していたのは**識別子**（スキーマの中の綴り、`required` の有無）で
あって、**その隣の文**ではない。文章はコンパイルされない: 型も参照も無いので、機構を消しても
それを説明する段落は何事もなく残り、grep する動機も生まれない。しかも MCP では、その段落は
コメントではなく**製品の一部**である — `tools/list` の Description、`get_usage` の本文、
`describe_runtime` の manifest はモデルが読んで従う入力であり、嘘があれば実際に誤った呼び出しに
なる。さらに build tag 付きのテスト（`integration` / `e2e`）は `go test ./...` がそもそも
**コンパイルしない**ので、撤去で消えたフィールドを参照したまま何か月も壊れて残る。

**適用方法:**
- 機構を撤回したら、**廃止語の一覧**を作り、モデルが読む文字列全部（各ツールの Description と
  InputSchema、usage 本文、ランタイム manifest）を走査して落ちるテストを同じコミットで書く。
  一覧は 1 つだけ持ち、スキーマ用と文章用に分けない。
- スキーマ側は識別子だけでなく**契約の形**も固定する: 「`work_dir` を宣言しているツールは
  必ず `required` に入れる」。任意の必須引数は、モデルにとっては「既定値がある」の意味になる。
- `make test` に `go vet -tags <各タグ> ./...` を足す。タグ付きスイートは実行できなくても
  **型検査はできる**。実行が実機依存であることと、コンパイルされないまま腐ってよいことは別。
- 撤回の掃討範囲は「コード」ではなく「**利用者とモデルが読む面**」で数える。チェックリスト:
  `initialize` の `instructions`（モデルが最初に読む面。`tools/list` より前に届く）、serverInfo、
  各ツールの Description と InputSchema、usage 本文、ランタイム manifest、エラーの message と
  details、`--help`、README（**全言語**）、セットアップ手順、設定例、RFP、そして**同梱して
  配布する skill / プロンプト**。最後の 2 つは特に見落としやすい: skill はエージェントの
  スキルディレクトリに**インストールされて指示として読まれる**ので、そこに残った旧引数名は
  ドキュメントの瑕疵ではなく「サーバーが拒否する呼び出しをエージェントに命じている」状態である。
  README の片方の言語だけ直すのも最頻の漏れ。
- 既存テストが「**在るか**」ばかりを見ていないか確認する。同梱 skill のテストが「必要なツール名が
  全部書かれているか」だけを見ていたため、廃止語が 8 ファイルに残っても誰も落ちなかった。
  撤回では **absence のテスト**が要る。
- 過去の設計文書（RFP など）は書き換えずに、撤回を**打ち消し線＋日付＋後継**で注記する。履歴を
  正しく保ったまま、現行仕様として読まれるのを止められる。

関連: 「『全ての N に適用する』と設計文書に書いたら、N を数え上げるテストを同じコミットで書く」。
あちらは適用地点の網羅を、こちらは**説明文**の網羅を固定する。

### WebKit の許可境界は実際のコールバックで検証する

**事象:** macOS クライアントの移植で、JavaScript の自動遷移がクリック相当のメタデータを返した。
また、認証 delegate と似た名前の非同期メソッドはコンパイルできたが、証明書問い合わせが届かなかった。

**なぜ:** WebKit の navigation type / button number は人による接続承認を証明しない。
Objective-C の optional delegate に似た独自メソッドを定義しても、プロトコル実装漏れとしてはエラーにならない。
HTTP redirect の Cookie や証明書検証は、単独の条件関数だけを試験しても呼び出し経路の欠落を検出できない。

**適用方法:** Web から native への接続などの権限は、変更不能な接続候補を表示するネイティブ確認で一度だけ消費する。
一時的な HTTPS サーバーと本物の WKWebView を使い、自動 location 変更、form POST、リダイレクト後の
受信 Cookie、証明書問い合わせ、キャンセル後の承認再利用まで検証する。証明書はテスト内でだけ信頼し、
システムの信頼ストアを変更しない。SDK の async delegate 名を確認し、コンパイル成功を callback 到達の証拠にしない。
並列の依存テストで共有 fixture が停止した場合は、失敗を削除せず順次実行して切り分ける。

出典: spice-client の移植・シミュレーション検証（2026-09）。

## 区間を境界で切る判定は「跨ぐ」だけでなく「境目に接する」を含める — 取りこぼしは位相依存で潜伏する

**事象:** 操作時間を論理日（例: 05:00 起点）へ帰属させる集計で、日境界の切断を
`seg.Start < 境界 && 境界 < seg.End`（境界を跨ぐ区間）だけで判定していた。区間列は
連続しているので、状態変化やギャップ分割がちょうど正時に着地すると、**どの区間も
境界を跨がない**。切断は起きず、しかも次の境界値は「未設定のときだけ再計算」する
設計だったため、**到達済みの境界が limit に居座り、以降の境界も全て素通り**した。
結果、日跨ぎのセッションが次の長時間離席まで伸び、その日の集計が 0 になる。新機能
だけでなく、既にリリース済みの「セッションは 2 日以内」という上限も同じ経路で
無効化されていた。

**なぜ気付けなかったか:** 発火条件はサンプリング周期の**位相**（`unix % interval == 0`
になるか）で決まる。テストは 1 つの位相でしか書いておらず、実運用の数週間分の履歴でも条件を満たすサンプルがほぼ皆無で、無症状のままだった。デーモンを再起動する
たびに位相は振り直されるので、「今は出ていない」は「出ない」ではない。コードを読む
検証パスも、述語が「跨ぐ」だけを見ていることを欠陥として認識しなかった。

**適用方法:**
- 区間列を境界で切る述語は **2 本立て**にする。「境界を跨ぐ区間」に加えて
  「境界**以降**で始まる区間」（`!start.Before(limit)`）でも切る。連続する区間列では
  後者が本命で、前者だけでは境目一致を必ず取りこぼす。
- 「条件が満たされるまで保持する値」（limit・次回期限・次の境界）には、
  **取りこぼしたときに自己回復するか**を必ず問う。回復しないなら、その値を進める
  経路を判定と同じ場所に置く。1 回の取りこぼしが恒久的な機能停止になる。
- この欠陥クラスのテストは **step と開始オフセット（位相）をテーブルで振る**。
  単一の位相で書いたテストは、構造的にこの種の欠陥を検出できない。
- 時刻境界を実時刻の「時」で定義したら、**夏時間で論理日が 23/25 時間になる**。
  「24 時間を超えない」と書く前に跨ぐ日のテストを 1 本書き、秒が保存されることと
  境界がどこに落ちるかを実測してから文書にする。

## ビューの描画コールバックで増えるカウンタは、ヘッドレスのテストでは何も証明しない

**何が起きたか:** SPICE クライアントの実ピアゲートが、実サーバーがフレームを送り始めたら
セッションの診断値 `frames_presented` が増えることを assert した。初回の実走は 30 秒待って
失敗した。そのカウンタは Metal ビューの drawable コールバックで増えるもので、`swift test` の
プロセスにはビューが無い。フレームは届いていたが、数える者が居なかった。設計レビューは実走が
再現する前にソースからこれを予言していた（spice-client ADR-0002、2026-09-18）。

**適用方法:** ヘッドレスのテストでは、ビューが報告するものではなく、ビューが観測するものを
観測する。可視ウィンドウが設定するのと同じ要求でフレーム源を購読し、異なるリビジョンを数える。
ゲートが assert するすべてのカウンタに同じ監査をする。それを増やす唯一の呼び出し箇所を見つけ、
そのコードがテストプロセスでそもそも走るかを問う。加えて、環境変数で有効になるスイートは、
変数が無ければスイートをスキップしたまま `swift test` が 0 で終わる。終了ステータスだけを
信じるゲートはテスト 0 件で通るので、テストに受領証を残させてゲートがそれを検査する。

## 同時 1 クライアントのサーバーは、並列のテストスイートを flake に変える

**何が起きたか:** 実ピアのゲートに 2 本目のスイートを足した。両スイートは同じ QEMU の SPICE
サーバーを駆動し、`swift test` はスイートを並列に走らせる。接続が失敗し始め、フレーム観測が飢え、
失敗する箇所が実行ごとに移動した。どちらのスイートにも問題は無かった。QEMU の SPICE サーバーは
同時に 1 クライアントしか扱わず、2 本がそれを奪い合っていた（spice-client、2026-09-18）。

**適用方法:** 共有する実フィクスチャに 2 本目のスイートを足す前に、そのフィクスチャが同時に何
クライアントを扱うかを問う。答えが 1 なら、各スイートの `.serialized` では足りない。あれはスイート内
だけを直列化する。テストランナーを別々に逐次起動するしかない。それだけがランナーに覆されない。
見分ける症状は、単独では通るのに、実行ごとに失敗する箇所が移動することである。

## 直さない欠陥は「検査される事実」として固定する。直った日にゲートが赤くなるように

**何が起きたか:** 実ゲートが製品の欠陥を見つけた。最初のビューポートリサイズ以降、同じエージェント
接続では以後のリサイズがゲストに届かない。修正には vendored 依存のパッチ範囲を広げる必要があり、
その範囲は ADR が意図して絞っていたので、この変更で決めることではなかった。assert を落とせば、
直った日に気づく仕掛けが何も残らない（spice-client、2026-09-18）。

**適用方法:** 欠陥そのものを assert にする。ゲートは 1 回目のモードが適用されることを要求し、
2 回目のモードが**現れない**ことを要求する。メッセージには「現れたら欠陥は直っている。テストと記録を
更新せよ」と書く。こう固定した欠陥はどちらの向きにも静かに腐れない。悪化すれば落ち、直っても
記録が古いままなら落ちる。これが「直さなかったことを記録する」の機械検査側の半分である。

## クレジット制のチャネルで「きりのよい数値」で止まったら、窓の問題であってデータ処理の不具合ではない

**事象:** ゲスト側エージェントへのファイル送信が、毎回ちょうど 64,000 バイト中
32,000 バイトで停止した。部分ファイルの内容は正しく、エラーも切断も起きない。
ただ進まなくなる。チャンク長は既定の 16,000 バイトだった。

**なぜ:** そのチャネルはトークン（クレジット）によるフロー制御下にあった。メッセージは
ワイヤ上の 2 KiB 断片ごとにトークンを 1 個消費し、相手はトークンを 10 個与えて
5 個ずつ返す。16,000 バイトのチャンクは 8 個必要である。1 つ目は 10 個から 8 個を使って
2 個残し、返却の 5 個が来て 7 個になる。2 つ目には 8 個必要なので、永久に足りない。
停止位置が毎回同じ「きりのよい数値」なのは、それがデータの性質ではなく窓の算術で
決まっているからである。バイト処理やバッファ境界を疑うと、正しいコードをいくら読んでも
何も見つからない。

**適用方法:**

- 停止位置が実行ごとに一定で、かつチャンク長の整数倍なら、まずフロー制御を疑う。
  データ依存の不具合なら停止位置は内容によって動く。
- クレジットの実測を最初に取る。初期トークン数、消費単位、返却の粒度をログに出す。
  これは 3 つの数値で、どれも仕様書より実装のログの方が速く確実である。
- チャンク長は「大きいほど速い」ではなく、**相手が一度に開ける窓に収まる**ように選ぶ。
  1 メッセージが初期クレジットの半分を超えるなら、2 通目は必ず詰まる。
- 依存ライブラリの既定値は、その依存が想定した相手の窓に対する既定値である。別の相手
  （別のハイパーバイザ、別のサーバー実装）に繋いだ時点で、既定値は前提ごと無効になる。
  こちらのアプリケーションの数値として明示的に渡し、根拠を残す。

## 書き手が領域を先取りする相手に、サイズの安定を完了判定に使ってはいけない

**事象:** 転送されたファイルの受領をゲスト側で観測するのに、「サイズが 2 秒間変化しなく
なったらハッシュを取る」という監視を書いた。部分ファイルのハッシュが返ってきた。

**なぜ:** 受信側の常駐プロセスは、最初のバイトが届く前にファイル全体の大きさを確保して
いた。したがって受信途中のファイルも既に最終サイズを持っており、「サイズが安定した」は
転送開始の直後から常に真である。判定として何も言っていない。

**適用方法:** 書き込みの進行を表す量で判定する。更新時刻（mtime）の安定は、
先取り確保の影響を受けない。必ず併せて、

- **必ず 1 行出す強い期限**を置く。無音は「まだ書いている」と「もう来ない」を区別
  しないので、観測側が黙ると検証側は待つしかなくなる。
- 相手がファイルを**消した**場合の行も出す。転送の完了処理でテンポラリを片付ける実装は
  珍しくなく、消えたファイルは沈黙ではなく報告された結果にする。
- 完了の証拠は、受け取った側が計算したダイジェストにする。送信側の「成功しました」は
  送信側の状態でしかない。

## 観測している層を名指しできないゲートは、その 1 つ下の層しか証明していない

**事象:** 実ピアのゲートは「注入したキーがゲストに届く」ことを毎回検証しており、ずっと合格して
いた。ある日ゲストにデスクトップを表示させて人が触ったところ、**端末に 1 文字も入力できなかった。**

**なぜ:** そのテストはゲストの `/dev/input/event*` を直接読んでいた。キーは確かにゲストの
カーネルまで届いている。しかしゲストの X サーバーには入力ドライバも udev も無く、入力デバイスを
0 個で起動していた。つまり X クライアントには一文字も届いていなかった。テストが証明していたのは
「カーネルまで届く」であり、利用者が体験する「アプリケーションに届く」ではなかった。両者の間に
丸ごと 1 層あり、その層はゲートの寿命の間ずっと壊れていた。

観測点を 1 つ下に置くのは、たいてい実装が楽だからそうなる。生の入力イベントは読みやすく、
X クライアントの受信を観測するには別のプログラムが要る。**楽な観測点は、たいてい本物より下にある。**

**適用方法:**

- テストごとに「これは何層目を証明しているか」を書く。書けないなら、その検証は範囲が不明である。
- 利用者が体験する層と観測する層がずれるなら、**ずれを埋める検査を足す**。全部を上の層で観測
  できなくてよい。今回は「X が入力デバイスを 2 個以上取ったこと」をゲストのログに出して要求する
  検査を足した。キーの到達そのものは下の層のままだが、間の層が消えたら落ちる。
- 「ずっと合格している検査」は、正しさの証拠であると同時に、**何も見ていない可能性の証拠**でもある。
  一度も落ちたことがない検査は、わざと壊して落ちることを確かめる。
- 表示や入力のように人が体験する経路は、**一度は人が見る**。今回の 2 件はどちらも、自動化された
  検証が全て緑のまま、人が画面を見た最初の日に見つかった。
- **観測者は、観測すべき事象より先に走っていなければならない。** 観測点を上げた直後に踏んだ罠で、
  X のキー観測を「準備完了」マーカーの後ろで起動したところ、テストのキー注入が先に届いて取りこぼした。
  観測者はそのマーカーの前に起動し、走っていることを確認してからマーカーを出す。

## トレースの照合スクリプトが、直っている修正を「壊れている」と判定する

**症状:** GUI の不具合を直し、実機のイベントトレース（マウス押下・action・メニューの開閉・設定の
変更をミリ秒単位で記録）で確認した。照合スクリプトは 1 日に 2 回、正しく動いている修正を失敗と
判定した。1 回目は「58 クリック中 29 回が効いていない」、2 回目は「7 回の選択のうち 5 回が消えた」。
どちらも、使っていた本人は「問題なさそう」と言っていた。（net-meter、2026-09）

**なぜ:** どちらも、記録の**順序についての思い込み**だった。

- 1 回目: 記録用のモニタは、アプリ自身のモニタの**後**に呼ばれる。閉じるクリックについて記録用の
  行が書かれた時点では、パネルはもう閉じている。その行の「表示中か」を「クリック前の状態」と
  読んだため、閉じるクリックが全部「何も起きなかった」に見えた。
- 2 回目: バインディングの setter は、メニュー終了の通知より約 190 ms **前**に走る。スクリプトは
  終了通知の後の行だけを探していた。

生の行を時刻順に読めば、どちらも数分で分かった。

**適用方法:**
- 1 つの物理的な操作は 1 つの識別子（イベント番号など）でまとめ、その操作が**残した状態**
  （マウスアップ時点の状態など）で判定する。記録の行の並びを因果の順序だと仮定しない。
- 「A の後に B が来るはず」という照合を書く前に、生の記録で実際の順序を 1 例確かめる。
- **使った人の観察とスクリプトの判定が食い違ったら、先に生の行を読む。** スクリプトは
  自分が書いたばかりの、どこからもレビューされていないコードである。
- 記録用の仕組みはコンパイル時フラグの中だけに置き、リリースのバイナリに入っていないことを
  **シンボルで**確かめる（`nm <binary> | grep -ci trace` が、リリースで 0、記録版で 25 だった）。
  このエントリは当初 `strings` を勧めていたが、誤りだった: Swift は 15 バイト以下の ASCII 文字列
  リテラルをコードに即値で埋め込むので、`strings` にも `grep -a` にも出ない。記録版のバイナリでも
  0 件になり、「入っていない」の確認として成立していなかった（2026-09-20 訂正）。**不在を確かめる
  検査は、在るはずの対象で一度は陽性になることを先に見る。**

## ガードは複製の上の変異で確かめる — 「捕捉されなかった」には 3 つの型がある

**事象:** 初回から緑のテストが守っているつもりのガードを、1 つずつ壊して確かめた（4 回に分けて
合計 90 本）。大半は捕捉されたが、コンパイルエラーや無限待ちで「落ちただけ」の無効な変異が
混ざった回があり、最後の回では 35 本中 3 本が捕捉されず、それぞれ別の欠陥を指していた: (1) 長い文字列を短縮する安全網が `map[string]any` 直下の文字列に届いていなかった
— **ガード自体の穴**。(2) 巨大な文書をページングするテストが、常に `offset` を付けて呼んでいた
ため、読者が最初にする呼び出し（`offset` 無し = 以前は全文が返った経路）を一度も通っていな
かった — **テストが本物の経路を通っていない**。(3) 出力前の一括無害化を外しても、出力箇所
ごとのエスケープが残っていて出力は無害なままだった — **冗長な機構が欠落を隠していた**。

**なぜ:** 緑のテストは「ガードが在る」ことしか示さない。ガードを外しても緑なら、そのテストは
何も見ていない。読んで確かめても、書いた本人は自分の想定した経路しか辿らない。

**どう適用するか:**
- 変異は**作業ツリーではなく複製**に掛ける。変異ごとに新しい一時ディレクトリへツリーを写し、
  何も削除しない（掃除は後で人が決める）。本物のツリーは一度も触らない。
- 変異が**実際に適用されたこと**をファイルのハッシュで確かめる。パターンが一致しなかった
  変異は「捕捉」ではなく「無効」に数える。
- 失敗は**アサーションの行**で確かめる（`_test.go:NN:` を拾う）。コンパイルエラー、panic、
  タイムアウトで落ちたものは無効 — import が未使用になる変異は import を使い続ける形に
  書き直し、panic で落ちるテストは算術の検査を panic する経路の前に置く。
- ガードは「落ちる」のであって「固まる」のではないこと。偽の時計が進まないせいで無限に待つ
  テストは、暴走の上限を入れて速く落とす。テストには必ずタイムアウトを付ける。
- 捕捉されなかったら、上の 3 型のどれかを判定してから直す: 穴ならガードを直す、経路の
  不一致ならテストを読者の呼び出しに合わせる、冗長なら機構を 1 つに減らす（等価な変異として
  放置しない — どちらが効いているのか読み手に分からなくなる）。
- 直したら全件を流し直す。「捕捉 N / 見逃し 0 / 無効 0」を記録に残す。

## スキップするリリースゲートは、通過するゲートである

**事象:** 一次ソース（政府機関のカタログと標準化団体のスコア）と上流 API の乖離を測る e2e を
リリースゲートにしていたが、一次ソースに到達できないと `t.Skip`、片方を比較できなくても
`t.Log` だけだった。独立検証が指摘するまで、「比較が 0 件でも緑」であることに気付かなかった。
さらに既定の `go test` は通過したテストのログを出さないので、8/8 を比較した実行と、何も
比較しなかった実行が同じ見た目だった。

**なぜ:** スキップは「このテストはこの環境に関係ない」の表明である。ゲートにとって
「確かめられなかった」は関係ないのではなく、**確かめていない**である。fail-open の一種で、
形が `|| true` でないだけである。

**どう適用するか:**
- ゲートとして走らせるテストでは、依存に到達できない・成果物が無い・フィクスチャが意味を
  失った（追跡対象から外れた等）は、いずれも**失敗**にする。メッセージは「実行されなかった」と
  明記する。
- 比較の証跡（何件中何件が一致したか）はログに出し、ゲートのターゲットは証跡が見える形で
  走らせる（`go test -v`）。証跡の見えないゲートは、何も比較しなかったゲートと区別できない。
- ゲート自身の破壊実演を 1 回はやる: 期待値を偽って、実際に落ちることを見る。

## 一次ソースとのドリフト検知は許容幅で書く — 厳密一致は同期ラグで毎回落ちる

**事象:** 集約 API のデータ（KEV 収載、EPSS）が一次ソースと一致し続けるかを e2e で見張る
設計にした。厳密一致で書くと、一次ソースに当日追加された項目と、モデルの日次更新の境目で
必ず落ちる。

**どう適用するか:**
- 許容幅を**同期の仕組みから**決める: 収載は「追加から N 時間を超えた項目」だけを標本にし、
  総数は「N 時間超の件数 ≦ 上流の総数 ≦ 一次ソースの総数」、日次モデルの値は「直近 3 モデル日の
  いずれかと一致」。標本の一定割合（例: 1/4）を超える不一致でだけ落とす。
- 標本は「新しい端」と「古い端」の両方から取る。ラグは新しい端に、腐敗は古い端に出る。
- 落ちたときに問い直す設計判断を、メッセージに書いておく（「一次ソース突合層を不採用と
  した判断を見直せ」）。
- e2e 全体で**1 エンジン = 1 ペーサー**を共有する。テストごとにクライアントを作ると、
  バースト許容がテスト数だけ掛け算になり、IP 単位の上限を踏む。

## 書き込み経路はエスケープを生の文字に変える — ソース全体を検査して閉じる

**事象:** 「上流がエスケープシーケンスを送ってくる」フィクスチャを書くたびに、作者とファイルの
間の経路（エージェントのファイル書き込み / シェル引数のデコード）が、打った
バックスラッシュ + u + 4 桁を**生の文字**に変えた。3 回起きた。1 回目は Go の raw 文字列内の
JSON フィクスチャに生の ESC が入り、不正な JSON になってテストが何も通さず緑になった。
3 回目は、双方向制御文字のテストのソースに生の U+202E が入った — 「Trojan Source」の形
そのものである。警告を書いた文書自身にも生の ESC が入っていた。

**なぜ:** 経路のどこかが JSON 的なアンエスケープを 1 回余計に行う。見た目では分からない
（エディタは制御文字を表示しない）ので、注意では防げない。同型が 3 回出たら構造で閉じる。

**どう適用するか:**
- リポジトリ直下に、全ソース（コード・Markdown・設定・スクリプト）を走査して生の C0（タブと
  改行を除く）・DEL・C1・双方向制御文字・U+FFFD・BOM を拒否するテストを置く。走査した
  ファイル数の下限も assert する（何も見ずに緑にならないため）。
- 落ちたら打ち直さない。コードポイントを `chr()` で組み立てるスクリプトで置換する —
  スクリプト自身にも該当の文字やエスケープを書かない。
- エスケープ入りのフィクスチャは二重引用符の文字列で組み立て、**テキストが届いたこと**を
  先に assert する。壊れたフィクスチャで空振りするテストは、ガードの有無と無関係に緑になる。

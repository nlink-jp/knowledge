# テスト

テスト設計と、ユニットテストでは届かない欠陥をリリース前に捕まえる手法。
各項目は「事象 → なぜ → 適用方法」。

---

## ユニットテスト全パスでも、実データ E2E と実機シミュレーションは別に必要

**事象（3 種の実例）:**
- ユニットテスト 47 件全パスのメール分析ツールが、実メール 12 通の E2E で 6 件のバグを
  露呈した（未登録の正規クラウド URL による偽陰性、サブドメイン一致の考慮不足、壊れた
  Base64 ヘッダのデコード失敗、認証結果単独判定の偽陽性など）。
- ビルド済みバイナリの実機シミュレーションで、データファイル不在時のエラー、フラグ無し
  実行の失敗、出力の日付未表示が発覚した。出力フォーマットや UX の問題はユニットテスト
  では原理的に見つからない。
- MCP サーバーはユニットテスト green + 台本 E2E 全 PASS の状態から、**実際に MCP
  クライアントとして使った途端に 3 件の欠陥が露出**し、その後も「使ってみて初めて出た
  欠陥」由来のリリースが続いた。台本 E2E は「自分が想定した手順」しか通らない。

**適用方法:**
- `testdata/samples/` に gitignored の実データ置き場を作り、リリース前に E2E を実行する。
- ビルド済みバイナリで基本操作を手動で一巡する: 正常系 → 設定なし起動 → 空の状態 →
  出力フォーマットの目視。
- **MCP/ツールは公開前に自分のクライアントに繋いで一巡する**。台本ではなくその場で
  考えた操作で（想定外を踏むのが目的）。第三者に依頼できればさらに良い。
- GUI のエラー表示は「エラーを意図的に起こして実機で出ること」を確認するまで信用しない。

## モックはエラー経路を「通す」が、そこで組み立てられた文言は誰も読まない

失敗経路の**分岐**はモックで網羅できる。網羅できないのは、その経路の末端で
**人間に渡る一文が意味をなしているか**である。アサーションは部分文字列一致で
緑になり、実際に読むと誤誘導になっている文言をそのまま通す。

**実例（2026-08-23, mcp-bridge v0.1.0 リリース前検証）。** 実 Slack MCP サーバに
失効トークンで接続して、ユニットテストが 1 つも落とさなかった欠陥が 2 件出た。

1. **原因が経路の途中で消える。** 401 を受けて資格情報を無効化 → 再試行 →
   「トークンが無い」で失敗、という順序のため、ユーザーに届く最終文言が
   `no access token` だけになっていた。事実としては正しいが、それは無効化の
   *結果*であって原因ではなく、読んだ人は「空のトークンファイル」を探しに行く。
   401 という原因・更新手段が無いという理由・実行すべきコマンドの 3 つを
   末端まで持ち回るよう修正した。
2. **成功したのにエラー行が出る。** 自己署名証明書のループバックコールバックでは、
   ブラウザの最初の接続が必ずハンドシェイクに失敗する（その失敗こそが、ユーザーが
   クリックスルーする警告を生む）。`http.Server` の既定 ErrorLog がそれを
   `tls: bad certificate` として毎回出力しており、しかも自前の「警告は想定内です」
   という案内の直後に出ていた。**成功したログインが失敗に見える**状態。

どちらもモックは同じ分岐を通っていた。違いは、実行して**出力を人間が読んだか**だけ。

**How to apply:**

- リリース前の実データ検証では、正常系だけでなく**失敗系を意図的に起こして
  端末の出力をそのまま読む**。無効な資格情報を1つ用意するだけで足りることが多い。
- エラー文言のテストは部分文字列一致だけにせず、**「出てはいけない語」も否定形で
  固定する**（上記1では `no access token` が出ないことをテストに入れた）。
- 使用しているライブラリが**自前のロガーを持つ**場合（`http.Server.ErrorLog` など）、
  それが本番経路で何を出すかを一度実行して確認する。自分が書いていない出力は
  自分のテストには現れない。

関連: [[all-green-unit-tests-still-need-real-data-e2e]]

## 配信で終わるパイプラインは、実際に配信するまで検証できていない

**症状:** フィードダイジェストのツールで、ユニットテスト 315 本と、収集から
ファイル生成までの実データ 1 巡がすべて通っていた。以下はそのすべてを
通り抜け、実際に送信して初めて現れた。

- インラインの `[title](url)` が、**タイトルだけでアドレス無し**で相手側に
  届いた。配信先の変換器にインラインリンクが無く、変換ではなく URL の破棄が
  起きていた。読むべきものを選ぶツールが、読む手段だけを落として配っていた。
- 文字数上限を測ったあとで、2 通目以降に `*(continued)*` を前置していた。
  実メッセージは**上限を 7 文字超過**。配信先は切り詰めずに拒否する。
- 4 分割だった前回のあとに 2 分割の実行をすると、`msg-03` と `msg-04` が
  ディスクに残る。送信側は連番で辿るので、今回の 2 通のあとに前回の 2 通が
  続いて送られる。

いずれもフィクスチャからは到達できない。1 つ目は配信先の変換器そのものが要り、
2 つ目は実長のマルチバイトテキストが要り（日本語は 1 文字約 3 バイトなので、
バイト基準の上限は両方向に静かに間違う）、3 つ目は「分割数が減る遷移」が要る。

**適用方法:**
- 「正しく描画された」と「正しく届いた」は別の主張として扱い、後者をリリース
  前に立てる。配信先から**読み返す**こと。そこに保存されている文字列が読み手の
  見るものであり、送った文字列と同じとは限らない。
- 各欠陥をケースではなく、パイプライン出力に対する不変条件にする——
  *全項目の URL が配信テキストに現れる（全フレーバーで）*、
  *全パートが上限内（マーカー込みで）*。不変条件はフレーバーやマーカーが
  増えても成立し続ける。
- 可変個数のファイルを書く前に、前回の出力を消す。列挙して消費する側は
  残骸も消費する。

## 訓練 runbook は書いた時点では未完成 — 1 回通すまで「何も検証していないステップ」が混ざる

**事象:** フォールバックツールの月次訓練 runbook を 7 ステップ書き、初回実行したら
**3 ステップが書き換わった**。(1) 「このプロジェクトは何をするもの？ ビルド/テスト
コマンドは？」で読み取り経路を検証しようとしたが、エージェントは指示ファイルを
システムプロンプトに注入しているのでツールコール 0 回で正解が返った — 正解が返る
ので合格に見えるが、検証したかった経路を通っていない。(2) 自動承認が設定既定で ON
で、承認ゲートの検証ステップが無人実行になるところだった。(3) 「プロジェクト外に
書いて」とモデルに頼んで sandbox 封じ込めを検証しようとしたら、モデルは制限を読んで
試行自体を断った（＝何も検証していない）。同じ要求の別実行では試行し、ゲートが先に
出た。

**適用方法:**
- **書いたら必ず 1 回通す。** ステップが書き換わるのは正常な結果である。書き換わら
  なかったときは「本当に通したか」を疑う。runbook を編集したら、変えたステップだけ
  でも実行する（AGENTS.md 等に明文化して強制する）。
- **「合格に見えるが何も検証していない」の 3 パターンを疑う**:
  検証対象の経路を通らずに正解が出る質問（別の経路に答えが置いてある）/ 被験体の
  協力に依存する検査（→ 直接経路に置き換える）/ 実行ごとに結果が変わる検査
  （→ それは検査ではない）。
- **状態依存の既定値は手順の先頭で固定する。** 「たまたま ON だった」で検査が骨抜きに
  なる。
- チェックリストとは別に **「実タスク 1 件を対象ツールだけで完了させる」ステップ**を
  置く。チェックリストは「動く」を示すが、「使える」は実タスクでしか出ない。
- **判定は「合格 or issue」の 2 値**にする。「だいたい動いた」を許すと記録が意味を
  失う。スキップは「スキップした」と記録する — 無記録の欠落は合格として読まれる。

## 実装済みなのに一度も発火しない機能は、単体テストを全部通る

**事象:** 会話履歴の自動圧縮を実装した。単体テストは全部緑。実運用では**一度も発火せず、
警告も出なかった**。原因は 2 つ重なっていた。(1) 閾値判定が使うコンテキストウィンドウ値は
起動時に非同期解決していたが、解決を仕掛けていたのは対話パスだけで one-shot パスには配線が
無く、値 0 のまま判定が常に false になっていた。(2) 切断点の不変条件を「ユーザー発言の境界
のみ」と定めていたが、長いエージェントループにはユーザー発言が先頭に 1 件しか無く、
**その機能が存在する理由そのものである事例を構造的に排除**していた。

**適用方法:**
- **単体テストは条件を直接与えるので、「その条件が実運用で成立するか」を検証しない。**
  閾値・条件付き発火のある機能は、閾値を極端な値へ振った設定で実機実行し、**発火ログを
  目で確認する**まで「実装した」と言わない。
- 非同期解決値に依存する機能は、入口（対話 / 単発 / スクリプト / 再開…）ごとに配線を数える。
  値が未設定のとき黙って no-op になる設計そのものを疑い、通知を出す設計に変える。
- 不変条件は「最も典型的な使い方」に当てたテストを 1 本必ず持つ。安全側に寄せた規則が
  本命ケースを排除していないかは、規則を読んでも気づけない。
- 発火しない状態が起こり得るなら、その事実を通知する。**無言の no-op は「機能が無い」と
  区別できない。**

## 外部依存は最初からモック可能に設計する

**事象:** テスト実行中に実ブラウザが起動してしまった。後から関数変数に差し替えたが、
最初からそう設計すべきだった。

**適用方法:** ブラウザ起動、外部 HTTP、時刻取得などの外部依存はパッケージ変数または
インターフェースで注入可能にし、テストで差し替える。

## xattr 書き込み失敗は deny ACL で「実注入」できる

**事象:** `setxattr` が失敗する経路（quarantine を付けられないボリューム等）をテスト
したい。モック seam は本番コードに可変グローバルを持ち込み、実 syscall の失敗経路を
通らない。ディスクイメージは遅く環境依存。

**適用方法:** 展開先ディレクトリに継承付き deny ACL を張ると、自分が所有するファイルでも
実際に EPERM を起こせる:

```sh
chmod +a "$(id -un) deny writeextattr,file_inherit,directory_inherit" <dir>
```

新規作成されるファイルが ACL を継承するので、配下すべてで xattr 書き込みが失敗する
（xattr 非対応ボリュームへの展開と同じ形）。速く（実測 0.13 秒）、本物の失敗経路を通る。
テストからは chmod を実行し、失敗したら skip する（環境差の保険）。

## MCP サーバーの自動 E2E はダミー JSON-RPC クライアントで

**事象:** LLM をループに含めるテストは非決定的・遅い・トークンコストが掛かる。一方、
プロトコルレベルの round-trip / エラーパス / タイムアウト / ワークスペース分離は
すべて固定 JSON-RPC で検証可能。

**適用方法:**
- テストから子プロセスを spawn して stdin/stdout で JSON-RPC を打つ Harness
  （`Start / Call / Notify / CallTool / Close`）を実装する。
- `//go:build e2e` タグで通常の `go test ./...` から隔離。コンテナ等の実環境を要求する
  テストは env var で skip 制御。
- 最低限のシナリオ: lifecycle / errors / timeout / 連続ワークスペース分離。
- LLM 実機（Claude Desktop 等）での確認は最終段階だけでよい。ただし「自分でクライアント
  として使う」段は別途必要（上記 E2E の項参照）。
- 埋め込みネイティブライブラリの stdout 汚染は stub build では再現しない — 実エンジンで
  E2E すること（mcp-server-design.md 参照）。

## テストが緑でも、期待値そのものが誤っていれば何も担保しない

**事象:** 外部 API の状態を UI の挙動へ写像するコードにユニットテストを書き、全て緑だった。
それでも機能は誰も使えない状態で出荷され、ユーザーが実機で触って初めて発覚した。

**なぜ:** テストは「私が正しいと思った写像」を忠実に検証していただけだった。写像そのものが
間違っていたので、テストは誤りを固定する役にしか立たなかった。外部 API のセマンティクス
（どの状態値がどういう意味か）は**こちらの想像であって、テストでは検証できない**。

**適用方法:**
- 外部 API の状態値を UI 挙動へ写像するときは、**そのテストを「仕様の確認」と見なさない**。
  ドキュメントの読み違いはテストを通過する。
- 特に「その状態のときコントロールを無効化する」ような**能力を奪う分岐**は、
  誤ると機能全体が到達不能になる。実機確認の対象として明示的に挙げる。
- 実機でしか分からない領域を**作業計画の時点で列挙**し、「ここは確認してもらう」と
  宣言しておく。後から気づくと、それまでの「テスト緑」が判断を誤らせる。

## 「実測済み」を名乗る前に、プローブ入力が実物の代表かを問う

**事象:** 端末 Markdown レンダラが幅超過のコードブロック行をどう扱うかを、132 セルの
**空白を含まない**罫線 1 行で実測し、「切り詰めも折り返しもしない（無加工で通す）」と
結論して設計文書に「実測済み」と記載した。独立レビューが実物の罫線アート — ボックスの
間に**空白を含む** — で再測定したところ、レンダラはコードブロック行を**空白で語折り返し**
しており、幅超過の図は端末に届く前に断片の交互列に粉砕されていた。プローブがたまたま
その機構（語境界）を運ばない入力だったため、存在する挙動が観測不能だった。

**なぜ:** 合成した最小入力は「測りたい性質を運ぶ成分」を欠きうる。n=1 のプローブで
一般命題（「このレンダラは折り返さない」）を主張すると、欠けた成分の数だけ偽の
「実測済み」が生まれる。しかも「実測済み」の札が付いた主張は再検証されにくく、
本人の仮説に最適化されたプローブの欠落は本人には見えない。

**適用方法:**
- プローブ入力は**本番でその経路を流れる実物**（実レンダラ出力・実モデル出力・実ログ）
  から取る。合成するなら、測りたい性質に効きうる成分（空白・全角・制御文字・長さ）を
  意図的に含める。
- 文書に「実測済み」と書く主張には**入力の素性を併記する**（何を・どう流したか）。
  再測定者が代表性を判定できる形でだけ、実測は主張になる。
- 独立検証パスに「主張は全件コード/プローブで再検証してから採用」を課す。この事例を
  捕捉したのはその指示だった。同型の先例に「手書き期待値が実レンダラの装飾を含まず
  偽陰性を出荷」がある — 期待値もプローブも、実物から作る。

## GUI は「見えている部分」と「動いている部分」が独立していることを前提に検証する

**事象:** メニューバー常駐アプリで、バーのラベルが正しく表示されているのを確認して
「動作している」と判断した。実際にはクリックで開くパネルの中身が初版からずっと空だった。

**なぜ:** メニューバーのラベルとパネルの内容は別のビュー階層で、片方が正常でももう片方が
壊れていることがある。またパネルはプログラムから開きにくい（アクセシビリティ権限の
プロンプトが出る、クリックが前面プロセスに飛ぶ等）ため、自動確認から漏れやすい。

**適用方法:**
- 「ラベルが出ている」は動作確認ではない。**UI の各面を個別に確認対象として数える**。
- 自動で開けない面があるなら、**そこは人が見る前提で計画に書く**。曖昧にしたまま進めると、
  確認していない面を確認したつもりになる。
- 長時間稼働でしか出ない挙動（タイマー凍結、日付跨ぎのリセット）は、
  一晩置いた後の実データで検証する。

## メニューバー常駐（LSUIElement）アプリの E2E は CGEvent + CGWindowList + ウィンドウ単体 screencapture で駆動する

**症状:** メニューバー常駐アプリのパネルをテストスクリプトから開けず、各状態が
未検証のまま残った（上の項目を参照）。AppleScript は役に立たない —
`System Events` の `key code` は Carbon `RegisterEventHotKey` のハンドラに届かず、
`NSStatusItem` の action も AppleScript の click では発火しない。

**なぜ:** パネルにはスクリプト可能な面が無い。しかしグローバルホットキーと
ウィンドウは持っており、どちらもより低いレイヤから到達できる。

**適用方法:** ハーネスが一度コンパイルする小さな Swift ヘルパで 3 点。

- **開く** — ホットキーを `CGEvent` として post する
  （`CGEvent(keyboardEventSource:virtualKey:keyDown:)` →
  `post(tap: .cghidEventTap)`）。post する側のプロセスが Accessibility 許可済み
  である必要がある（`AXIsProcessTrusted()`）。
- **開いたか確認する** — `CGWindowListCopyWindowInfo([.optionAll], kCGNullWindowID)`
  を owner 名で絞り、`kCGWindowIsOnscreen` と `kCGWindowNumber` を読む。
- **見る** — `screencapture -x -o -l <windowid>` でそのウィンドウ単体を撮る。
  全画面キャプチャより必ずこちらを使う。無関係なウィンドウ（他人とのチャット、
  メール、チケット）が画像に一切入らない。

ホットキーは既定値を仮定せず、**アプリ自身の `UserDefaults` から読んでから**送る。
保存値はたいてい `NSEvent.ModifierFlags`（shift `0x20000` / command `0x100000` /
option `0x80000`）であって **Carbon マスクではない**。違う組み合わせを送ると
「ホットキーが壊れている」ようにしか見えず、誤った不具合報告を招く。

**想定しておくべき失敗モード:** 合成キー入力は key status を持つウィンドウに
届く。そしてそれは**テスト対象とは限らない** — non-activating panel は key status
を安定して取らないし、macOS の focus-stealing 防止は起動後 ~30 秒 activation を
拒否しうる。外れた打鍵はすべて**ユーザーの前面アプリに入り**、余計な文字列を
打ち込み警告音を鳴らす。したがって、打つ前にウィンドウが key であることを確認し、
送る文字列は短く無害なものにし、**入らなくなった時点でこの手法をやめる**こと。
リトライこそがユーザーの他のウィンドウに届く。この方法は「ウィンドウを開いて
状態を撮る」用途には向くが、**信頼できるテキスト入力ドライバではない**。

**代替ではなく補完:** この方法で到達できない状態（IME 変換中、初回のモデル
ダウンロードなど）は、純関数のユニットテストと、人が一度目視する工程が引き続き必要。

## レイアウト崩れは、アプリを起動せずテストターゲットからのオフスクリーン描画で見る

**症状:** 純関数のユニットテストは文字列と数式しか触れないので、「その文字列が
実際の幅に収まるか」は原理的に検出できない。表示行を 1 本増やしただけの変更でも、
最長の分岐で truncation が起きるかどうかは机上では決まらない。かといって合成イベントで
実アプリを駆動する方法（前項）は、外れた入力がユーザーの前面アプリに漏れるため、
レイアウト確認のたびに使うには重い。

**なぜ:** SwiftPM の実行可能ターゲットはテストから `@testable import` できる。
ビューを `NSHostingView` に載せればアプリを起動しなくてもレイアウトが確定し、
`bitmapImageRepForCachingDisplay(in:)` + `cacheDisplay(in:to:)` で PNG に落とせる。
実アプリと同じレイアウトエンジンと実フォントが走るので、折り返し・truncation・
実際の文字幅がそのまま出る。ユーザーの画面には何も起こらない。

**適用方法:**

- テストターゲットに使い捨てのレンダラを置く。`NSHostingView(rootView: TheView().environmentObject(model))`
  を作り、**本番と同じ幅**（例: popover の内容幅 + padding）を与えて `layoutSubtreeIfNeeded()`。
- 高さは `fittingSize.height` を使い、決め打ちで押し込まない。収まらない状態を見たいのだから、
  高さを固定すると証拠のほうが消える。
- 状態は `@Published` に直接値を入れて作る。表示の検証なので、外部プロセスや
  ネットワークは呼ばせない。
- **分岐ごとに 1 枚ずつ出して全部見る**（正常 / 警告 / 超過 / データ不足）。崩れるのは
  たいてい最長の文字列を持つ分岐で、それは平常時の分岐ではない。
- 確認が済んだらレンダラは消す。スナップショットを回帰テストとして残すと、OS の
  フォント更新やシステム配色の変更で無関係に落ちる。残すなら意図して選ぶこと。
- 合成イベントで実アプリを駆動する手法は、**本物のアプリでしか起きないこと**
  （許可ダイアログ、メニューバー上の実配置、起動直後の挙動）に取っておく。

## 二重の防御があるとき、片方だけで説明のつく観測を両方の証拠にしない

**事象:** MCP サーバーの stdout 汚染対策を 2 層で入れた — ①発生源でランタイムのログ
コールバックを差し替える ②本物の stdout を dup して transport 専用にし fd 1 を stderr へ
向ける。実 E2E で「stdout は JSON のみ・stderr は 0 行」を観測し、**両方が効いている証拠
だと読みかけた**。

**なぜ:** stderr が 0 行だったのは①のログハンドラが info レベルを落としていたからで、
**①だけで観測結果が完全に説明できる**。②が実際に機能したかどうかについて、この観測は
何も言っていない。②が壊れていても同じ観測になる。

**適用方法:** 防御を多層で入れたら、**層ごとに独立した検証を用意する**。この件では
機構を直接叩くユニットテストに置き換えた:

```go
protocol, _ := claimStdout()
protocol.Write([]byte("PROTOCOL\n"))   // transport 側に出るべき
os.Stdout.Write([]byte("STRAY\n"))     // stderr 側に出るべき
// → protocol ストリームに "STRAY" が無いことを assert
```

一般則として、**「観測 O は防御 A でも防御 B でも説明できる」なら、O は A の証拠でも
B の証拠でもない**。統合テストが緑であることは、各層が生きている証明にならない。

## コードを疑う前にフィクスチャを検証する

**事象:** 話者分離の検証で `say -v Kyoko` と `say -v Otoya` の 2 音声から会話音声を合成し、
「2 話者のはずが 1 話者と判定される」と実装を疑って数十分を溶かした。原因は
**`Otoya` が未インストールで、`say` が無言のまま既定音声にフォールバックしていた**こと。
4 クリップ全部が同一話者だったので、話者分離の「1 話者」判定は正しかった。

**なぜ:** 生成系のコマンドは、指定したリソースが無いときエラーではなく**もっともらしい
別物**を返すことがある。`say` の voice、フォント指定、モデル名、ロケール指定などが典型。
出力ファイルは正常に生成されるので、フィクスチャが壊れていることに気づく手がかりがない。

**適用方法:** 合成したフィクスチャは、**期待した性質を持っているかを別手段で確認**して
から実装の検証に使う。最低限、指定したリソースが実在するかを事前に確かめる
（`say -v '?'`、フォント一覧、モデル一覧）。テストが「正しい答え」を返しているのに
それを不具合と読む方が、実装バグより高くつく。

## 「該当なし」は、全ソースが実際に答えたときだけ答えになる

**何が起きたか:** ある lookup ツールは、上流が名前を `domain` と `hostname` の
どちらか一方にしか索引せず、しかも**どちらも 200 を返す**ため、2 つの型で照会する。
実 API 検証中に片方が 429 で落ち、もう片方が 0 件を返した結果、ツールは
**「どの報告もこの IoC を挙げていない」と表示して exit 0 で終了した** — 一時的な
上流エラーから「シロ判定」を捏造したことになる。スタブによるテストは全て通っており、
実 API を叩いて初めて露見した。

**なぜ:** 「一致が無い」と「訊けなかった」は**データ上は同一**で、意味は正反対である。
失敗したソースを空の結果集合に畳み込むコードは、後者を前者として報告する。しかも
否定的な答えは誰も再確認しない — 偽陽性は対応する人間が精査するが、偽陰性は綴じられて
忘れられる。片方が失敗し片方が成功したときにしか存在しない不具合なので、モックでは
原理的に捕まらない。

**どう適用するか:**

- 結果に `incomplete` フラグを明示的に持たせ、「空 **かつ** 不完全」を独立した状態
  として名前を付ける。呼び出し側が 2 つの真偽値を毎回思い出す設計にしない。
- 出力に書く。利用者に見える `INCONCLUSIVE` は、黙った 0 件よりはるかによい。
- 終了コードに載せる。スクリプトは exit 0 を「シロ」と読む。未検証の否定は 0 で終わらせない。
- 失敗したソースを名指しする。「何か失敗しました」では、答えをどこまで信じてよいか
  読み手が判断できない。
- 上流が同一の論理オブジェクトに複数の endpoint を持ち、**そのどれもが 200 を返す**
  場合、取り違えはエラーにならず静かな空結果になる。代替も引き、どちらが答えたかを併記する。

## 揺らぐ系の指標を 1 回の実行で語らない

**何が起きたか:** ローカル推論エンジンで 2 つのモデルを比較し、片方が「49 分の
音声中に 48 セグメント連続の反復ループを起こす」と報告した。後日まったく同じ
バイナリ・同じモデル・同じ音声・同じ設定で回し直したところ、最大連は 19 だった。
3 回ずつ回して初めて分かったのは、**出力量そのものは安定している**（文字数の振れは
±1%）のに、**破綻の構造は大きく振れる**（最大連 19 / 45 / 48）ということだった。
マルチスレッドの簡約順序が生む微小な浮動小数差が、確率的な分岐点で決定を反転させる。

**なぜ:** 「決定的な処理だから 1 回測れば足りる」という前提が、並列化された数値計算では
崩れる。しかも崩れ方が一様でない — 平均的な量は安定するのに、閾値近傍の離散的な判断
（ループに入るか、話者を分けるか、フォールバックするか）だけが揺れる。**最初の 1 回が
分布の裾だった場合、報告した数値は再現せず、それを見た人はこちらの測定全体を疑う。**

**どう適用するか:**

- **系が揺らぐかどうかを、比較を始める前に確かめる。** 同じ入力を 2 回通すだけでよい。
  出力が違えば以降の全指標は n≥3 で幅として扱う。
- **報告は点ではなく範囲で書く。** 「48 連続」ではなく「19〜48（3 回）」。
- **判定に閾値を置くなら、2 群の範囲が重ならないことを根拠にする。** 上の例では
  「ループを起こす側 19〜48」対「起こさない側 2〜3」なので、閾値 6 は隙間に置ける。
  片方の 1 標本の隣に閾値を置くと、次の実行で誤判定する。
- **量が安定していることを、構造も安定している証拠に使わない。** 上の例では文字数が
  ±1% で一致していたが、それはループの再現性について何も言っていない。

## 正解が無い出力は、構造の健全性で測れる

**何が起きたか:** 39 分の実音源で 2 つの文字起こしモデルを比較したかったが、
参照テキストが無いため誤り率は測れなかった。代わりに**正解を要さない指標**を測った —
セグメントの被覆率、同一テキストの連続反復、セグメント間の最大空白、話者ラベルの偏り。
これで「一方は 1.45 倍の文字を出す」「一方だけが反復ループに落ちる」という、
選択を左右する差が定量化できた。

**なぜ:** 正解の無いデータは「測れない」と諦められがちだが、**壊れ方には形がある**。
反復ループ、取りこぼし、過分割は、内容を読まなくても構造だけで検出できる。しかも
そういう破綻は往々にして**出力が完全に整形式のまま**起こる（JSON は妥当、全フィールドが
埋まり、エラーも出ない）ので、構造を測らなければ誰も気づかない。

**どう適用するか:**

- 正解の要る指標（精度）と要らない指標（構造）を分け、後者だけで先に比較する。
  多くの場合それだけで候補が絞れる。
- **範囲が重ならない差だけを結論に使う。** 構造指標は代理指標なので、僅差は
  意味を持たない。
- **指標スクリプトは本文を一切出力しない設計にする。** 件数と率だけを出すなら、
  秘密情報や私物のデータにそのまま向けられる。正解の無い実データは、たいてい
  「外に出せないから正解が無い」のであって、この制約と正解の欠如は同じ根を持つ。
- 被覆率のような指標は**単独では両義的**であることに注意する。被覆が高いのは
  取りこぼしが少ないからかもしれないし、無音や音楽に対して幻覚しているからかもしれない。
  独立した第三の観測（この例では VAD）で切り分ける。

## 列挙ツールが返した対象は、目的の対象と照合してから証拠にする

**事象:** USB 接続の外付け SSD から SMART 情報が読めるかを調べていた。診断ツールの
自動列挙モード（`--scan`）が返したデバイスに対してコマンドを実行し、返ってきた I/O
エラーを「この SSD では読めない」証拠として報告した。実際には列挙は**調査対象の 2 台を
1 台も拾っておらず**、別系統のハブにぶら下がった**中身の入っていない空のドライブケース**を
1 件だけ返していた。そのエラーは「メディアが無い」ことでも説明がつき、調べていた制約の
証拠には全くなっていなかった。対象 2 台をデバイスパスで名指しして測り直すと、別のエラーが
出た（結論そのものは変わらなかった）。

**なぜ:** 列挙ツールは「見つかったもの」を返すのであって「こちらが指したもの」を返さない。
結果が 1 件だと、それが目的の対象だと錯覚しやすい。さらにこの件では**結論が偶然正しかった** —
「USB 経由では読めない」という答えは別の証拠でも裏づけられていたため、**証拠の方が
間違っていることが最後まで表面化しなかった**。正しい結論を誤った証拠で支えると、前提が
変わったとき（別のハードウェア、別の OS 版）に何が崩れたのか追跡できなくなる。

**適用方法:**

- 列挙の出力は、**独立した識別子**で目的の対象と照合してから使う（デバイスパス、
  シリアル、容量、論理名）。ツールが付けたラベルだけを信じない。
- **列挙件数と、自分が知っている対象の件数を突き合わせる。** 2 台繋がっているのに 1 件しか
  出ないなら、その時点で列挙自体を疑う。ゼロ件より、数の合わない非ゼロ件の方が危険。
- 対象を名指しできる経路があるならそちらで測り直す。**自動列挙は探索の道具であって、
  検証の道具ではない。**
- 「結論が合っているから証拠も正しい」は成り立たない。結論と証拠は別々に点検する。

## 論理ツリー上の位置から物理的な配置を推定しない

**事象:** 同じ調査で、対象 SSD が OS のデバイスツリー上で SoC 内蔵の USB コントローラ配下に
いることを根拠に「本体の USB 専用ポートに挿さっている」と判定し、利用者に
「Thunderbolt ポートへ挿し替えよ」と指示した。**実際は最初から Thunderbolt ポートに
挿さっていた。** その環境では Thunderbolt ポートの USB トラフィックも同じ USB コントローラに
現れる設計で、ツリー上の位置からポート種別は原理的に判別できない。利用者の
「いや、そちらに挿さっている」の一言で覆った。

**なぜ:** 抽象化層のツリーは「そのデバイスがどう扱われるか」を表すのであって、
「どこに挿さっているか」を表さない。さらに同じ物理ポートが複数のプレーンに別々に現れる系
（この例では USB プレーンと Thunderbolt プレーン）では、片方のプレーンだけを見ると
「そこには何も無い」ように見える。

**適用方法:**

- 物理配置は、**位置が確定しているデバイスを基準点にして較正する。** この件では
  「Thunderbolt ハブは Thunderbolt ポートにしか挿さらない」→ そのハブが問題の USB
  コントローラ配下に現れている → このコントローラは Thunderbolt ポートも含む、と 1 手で
  確定できた。推定を積み上げるより、**既知の 1 点を探す方が速い。**
- **片方のプレーンの「デバイスなし」を不在の証拠にしない。** 逆に、この非対称性自体は強い
  診断信号になる — 上の例では Thunderbolt バス側が「未接続」と言い張ることが、その機器が
  PCIe リンクを張らない純粋な USB ブリッジである証拠になった。
- **目の前の人間が数秒で答えられる物理的事実を、ツール出力から推定しない。** 聞く方が速く、
  確実で、外したときの手戻りも小さい。推定してよいのは、聞ける相手がいないときだけ。

### 並行性の懸念は読解ではなく並行テストで検証する — バグは疑われた層の隣で出る

**事象:** 「タイムスタンプ由来のセッション ID は並列実行で衝突するのでは」という
指摘を受けた。コードを読むと疑われた層は安全だった（O_EXCL + サフィックス再試行 +
flock）。だが「安全であること」を示すために書いた 16 並行の実測テストは、**隣の層**
（状態ディレクトリのマーカー書き込み）の実レースを約 50% の頻度で検出した。読解に
よる「安全です」という回答なら、このバグは残っていた。

**適用方法:**
- 並行性への疑義には、結論がどちらでも**まず並行回帰テストを書く**（同時スタート用の
  start チャネル + `-race` + 複数ラウンド）。テストは疑われた仮説だけでなく経路全体を
  通すので、隣接層の欠陥も浮く。
- goroutine テストで見つけ、**実プロセス同時起動でも確認する**（O_EXCL・flock・rename
  はカーネル語彙なので同型だが、E2E は配線の見落としを拾う）。
- 「該当なし（安全）」と答える前に測る — 否定的回答の完全性義務は並行性にも適用される。

### 依存注入した機能は「本番の 1 呼び出し箇所」が最弱点 — 配線は AST テストで固定する

**事象:** UI 言語カタログ機能を実装し、ユニットテストは全部 green、非対話モードの
E2E も通した。だが本番唯一の TUI 構築箇所がカタログ引数を渡し忘れており、TUI 全体が
1 リリースの間、黙って英語フォールバックで動いていた。テストは依存を自分で注入する
ので配線漏れを検出できず、E2E は配線されている側の面だけを見ていた。

**適用方法:**
- 「実装済みでも黙って発火しない」の第 3 のパターン: **オプション構造体のフィールドは
  nil 既定で静かに退化する**。nil 許容 + 良識的フォールバックは、まさにその親切さの
  ぶんだけ配線漏れを不可視にする。
- 巨大な初期化関数の中のリテラルには挙動テストが届かない。**go/ast で本番ファイルを
  パースし、構築リテラルに必須フィールドが並んでいることを検証するテスト**が配線を
  固定する（数十行で書ける・整形に頑健・フィールド消滅で確実に落ちる）。
- E2E は「新機能が効いた面」ではなく「新機能が通る全ての面」で 1 回ずつ。今回は
  非対話（cmd 側）だけ実測し、対話（TUI 側）を実測しなかったのが敗因。
## ログから時刻の結論を出す前に、そのログの時刻表現の素性を確定させる

**事象:** 日次のログ要約レポートが「昨日ディスクの I/O エラーが発生」と報告した。カーネル
ログの内容（ATA コマンドのタイムアウトとリンクリセット）を読み解いてドライブ故障の診断まで
組み立てたが、実体は **2 年前の同月同日**のログだった。`/var/log/messages` が 2.7 年
ローテートされておらず、RFC 3164 形式が年を持たないため、レポートの日付一致が過去年の
同じ日付文字列を拾っていた。

**なぜ:** 中身の解釈は正しかった。誤っていたのは**前提の時刻**で、それが偽だったので診断
ごと無効になった。時刻表現の曖昧さは何段階もある — 年の有無、タイムゾーンの有無、表示側の
再解釈、事象時刻か取り込み時刻か、相対時刻の変換。どれもログを読む段階では見えず、結論を
出した後に効いてくる。

**適用方法:** 中身を読む前に、次を確定させる。

1. **カバー期間** — `ls -la`（サイズ）→ `head -1` / `tail -1`。静かなサーバのログが
   数十 MB なら、それだけで異常のサイン。
2. **年を持つか** — RFC 3164（`Aug 22 06:37:29`）は持たない。**年なし形式は、ファイルが
   1 年を超えた時点で日付一致が壊れる**。
3. **タイムゾーン** — 記録側（RFC 3164 はオフセットも持たない）／表示側（`journalctl` は
   閲覧者の TZ でレンダリングするため、同じ事象がテキストログと違う時刻に見える）／混在
   （コンテナが UTC、ホストがローカル時刻）。**DST のある地域では年 1 回「重複する 1 時間」
   と「存在しない 1 時間」が生じ、文字列ソートも日付一致も壊れる**。
4. **事象時刻か取り込み時刻か** — 転送やバッファリングを挟むと後者になる。
5. **単調性を仮定してよいか** — 「追記順＝時系列」は複数書き手・NTP のステップ調整・
   マージされたファイルで壊れる。
6. **相対時刻の変換** — `dmesg` の `[12345.678]` は起動からの経過秒。`dmesg -T` は
   起動時刻＋単調時計から絶対時刻を計算するため、**時刻がステップ調整されるとずれる**。

曖昧な時刻表現しか持たないログで日付を判断せず、明示的な情報源に当たる:

```
journalctl -k --since "YYYY-MM-DD" --until "YYYY-MM-DD" -o short-iso
```

journald は UTC マイクロ秒の実時刻と boot ID を保持しており、年・タイムゾーン・起動回数の
いずれも曖昧でない。要点は「別の情報源と突き合わせる」ではなく、**時刻表現の素性が良い
情報源に当たる**こと。

年なしログで年を割り出すには、日付文字列の出現行番号を見る:

```
grep -n "^Aug 22 " /var/log/messages | cut -d: -f1   # 出現行番号
grep -n "^Jan  1 00:0" /var/log/messages             # 年境界
```

同じ日付文字列が遠く離れた行番号に現れたら、そのファイルは複数年にまたがっている証拠。
年境界の行番号で挟めば各クラスタの年が確定する（5 の単調性仮定に依存する）。

### 利用から学ぶ機能は、利用の形をしたデータでテストする

**症状:** 承認ルールの学習器を、ユニットテスト・E2E・「3 つの別セッション
で承認」という閾値とともに出荷した。最初の実セッション — 25 回の
エスカレーションを全部承認 — は提案ゼロを生んだ。E2E は閾値を満たす
ためにちょうど 3 セッションを仕込んでおり、機構が動くかは測ったが、
**閾値が到達可能かは一度も測っていなかった**。

**なぜ重要か:** 閾値を満たすために書かれた fixture は、その閾値を反証
できない。テストは緑で、機能は動き、欠陥は実データが来るまで不可視
だった — 「発火しない機能」と同じクラスだが、沈黙ではなく**合格して
いるテストの背後**に隠れている。

**適用方法:**
1. **少なくとも 1 つの fixture を、閾値ではなく本番の形にする。**
   学習器なら、実利用が生む分布のこと: 1 セッションに集中した作業、
   1 回限りの項目が多数、ロングテール — そのドメインの実際の姿。
2. **「これは動くか」と「このハードルは届くか」を別々に問う。** 別の
   問いであり、実分布が要るのは前者だけである。出荷前に、数字で
   答える。
3. **実報告が来たら、診断の前に再現する。** 報告された形の合成
   トランスクリプトが、もっともらしい物語を 1 回のテスト実行で 2 つの
   実測された原因に変え、そのまま回帰テストになった。
4. **そもそも摩擦が、数えている形をしているか確認する。** 今回は半分が
   カテゴリの問題だった: ツール単位の頻度では「毎回違うツールを 1 回
   ずつ」という形の摩擦は見えない。そのカウンタ上の閾値は安全かつ
   到達可能にはならないので、変えるべきはルールの**単位**であって
   数値ではなかった。

## 機能を区切る定数は、実利用でその窓が覆う母集団を数える

**事象:** エージェントのリスク評価器に「オペレータ指示を証拠として同梱する」機能を
付けたとき、対象を**ターン先頭 3 ラウンドのみ**と直感で区切った（「序盤のコールは依頼に
遡れる、深部は依頼が名指さないサブゴールに仕える」）。数週間後、全セッション記録から
ラウンド位置を再構成して実測すると: モデル評価の **70%** が窓の外、ターン**終端**の
ゲート対象コール — 送信・保存など、整合を最も知りたいアクション — は **63%** が窓の外
だった。窓外で起きたエスカレーションは、記録のある範囲でオペレータが事後に全件手承認
しており、実態は読み取り専用の調査コールへの誤警報だった。

**なぜ重要か:** カットオフ定数は設計時点の想像上の利用形に基づく。実利用の分布は裾が
重く（ラウンド 8〜48 に評価の半分があった）、**どの定数も裾とは合わない** — 「現実に
合う数字」が存在しないことが実測の答えになる場合がある。これは「発火しない機能は
適合率では検出できない — 分母を数える」の変種で、**窓の守備率も分母を数えないと
見えない**。機能は動いていて、テストも通り、窓内では正しく働くので、なおさら気づけない。

**適用方法:**
- 機能をカットオフ定数（ラウンド数・件数・サイズ・経過時間）で区切ったら、リリース後に
  実ログで**その窓が覆う母集団の割合**を測る。守備率が少数派なら、定数の調整ではなく
  カットオフ自体の要否を問い直す。
- 測れる形で記録を残す: 判定イベントに位置情報（ラウンド番号等）を含めるか、メッセージ
  列から位置を再構成できるトランスクリプトにする。今回の実測は後者で可能だった。
- 窓外の「機能なし」経路が誤警報を生んでいるかは、エスカレーション→直後の人間の判断
  （承認/拒否）の対応で測る。全件承認されているエスカレーションは摩擦であって防御ではない。

## 外部 API の語彙と可視範囲はライセンス階梯で変わる — 文書ではなく手元のキーで実測する

**事象:** 公式ドキュメントに載る filter 語彙（ハイフン形式）を実 API が 400 で
拒否し、受理される語彙（アンダースコア形式）は文書のどこにも無かった。受理される
型でも中身は階梯依存で、上位ライセンス限定の型は**エラーではなく空**を返した。
ベンダー自身の公開参照実装も文書側の語彙を使っており、そのままでは動かなかった
（lookup CLI+MCP プロジェクト、2026-09）。

**なぜ:** API の応答は「エンドポイント仕様 × キーのエンタイトルメント」の積で
決まる。文書は最上位ライセンスの視界で書かれがちで、参照実装の存在は正しさの
証拠にならない。空応答・400・403 はどれも「使えない」だが意味が違う —
区別しないと「存在しない」と「（この階梯からは）見えていない」を取り違える。

**適用方法:**
- 統合前に**手元のキーで**仕分けの実測を行う: 400（語彙・構文の拒否）/
  403（エンドポイント単位の拒否）/ 空（内容の階梯ゲート）。結果は日付とキーの
  階梯を添えて記録する。
- 権限一覧を返すエンドポイント（privileges 等）があれば最初に読む。挙動からの
  推測より 1 リクエストで確定する。
- **手元で実測テストできない機能は出荷しない**。上位ライセンスで動くはずの機能を
  推測実装で残すと、検証不能なコードパスが恒久化する。スコープを「検証可能な
  機能セット」で切り、その判断と理由を利用者向け文書に明記する。
- 階梯ゲートされた空応答をツール結果として返す面では、利用者向け文書に
  「空 = 不存在ではない」ことを書く。

### golangci-lint は同一メッセージの指摘を 3 件で打ち切る — 一括修正の前に全件を出す

**事象:** `defer x.Close()` の errcheck 指摘が「8 件」と表示されたが、実体は 18 箇所
あった。golangci-lint は `max-same-issues`（既定 3）で同一テキストの指摘を、
`max-issues-per-linter`（既定 50）で linter ごとの件数を打ち切る。受信者名ごとに
3 件ずつ出ていたため、表示分だけ直して再実行すると次の 3 件が「新たに」現れる。

**適用方法:**
- 一括修正の前に `golangci-lint run --max-same-issues 0 --max-issues-per-linter 0 ./...`
  で全件を出し、件数を把握してから機械的に直す（正規表現で
  `defer x.Close()` → `defer func() { _ = x.Close() }()` 等）。
- 同型の指摘が 1 件でも見えたら、その型で全ファイルを grep する。表示件数は下限で
  あって全数ではない。

# 設定・識別子・CLI 入出力

設定ファイルの読み込み、識別子の canonical 化、ファイルシステム、OAuth、
ターミナル入出力に関する知見。
各項目は「事象 → なぜ → 適用方法」。

---

## 識別子・データ形式

### wire 形式の不一致は「ソースの canonical 化」と「境界の正規化」の両方で直す

**事象:** LLM に送る tool 名の形式（kebab vs snake）が一部バックエンドで受理されず
dispatch に失敗した。「境界正規化のみ」（ソースは kebab のまま）はソースが嘘をつく状態に
なり却下。「ソースリネームのみ」は古いセッション履歴・scaffold 済みユーザーデータ・
外部サーバーの publish 名が壊れる。

**適用方法:**
- **コントロールできるもの（ソース）**はコード上の綴りを wire と一致する canonical 形に
  リネームする。ソースが嘘をつく状態は読者の認知負荷を恒久的に増やす。
- **コントロールできないもの（外部入力）**は単一の `canonicalize()` helper を registry
  境界（lookup / dispatch ingress / schema emit / 永続化設定のロード）で適用して透過する。
- どちらか片方では不十分。「dispatcher だけ alias 受け入れ」は schema が嘘をつき続ける
  負債になる。

### canonical 形を変えたら、ユーザー設定ファイルもロード時に migrate する

**事象:** ルックアップ側だけ canonical 化した結果、過去に保存されたユーザー設定
（override map / disabled list の key が旧形式）が hit せず**静かに無視される**状態に
なった。ユーザーは「設定した記憶があるのに効いていない」silent failure を踏む。

**適用方法:**
- 識別子変更を計画したら、grep で「その識別子を key として永続化している箇所」を全て
  列挙する（config、セッションメタデータ、export/import 形式等）。
- migration は**ロード時 1 回の in-place rewrite** が最小実装（次の save で canonical 形が
  書き戻される）。旧・新 key が並存する縮退ケースは canonical 優先で OK。
- 注意: 構築済みオブジェクトに直接設定値を流すテストは migration 経路を通らない。
  両方の入力形を検証するテストにする。

### マシンローカルな ID をクロスマシン可搬データに持たせない

**事象:** export/import されるデータに、タイムスタンプ由来のセッション ID
（`sess-<unixMilli>`）への参照が含まれていた。マシン間では壁時計のミリ秒空間を共有する
ため**ほぼ確実に衝突**し、将来その参照を使う機能が「別セッションに作用」する潜在バグに
なる。しかも該当フィールドは write-only の死蔵だった。

**適用方法:**
- **YAGNI**: read 0 件の provenance フィールドはスキーマから削除する。残す/消すは
  フィールド単位で実 set/read を grep 確認。
- どうしても残すなら import 境界で**外来 ID を無条件クリア**する（ローカル一覧と照合して
  残す案は偽リンクを作るのでより悪い）。
- export は `kind` + `schema_version` のエンベロープで包んで誤ファイルを fail-fast 拒否。
  import はマージ・重複スキップを既定に（非破壊・冪等）。
- 機械生成 JSON は素の Unmarshal（strict なし）なら旧キーは無視され次回 save で消える =
  マイグレーション不要。

### ID 順の一覧が時系列なのは ID がタイムスタンプである間だけ — 時刻は別の列で持つ

**事象:** セッション transcript を集計するツールが、セッション一覧を ID
文字列順で並べていた。ID が `YYYYMMDD-HHMMSS` だった間は時系列に見えたが、
生成側が ID を UUID v4 に変えた版から、新しいセッションが旧 ID 群の後ろに
hex 順で並び、行を見ても「いつ動いたか」が分からなくなった。解析器は
ファイル名に依存していなかったので取り込みは壊れず、壊れたのは表示だけ —
だからテストも通ったまま気づかなかった。

**なぜ:** 「ID でソートすると時系列になる」は ID の中身に対する暗黙の依存で、
コードのどこにも書かれていない。生成側は互換性を「既存ファイルが読める・
resume できる」で定義し（実際そのとおりだった）、消費側の並び順は契約の外に
ある。ID の形式変更は生成側の ADR には「minor で互換」と書かれる種類の変更で、
消費側が自分で追随を確認しに行くしかない。

**適用方法:**
- 時刻で並べたい一覧は、**ID とは別に時刻を持つ**（最初/最後のレコード時刻を
  集計行に載せ、`--sort time` を既定にする）。ID は不透明な識別子として扱う。
- 生成側の「セッション」「ID」に関する ADR が出たら、消費側の **表示・並び・
  キー幅** を実データで確認する。パーサのテストが緑でも表は壊れている。
- 追加する時刻キーは **常に書く（空なら `""`、`omitempty` 禁止）**。キー不在が
  「古い CLI」だけを意味するようにしておくと、後で GUI が読み始めても判別できる
  （llm-integration の `tool_prompt` と同じ理由）。
- 「穴埋め行」を持つ密な時系列（`--dense`）には時刻ソートを適用しない —
  レコードの無い行は時刻を持たず末尾に沈んで、キー順で正しかった系列を壊す。
  組み合わせを拒否する方が、比較関数に fallback を足すより安全（推移律が保てる）。

### 長形式で保存すると、取り込み直しが冪等になる

**事象:** 外部サービスの履歴を後から取り込んで穴を埋めたい。エクスポート範囲は重複しがちで、
二重投入や取りこぼしが起きやすい。

**なぜ:** 「1行 = 1 レコード、その主キーがレコードの同一性そのもの」という形にすると、
`INSERT OR IGNORE` がそのまま「足りない分だけ入れる」動作になる。逆に「1行に複数項目を
カラムとして並べる」形だと、部分的な重複をアプリ側で判定するはめになる。

**適用方法:**
- 時系列は `(対象, 項目, 時刻) → 値` の長形式にする。主キーがそのまま冪等性を与える。
- 副次的な効能として、**未知の項目が増えても schema 変更なしに載る**。外部サービスが
  フィールドを増やしても、取り込み側は壊れない。
- 取り込みコマンドには `--dry-run` を付け、「何件が新規で何件が既存か」を実行前に出す。
  実装はトランザクションを張って rollback するだけでよく、推定でなく実数が得られる。

### macOS の IF 別バイトカウンタは、非特権プロセスには加工されて渡される — フィールドの幅は値の幅を保証しない

**事象:** ネットワークインターフェース別の送受信速度を出すために、`sysctl`（`NET_RT_IFLIST2`）で
`if_data64` の累積バイトカウンタを読んだ。フィールドは 64bit なので「巻き戻りは起きない」前提で
設計し始めたが、同時刻の OS 付属 `netstat -ib` と突き合わせると値が合わなかった。自作のプロセスが
受け取っていたのは、**真値を 2^32 で割った余りを、さらに 1 KiB 単位に切り捨てた値**だった。
9 MB/s の通信なら、約 8 分ごとに巻き戻る。（2026-09。macOS 27.0 の実機・有線で、`netstat` の
読み取りで前後を挟んだ比較を独立に 2 回。macOS 26.6.2 の VM では 1 KiB の切り捨てを 1 回確認した。
そちらの 32bit 切り詰めは、カウンタが 4 GiB 未満だったため判定できず未確認。）

**なぜ:** 型の幅が示すのは「入りうる値の範囲」であって、「実際に渡される値の範囲」ではない。
OS は同じ API でも、呼び出し元によって返す精度を変えることがある。OS 付属のツールと自作の
プロセスで値が違った理由は確かめていない（付属ツールだけが持つ権限の差と推測している）。
この種の加工はコンパイルでもテストでも見つからない。数値はもっともらしく、差分を取れば速度も
もっともらしく出る。巻き戻った瞬間にだけ、数 GB/s の棘として現れる。

**適用方法:**
- OS のカウンタを読む設計では、型を信じる前に**加工されていない参照値と突き合わせる**。
  参照 → 自作 → 参照 の順に挟み、自作の値が前後の「参照値 mod 2^32」の間に入ることを確かめる。
  片側だけの比較では、その間に流れた通信量と区別できない。
- 切り詰めは、真のカウンタが 2^32 を超えるまで観測できない。起動したての機械や VM での
  「一致した」は、切り詰めが無いことの証拠にならない。
- 差分は**常に 2^32 を法として**取る。1024 は 2^32 の約数なので、切り捨てと剰余は順序を
  入れ替えられる。切り詰めのある OS でも無い OS でも、1 サンプルの増分が 4 GiB 未満である限り正しい。
- その前提は**サンプル間隔が有界であること**に依存する。スリープやタイマーの停止で間隔が
  延びたサンプルは、値によらず捨てて再基準化する。経過時間はスリープ中も進む時計で測る。
  止まる時計では、スリープが普通の長さの間隔の中に隠れる。
- 巻き戻りとリセット（インターフェースの再生成など）は別物として扱う。リンク速度の上限だけでは
  区別しきれない — リセット後の差分が 4 GiB の範囲に一様に散らばるなら、10GbE の上限は
  その約 3 割を正常な増分として受け入れる。
- 分解能は 1 サンプルあたり 1 KiB。それ未満の通信は 0 と 1 単位のあいだを行き来する。
- `netstat -ibn` を機械的に読むとき、アドレスを持たない行（loopback、トンネル）は列が 1 つ少ない。
  列番号を決め打ちすると、その行だけパケット数をバイト数として読む。

## データ保持

### 保持期限は保持日数ではない — 取り込み遅延のぶん手元のデータは足りない

**事象:** 400 日ぶんを保持するつもりでパーティション期限を 400 日に設定したところ、実際に照会
できたのは 399 日だった。さらに、供給側が 450 日ぶん投入した過去データのうち、古い側 50 日が
着地と同時に消えていた。**どちらもエラーも警告も出ない。**

**なぜ:** 保持ウィンドウは両端で決まる。古い側は「今日 − 期限日数」で、これは期限設定が削除する。
新しい側は「今日 − 取り込み遅延」で、供給側がまだ出していない。期限は古い側しか動かさないので、

```
実際に残る日数 = 期限日数 − 取り込み遅延 + 1
```

となり、日次集計のように 1〜3 日遅れて届くデータでは、その遅延ぶん常に不足する。
また、過去データの一括投入（バックフィル）を受ける先に期限が設定されていると、
**着地した端から古い側が期限切れになる**。投入も削除も正常動作なので、どこにも異常が出ない。

**適用方法:**

- 保持したい日数が決まっているなら、期限は **「保持したい日数 + 取り込み遅延」** に設定する。
  遅延に幅があるなら最悪値で取る。
- **最古の日が「今日 − 期限日数」にちょうど一致していたら、供給側の上限ではなく自分の設定で
  削っている。** 供給側の上限で止まっているなら最古の日は設定と無関係な日付になり、日が経っても
  前進しない。自分で削っているなら毎日 1 日ずつ前進する。この違いで判別できる。
- **バックフィルが完走するまで期限を入れない**（または投入され得る最大日数以上にしてから待つ）。
  投入は数日かかることがあり、途中経過は歯抜けに見える。後から期限を延ばしても、消えたものは戻らない。
- **既定の期限は、設定後に作られるものにしか効かない。** 入れ物を作った直後・中身が作られる前が
  唯一きれいなタイミング。逃したら既存分を数え上げて個別に設定する（数え漏らすとそこだけ無期限に
  溜まり続ける）。
- **遅延の異なるデータが同居する入れ物では、既定値ひとつで縛らない。** イベント単位（遅延は分）と
  日次集計（遅延は日）が同じ入れ物にあると、後者だけが不足する。
- 期限が約束するのは「これだけ残す」ではなく **「これより古いものを消す」**。ローリングで毎日末尾が
  消え、積み上がることはない。長期保持の義務があるなら、期限つきのホット層とは別に、
  削除されない退避層を用意する。ホット層の期限は照会の速さと費用の設定であって、証跡保全の設定ではない。

出所: 監査ログをデータウェアハウスへ書き出す構成の保持設計（2026-09）。

## 設定ファイル

### 手書き JSON/TOML は strict decode で読む

**事象:** ユーザーの設定ファイルにフィールド名のタイポ（`callbackSchema` — 正しくは
`callbackScheme`）があり、デフォルトの Unmarshal が黙って無視してデフォルト値に
フォールバック。「HTTPS を指定したのに http で来る」という症状の原因特定に時間を要した。

**適用方法:** ユーザーが手書きする設定は Go なら `json.Decoder` +
`DisallowUnknownFields()`、Python pydantic なら `ConfigDict(extra="forbid")` で読む。
テストで「typo フィールドが弾かれること」を 1 ケース入れる。
**機械生成データは逆に素の Unmarshal**（後方互換のため旧フィールドを無視させる —
上記「マシンローカル ID」の項参照）。使い分けが重要。

### 「保存先ディレクトリ」設定を変えても、絶対パスで永続化済みの参照は追随しない

**事象:** 導入済みの資産ファイル群を別ボリュームへ移し、設定の保存先ディレクトリ
（`models_dir` / `output_dir` / `cache_dir` 等）を新しい場所に書き換えた。しかし
**絶対パスを記録した registry / index / manifest** は旧パスのまま残り、既存エントリが
全て存在しないディレクトリを指す状態になった。

**なぜ:** 保存先の設定は「**これから**書き込む先」を決めるだけで、既に書かれた記録には
触れない。両者は別物なのに、利用者からは一つの「モデルの置き場所」に見える。

**適用方法:**
- 「保存先を変える設定」を作った時点で「既存分をどう移すか」まで設計する。README には
  移行手順を 3 ステップ（ファイル移動 → 設定変更 → reconcile）で明記する。
- **reconcile コマンドをセットで用意する。** dry-run 既定 + `--apply` で書き込み。
  張り替えるのは「記録パスが**存在せず**、かつ新ディレクトリに**同名ファイルが存在
  する**」ときだけ。現行パスで解決できるものは触らない（意図的に別ディレクトリへ置いた
  資産を壊さない）。候補が無いものは推測せず「未解決」として報告する。
- 対象ディレクトリを上書きする `--to DIR` を付けておくと、同じコマンドが**取り消し手段**
  になる（旧ディレクトリを指して再実行するだけ）。
- reconcile はレコードの書き換えに限定し、**バイト列の移動はしない**（利用者の `mv` の
  領分）。ファイル未移動のまま dry-run すれば「全件未解決」と正しく報告される。
- **ロード時の暗黙リベースは採らない。** basename で解決する以上、同名の別ファイルを
  無言で掴む余地があり、しかもディスク上の記録と実際に使われた値が食い違ったまま残る。
  黙って自己修復する状態は、自分の破損を報告する状態より読み解きにくい。明示コマンド +
  正直な一覧を選ぶ。
- 記録されたファイル欄を列挙する処理は 1 箇所（get/set アクセサを返す `fileRefs()` 的な
  もの）に集約する。列挙・不在検査・張り替えが別々に走査すると、フィールド追加時に
  片方だけ漏れる。実在判定を関数として注入すれば全て合成 FS でテストできる。

### 一覧・ピッカー・カタログは、参照先の実在を検査してから返す

**事象:** 導入済み一覧が registry を読むだけで **stat しなかった**ため、参照先ファイルが
不在でも全件が「導入済み・健全」と表示された。CLI 表・`--json`・MCP ツール・GUI 管理画面が
同じ未検査ビューを共有しており、実際にファイルを開く処理に入って初めて旧パスで失敗する。
「管理画面は認識しているのに、使おうとすると失敗する」という原因の分かりにくい症状になる。

**なぜ:** 検査していない状態を「健全」として提示したから。表示の情報源（記録）と真実
（ディスク）が別物であることを、どのレイヤも確認していなかった。前項のパス追随の欠如と
この不在非表示は**独立した 2 つの欠陥**で、重なると発覚が生成・実行時まで遅れる。

**適用方法:**
- 一覧系は返す前に参照先を stat する。不在は行に出す（`STATUS` 列 + 不在ファイルと対処
  コマンドを名指しするフッター）。外付けボリューム未マウントも同じ形 — ファイルは消えて
  いないが、一覧が「ある」と言ってはいけない。
- front-end へは bool ではなく**不在パスのリスト**（`missing_files`）を返す。原因表示まで
  作れる。空なら省略し、**キー欠落は「健全」に倒す** — 旧バージョンのクライアントでも
  壊れない。
- **front-end はロードできないものをピッカーから外すが、管理画面には残す**（見えないと
  直せない・消せない）。消えた理由の説明文も要る。「利用可能」と表示するものは必ず
  ロードできること。
- 実行時の解決層でも早期に弾き、不在ファイル・現在の設定値・対処コマンドを名指しする。
  下層ライブラリの低レベルエラーをそのまま見せない。
- 一覧が**単一の共有ビュー**から作られていれば CLI / JSON / MCP / GUI が同時に直る。
  表示面ごとにビューを組むと検査漏れが再発する。
- コストは呼び出しごとに O(files) の stat。不在・未マウントのパスは ENOENT で即座に
  失敗するため、縮退ケースほど速い。

### macOS の設定ファイルは Application Support と ~/.config の両方を探す

**事象:** ユーザーが `~/.config/<app>/config.toml` に認証情報を置いたのに、アプリは
`~/Library/Application Support/<app>/` しか見ておらず、「認証情報なし」と言い続けた。

**なぜ:** macOS には2つの慣習が併存し、CLI 利用者は macOS でも `~/.config` を第一の
置き場と考える。**設定ファイルが存在するのに黙って読まれない**のは、無いと言われるより
はるかに悪い（存在するのだから設定は済んだと考えてしまう）。

**適用方法:**
- 読み取りは優先順に探索する: `XDG_CONFIG_HOME/<app>` → `~/.config/<app>` →
  `~/Library/Application Support/<app>`。最初に存在したものを使う。
- 書き込み先（canonical）は Application Support のままでよい。分岐するのは config だけで、
  データディレクトリ（DB 等）は分けない。
- **診断コマンドは「実際に読んだパス」を表示し、無い場合は探索したパス一覧を出す**。
  この種の事故を一発で診断可能にする唯一の仕掛け。
- テストは `HOME` と `XDG_CONFIG_HOME` の**両方**を差し替える。片方だけだと開発者自身の
  実設定を拾って落ちる。

### 永続化した「判定結果」には再判定の経路を用意する

**事象:** 「このデバイスは対象か」をプローブして真偽値で保存していた。判定ロジックの
誤りを修正しても、**既に分類済みのレコードには届かなかった**。

**なぜ:** 設定値の migration と同じ失敗形だが、対象が「ユーザーの入力」ではなく
「こちらが導出した値」なので見落としやすい。ロジックを直せば直る、と錯覚する。

**適用方法:** 導出値を永続化するなら、**明示的な再判定コマンド／操作**（`--reclassify` 等）を
必ず用意し、それが唯一の移行手段であることをドキュメントに書く。コスト（API コール等）が
かかるなら既定にはせず、明示操作にする。

### 他人の設定を元に戻す機能では、意図ではなく観測を記録する

**症状:** 他プログラムの設定を変更し、元に戻す機能を持つツールで、一見無関係な
4 つの不具合が同時に出る——利用者が手で設定していた値の復元を拒否する、
利用者が設定していたキーを削除してしまう、書き込みが半分しか効かなかった後に
「他の何か」が設定を変えたと判定して後始末を拒否する、ツール外部で行われた変更を
黙って上書きする。menubar-spacer（macOS のステータス項目間隔設定、2026-09）で、
独立レビューが 1 つの書き込み層からこの 4 件を検出した。

**理由:** これらは 1 つの欠陥である。バックアップ記録がツールの**書こうとした内容**から
作られ、一方で読み取り層が**見たもの**を黙って作り変えていた。

- 記録の「適用した内容」フィールドが要求した目標値を保持していた。OS が片方のキーにだけ
  効かせた書き込みは、記録が実機と違う状態を記述したまま残す。復元経路はこのフィールドと
  実際の状態を比較して外部干渉を検出するため、ツール自身の中途半端な書き込みを
  他人の変更として分類した。
- 妥当性の範囲（0〜64）を**実機から読んだ値**に適用していた。手で設定された 100 は
  忠実に記録されたうえで、破損を守るはずのチェック自身によって拒否され、
  アプリ内に戻る道が無くなった。
- 値をツールが理解できる型に丸めていた。`defaults write -g SomeKey 8` は `-int` 無しでは
  **文字列**を書く。整数として読むと「未設定」になって返るため、復元は利用者が
  設定していたキーを削除する。小数は切り捨てられた。

**適用方法:**
- 記録の全フィールドを読み返しから埋める。要求からは埋めない。書き込み後に読み直して
  保存し直す。書き込みが失敗したときこそ、記録は実機を記述していなければならない。
- 検証は**ファイルをデコードするとき**に行う。**実機で観測した値**は検証しない——
  そこでの範囲チェックは、既定から最も遠い利用者、つまり最も復元を必要とする相手を
  正確に拒否する。
- 解釈できない値は逐語的に（property list の塊、生のバイト列として）保持し、
  そのまま書き戻す。「理解できない値」と「値が無い」を混同できないよう、
  独立したケースとしてモデル化する。
- 各キーが「元の値」か「最後に観測した値」のどちらかを持つ状態は、自分で後始末する
  対象として扱う。それ以外は外部干渉であり、取り消しは拒否し、明示的な新しい要求は
  実行したうえで何を置き換えたかを報告する。明示的な要求を拒むのは妨害であり、
  説明のつかない状態の上で取り消しを実行するのは破壊である。
- 戻る道を最初の書き込みより前に保存し、「読む → 判断 → 保存 → 書き込み」全体で
  排他ロックを保持し、実機の状態はそのロックの内側で読む。さもなければツールの
  2 つのコピーが、ツール自身が作った状態を利用者の元の状態として記録する。
- 読めない記録は削除せず退避する。しかも実際に書き込みを行った後にだけ退避する。
  読み取り失敗は一時的かもしれず、バイト列は人間にはまだ読めるかもしれない。

### 存在するキーは与えられた値である — `""`・NaN・番兵値を「未指定」と読まない

**症状:** 1 つのツールの独立検証で、同じ型が 3 箇所から出た。(1) 設定ファイルの
`base_url = ""` が、`if v != ""` のローダーで行ごと無視され、既定の URL が黙って使われた。
(2) TTL とタイムアウトは `strconv.ParseFloat` で読んで `x <= 0` を拒否していたが、`NaN` は
どんな比較も偽にするので素通りし、`Inf` や `1e300` は `time.Duration` を溢れさせた。
(3) CLI の `--min-cvss` は既定値 `-1` を「未指定」の番兵にしていたため、`--min-cvss -1` は
範囲外として拒否されず、絞り込み無しの一覧が絞り込み済みとして返った。

**なぜ:** 3 つとも「値の内容から、与えられたかどうかを推定している」。与えられたかどうかは
**存在**の問題で、値の問題ではない。推定が外れたとき起きるのは拒否ではなく黙殺で、利用者は
自分の指定が効いたと思い込む — 未知キーを黙って無視する設定ローダーと同じ欠陥である。

**どう適用するか:**
- 設定ファイルのキーは**存在で読む**（`if v, ok := section[key]; ok`）。空文字はそのまま
  検証器へ渡り、キー名を挙げて拒否される。「空なら未設定」と読んでよいのは環境変数だけ
  （空にするのが環境変数を消す普通の書き方だから）— その違いはコメントに書く。
- 数値は**範囲の内側**で受け付ける: `if !(f > 0 && f <= max)`。`f <= 0` の否定形は NaN を通す。
  上限は、型が溢れない値から決める。
- CLI フラグが与えられたかは `flag.Visit` に聞く。番兵値と比較しない。番兵にした値は、
  利用者が打てる値である。
- ページ上限のように「設定の上限」と「エンジンの上限」が同じ事実なら、片方が他方を import
  できなくても、両方を import するテストで等しいことを固定する。設定の既定値がツールの
  上限を超えるときは丸め、拒否するのは呼び出し側が明示した値だけにする。

### キャッシュキーを区切り文字で連結しない — 長さ前置きでハッシュし、大文字小文字を畳まない

**症状:** 結果キャッシュのキーを `kind + "_" + vendor + "_" + product` で作っていた。トークンは
`_` を含み得るので、vendor `a` + product `b_c` と vendor `a_b` + product `c` が同じスロットを
共有し、2 つ目の照会に 1 つ目の答えが返る。ファイル名として安全にするための小文字化は、
大文字小文字だけが違う識別子（ベンダーのアドバイザリ ID は大小混在）を同じスロットに畳んだ。

**なぜ:** 連結は、部品が区切り文字を含まないときだけ単射になる。入力ゲートが許す字種と
区切り文字の関係は、ゲートを緩めた日に黙って壊れる。

**どう適用するか:**
- キーは 1 つの関数でだけ作る。各部品を**長さ前置き**（`len:part|`）でハッシュに流し、
  `kind` + ハッシュの先頭をファイル名にする。手で連結しない。
- 部品の正規化（小文字化など）は、上流がその識別子を大小無視で扱うと**確かめた**ものに限る。
- 「衝突しそうな組」を並べたテストを置く: 区切りをまたぐ分割、空の部品、大小だけの違い、
  別の `kind`。エンジン越しに「2 つ目の照会が上流へ届く」ことも確かめる。

## ファイルシステム

### ボリューム空き容量を volumeAvailableCapacityForImportantUsage 単独で読まない

**事象:** 展開前に空き容量バジェット検査（ZIP 爆弾対策）を行う macOS アプリで、
SMB 共有上のアーカイブ展開が「空き容量が足りません — 必要: 414 MB / 空き: 0 KB」と
**全件拒否**された。サーバ側には 3 TB 以上の空きがあった。

**なぜ:** `volumeAvailableCapacityForImportantUsage`（purgeable 領域込みの
「実効空き」）が答えを持つのはローカル APFS ボリュームだけで、ネットワーク
マウント（SMB/NFS）では **nil ではなく 0 を返す**。値が「取れた」ように見える
ため、そのまま信じると「空き 0 = 満杯」と誤読する。statfs 由来の
`volumeAvailableCapacity` はネットワーク FS でも正しい値を返す。

**適用方法:**
- important-usage キーは**正の値のときだけ**採用し、0 以下は「回答なし」として
  `volumeAvailableCapacity` へフォールバックする。両方取れたら大きい方
  （ローカル APFS では purgeable 込みの方）。
- 本当に満杯のディスクは statfs も ~0 を返すので、フォールバック後も拒否は
  維持される — 安全側は崩れない。
- どちらも取れないときは検査をスキップする（値を捏造しない）。
- 判定は純粋関数に切り出してユニットテストする（`(0, 3TB) → 3TB`、
  `(0, 0) → 0`、`(nil, nil) → nil`）。

### rename による安全な置換はモードを落とす — 呼び出し側に決めさせると片方が間違える

**事象:** 「一時ファイルに書いて rename」で安全に置換する関数が、新規ファイルのパーミッション
を引数で受け取っていた。呼び出しは 2 箇所。片方は元ファイルを stat したモードを渡して正しく、
もう片方は `0644` リテラルを渡していた。後者を通ると、上書きのたびに実行ビットが落ち、`0600`
のファイルが `0644` に広がった。

**なぜ:** rename は inode を差し替えるので、モードは意図的に運ばないと消える。それを呼び出し側
の責任にすると「毎回正しく渡す」という規約になり、規約は破れる。

**適用方法:** 置換関数**自身**が、置き換える名前を lstat してモードを引き継ぐ。引数は「新規
作成時の既定」に降格するか、無くす。既存モードの適用は開いた fd への `chmod` で行う
（`OpenFile` のモードは umask に削られる）。ただし**新規作成には umask を尊重する** — 既定値を
umask 越しに強制すると、権限を狭めている環境で逆向きに同じ欠陥になる。継承するのは置換する
名前自身のモードだけで、シンボリックリンクの指す先ではない。

## OAuth

### refresh_token 無しのトークンは無期限扱いにする — 人為的な期限を捏造しない

**事象:** トークン交換レスポンスに `expires_in` が無いとき「now + 1 時間」の期限を捏造
していた。実際はプロバイダ（トークンローテーション無効の Slack 等）が無期限トークンを
発行していたため、1 時間後に「期限切れ + refresh 不能」でエラーになり、無期限トークンが
死んだ扱いになって毎時再ログインを強いた。

**適用方法:**
- `expires_in` 無し + `refresh_token` 無し → `expires_at = 0`（期限不明）として保存し、
  そのまま使う。実失効は上流の **401 で検知**してそこでエラー化する。
- `expires_in` 無し + `refresh_token` 有り の場合だけ「1 時間後に再確認」等の探索値が妥当。
- 「`expires_at` が保存時刻ちょうど +1h」は捏造期限を疑うサイン。

### プロバイダによっては http:// ループバック redirect_uri を拒否する

**事象:** RFC 8252 は `http://127.0.0.1:<port>/callback` を推奨するが、一部プロバイダの
アプリ登録 UI は `https://` 以外を完全拒否する（仕様違反ではない — RFC はクライアント側の
推奨であってプロバイダに受け入れ義務を課していない）。

**適用方法:** HTTPS ループバック経路を用意する:
1. ephemeral 自己署名証明書を生成（IP SAN: 127.0.0.1 + ::1、DNS SAN: localhost、
   ECDSA P-256、短い有効期限、メモリ内のみ）。
2. `tls.NewListener` で TCP リスナーをラップ。
3. redirect_uri は `https://localhost:<port>/callback`（IP リテラルも拒否する UI がある
   ため DNS 名で）。
4. 「ブラウザ警告は想定内、1 回クリックスルーで OK」とユーザー向けに明記する。

## ターミナル・入力 UI

### 複数行ペーストは単行読み取りだとシェルに漏れる

**事象:** 対話プロンプトで `bufio.Scanner` の単行読み取りをしていたところ、ユーザーが
複数行テキストをペーストすると 2 行目以降がシェルに漏れ、**コマンドとして実行され始めた**。

**適用方法:**
- 対話入力は「空行で終了」の複数行読み取りモードにする。
- 長い入力は `--input` フラグでファイルから読めるようにする。
- Scanner のバッファはデフォルト 64KB から拡大しておく。

### 入力履歴ナビゲーションは「ナビ中フラグ」必須

**事象:** ArrowUp/Down の履歴ナビを実装した際、通常入力中に行末で ArrowDown を押すと
履歴ナビ動作が誤発火し、draft（空文字）で入力が上書きされて**入力中の内容が消えた**。

**適用方法:**
- ArrowDown ハンドラの先頭で「履歴ナビ中でなければ return」を入れる。
- ナビ中のときだけ keypress を consume し、それ以外はデフォルト動作（カーソル移動等）に
  委ねる。
- 一般化: history navigation / autocomplete / IME 連携など「特定状態の時だけキーを奪う」
  UI は、状態フラグの確認を最初に入れる。

### UI 言語の混在は翻訳ではなく「完全二面カタログ + 完全性テスト」で直す

**事象:** CLI の対話 UI（ヘルプ・ヒント・ダイアログ）が日英混在になった。個々の文字列は
その時々の言語で追加されており、どれも単体では誤りでない。混在を一度手で直しても、
次の機能がまた片言語で文字列を足せば元に戻る — 問題は誤訳ではなく「2 言語に同じ面を
覆わせる強制力の不在」。

**適用方法:**
- 文字列 1 本につき 1 フィールドの `Messages` 構造体を 1 つ定義し、言語ごとの完全な
  リテラルを 2 面用意する（gem-agent `internal/uitext`）。
- **リフレクションテストで「どちらかのカタログに空フィールドがあれば失敗」させる。**
  このテストこそが修正の本体 — 新しい文字列は両言語に入るか CI に落ちるかになる。
- `%d`/`%s` を含むフィールドは fmt 動詞の並びが両カタログで一致することもテストする
  （ずれてもコンパイルは通り、片言語だけ実行時に壊れる）。
- 言語解決は POSIX 慣行（`LC_ALL` → `LC_MESSAGES` → `LANG` の最初の非空値、`ja` 接頭辞
  判定、`C`/`POSIX` は英語）。起動時に 1 回だけ解決する — 途中切替はスクロールバックを
  二分する。
- **対象外を先に宣言する**: grep されるログ体裁の行・`--help`（CLI 慣行）・モデル向け
  テキスト・ライブラリ由来のエラー連鎖は英語のまま。全部を訳そうとすると英語の連鎖に
  訳語の接頭辞が付き、除去したかった混在が戻る。

### 他プロセスが読むマーカー/フラグファイルは temp+rename で置く（os.WriteFile は create→write の 2 段階）

**事象:** プロジェクト所有者を記録する `.project` マーカーを `os.WriteFile` で書いて
いたところ、同一プロジェクトの並列起動の約半数が「path-escape collision」で誤って
起動拒否された。WriteFile は O_CREATE|O_TRUNC で**空ファイルを作ってから**内容を書く
ため、その隙間に別プロセスが読むと「所有者 = 空」に見える。

**適用方法:**
- 別プロセスが読み得るマーカー/フラグ/小状態ファイルは、同一ディレクトリの temp
  ファイルに書き切ってから `os.Rename`。rename は原子的なので、読み手には「無い」か
  「全文」しか見えない — どちらも安全に解釈できる 2 状態にしておく。
- **空ファイルは「所有者不明」として欠如と同義に扱い、次の書き手が修復する**
  （旧実装のクラッシュ残骸への耐性）。
- 検査→書き込みの TOCTOU が残っても、それが「best-effort の識別子であってロックでは
  ない」なら後勝ち rename で十分 — その割り切りはコメントに明記する。

### クラウドストレージの Writer は Close で「確定」する — 中断はコンテキストのキャンセルで

**事象:** GCS へのアップロードで `io.Copy` が途中失敗した際、後始末のつもりで呼んだ
`w.Close()` が**バッファ済みの部分データを完成オブジェクトとして確定**した。
content-addressed ストア（ハッシュ名・削除なし）だったため、壊れた内容が正しい名前で
恒久保存され、以後の重複排除が壊れた内容を配り続ける汚染になった。

**適用方法:**
- `cloud.google.com/go/storage` の Writer は「Close = コミット」。エラー経路の Close は
  クリーンアップではなく部分コミット。**中断は NewWriter に渡した context のキャンセル**
  が公式の手段 — writer 専用の `context.WithCancel` を切り、copy 失敗時に cancel して
  から Close する。
- content-addressed ストアでは「名前 = 内容」の不変条件そのものを守る: ハッシュ計算と
  アップロードは**同一 fd** で行い（パスで開き直すと rename 置換に負ける）、アップロード
  ストリームを再ハッシュする検証リーダーで「書き込み中に変わったファイル」を EOF 前に
  失敗させる。恒久ストアの誤登録は「後で直せない」前提で設計する。

### exec のキャンセルは「直接の子」しか殺さない — パイプを握る孫が Wait を永久に塞ぐ

**事象:** エージェントのシェルツール（sandbox-exec → bash → python）で、タイムアウトも
オペレーターの Ctrl+C も効かず永久ハングした。`exec.CommandContext` が kill するのは
直接の子だけで、孫の python は生き残り、継承した stdout/stderr パイプを握り続ける。
`CombinedOutput` 内部の `Wait` はそのパイプの EOF まで戻らない — **タイムアウトは発火
した上で無力化され**、その後の cancel も同じ Wait で詰まる。「ツールが応答しない」と
「中断できない」は同一の穴の 2 症状だった。

**適用方法:**
- 子を持ち得るコマンドは必ず: ① `SysProcAttr.Setpgid = true` でプロセスグループ
  リーダー化、② `cmd.Cancel` で **グループへ** SIGKILL（`syscall.Kill(-pid, SIGKILL)`）、
  ③ `cmd.WaitDelay`（数秒）を設定 — setsid/二重 fork で逃げた相手でも Wait は返る。
  kill は best-effort、**リターンは保証**、と割り切る（孤児 1 匹はセッションのハング
  より遥かに安い）。
- 再現テストは `bash -c 'sleep 30 & sleep 30'`（背景の子がパイプを継承）+ 短い
  タイムアウト/cancel + 数秒の水番。修正前は必ずハングする。
- UI 側にも多層防御を: キャンセル無視のツールに備え、中断中の再 Ctrl+C ×2 で警告 →
  ×3 で終了、の脱出はしごを用意する（記録が追記型なら「ここまでは保存済み」と言える）。

### プロセス内の走査にも「復帰は保証」の契約を — ctx を受け取るだけのツールは Ctrl+C を無視する

**事象:** エージェントのファイル検索中に Ctrl+C を押しても「中断中…」のまま
走査が続き、遅いファイルシステムでは残り走査時間がそのまま待ちになった。
`search_files`/`list_tree` は `ctx` を引数に取るだけで一度も `ctx.Err()` を見ず、
呼び出し側も `tool.Run(ctx, …)` を同期呼び出しして床を持たなかった — Ctrl+C が
することは「誰も読まない context をキャンセルする」だけだった。exec の孫問題
（上のエントリ）をシェルで直しても、プロセス内ツールには同じ契約が無かった。
忠実に写したプローブ（30k ファイル・SSD）で、20 ms のキャンセル後に出荷形は
1.6 秒（全走査）、dir/file ごとの ctx チェックは 2 ms、goroutine+select の
ラッパーは 1 ms で返った。

**適用方法:**
- 2 層で守る。①**協調**: walk はディレクトリ読み・ファイル読みの前（長い
  ファイルは N 行ごとにも）に `ctx.Err()` を見て、見つけた分を「[interrupted
  after N files — partial]」のラベル付きで返す（部分結果は結果であってエラー
  ではない・切り詰めを黙らせない）。②**床**: 呼び出し側は `Run` を goroutine
  で走らせ `ctx.Done()` と select、キャンセル後は短い猶予（1 秒程度）だけ協調
  復帰を待ってから放棄する — blocking syscall（ハングした NFS/SMB の ReadDir）
  は Go では止められないので、①だけでは足りない。停止は best-effort・復帰は
  保証、が exec と同じ規則
- 猶予は「協調復帰が競争に勝つ」長さにする: 健全な FS なら syscall 1 回分で
  戻るので短くてよいが、**exec の `WaitDelay` より長く**しないと、逃亡者が
  パイプを握ったシェル呼び出しの出力を床が一足先に捨てる。順序はテストで固定
- 床の外に置くもの: 承認ゲートと、**オペレーターの入力を待つツール**
  （ask_user）。放棄した stdin 読みは「共有 stdin の 2 人目の読み手」になり、
  次に打った行を黙って食う。ツール定義にフラグ（WaitsOnOperator）で名乗らせる
- 放棄したものは計上する: 実行中の放棄数を終了レシートに、遅れて戻ったら
  監査レコード、**変更系**が遅れて完走したら次ターン冒頭でモデルに告げる
  （モデルの最後の言葉は「結果は破棄」で、書き込みは着地している）
- 脱出はしごは全入口に: `signal.NotifyContext` は登録中の 2 回目以降の SIGINT
  を握り潰す。TUI だけに 3 回押し終了を作ると素の REPL/-p には脱出口が無い。
  呼び出し箇所はソース走査テストで固定
- 再現は FIFO で決定論化できる: walk の先頭ディレクトリに mkfifo し、テスト側
  が書き込みオープンで「walk が read に入った」ことを同期 → cancel → close で
  EOF を与える。修正前は後続ディレクトリまで走り、修正後は次のチェックで戻る

### Go TUI の幅モデルは 1 つに揃える — go-runewidth は CJK ロケールで曖昧幅文字を全角にする

**事象:** Bubble Tea + glamour の TUI で、コードブロックに入れた罫線アート（ER 図）が
**文字を含む行だけ箱の間隔が広がり、罫線だけの行は正常**という形で崩れ、さらに
スクロールバックの hard wrap で行の尻尾が千切れた。`LANG=ja_JP.UTF-8` では
go-runewidth が `EastAsianWidth=true` になり、East Asian Ambiguous の罫線文字
（─│┌┐├┤）・矢印（►◄）・「…」を 2 セルと数える一方、同じプロセスの x/ansi・uniseg と
一般的な端末設定は 1 セルと扱う。glamour はコードブロック各行の詰め物を go-runewidth で
計算するため、罫線が多い行ほど「既に広い」と見なされて詰め物が減り、行ごとに実幅が
ばらついた（実測: 連続する行で 176/125/172/125 セル）。`LANG=C` では全行 176 で均一。

**適用方法:**
1. **プロセス内の幅計測器を 1 つのモデルに揃える**: 起動時に
   `runewidth.DefaultCondition.EastAsianWidth = false` を固定する（x/ansi・uniseg・
   大半の端末と一致）。ただし `RUNEWIDTH_EASTASIAN` が明示設定されていれば尊重する —
   曖昧幅を全角描画する端末の利用者に opt-in を残す。
2. 幅を測る依存を新たに入れたら、**テストで `EastAsianWidth = true` にした状態で**
   罫線を含む行を描画し、全行の実幅が等しいことを固定する（ロケール依存のバグは
   開発機の `LANG` 次第で再現しないため、テストで意図的に再現する）。
3. 症状の見分け方: 「文字を含む行だけズレ、罫線だけの行は正常」なら幅計測の不一致、
   「罫線を含む行だけズレ」なら端末側の曖昧幅設定を疑う。

### Bubble Tea の bubbles 部品は Focus() をモデルへ格納する前に呼ぶ

**事象:** TUI の承認ダイアログへ後付けした textinput の 1 行入力欄が、
プレースホルダもカーソルも表示されるのに全キー入力を無視した（1 文字も
入らない）。配線は正しく見え、ユニットテストの Value() 検査だけが落ちた
（Go CLI エージェント、2026-08）。

**なぜ:** Bubble Tea のモデルは Update ごとに値コピーで引き回される。
`ti := textinput.New()` → 設定 → `m.input = ti` → `ti.Focus()` の順に
書くと、Focus（ポインタレシーバ）はローカル変数だけを変更し、モデルに
格納済みのコピーは unfocused のまま残る。textinput.Update は unfocused
のときキーを黙って捨てるため、エラーも panic も出ずに「入力できない欄」
になる。noCopy 型の panic（strings.Builder 等）と同根の値コピー問題だが、
こちらは音を立てない分たちが悪い。

**適用方法:**
1. 順序を固定する: 生成 → 設定 → **Focus()（戻り値の tea.Cmd を保持）→
   最後にモデルへ代入**。カーソル点滅はその tea.Cmd から始まるので
   捨てない。
2. bubbles 部品をモデルへ足すたびに「ポインタレシーバの呼び出しがコピー
   前に済んでいるか」を問う — 「この型は値コピーに耐えるか」チェックの
   追加項目。
3. 回帰テストは「モデルへ格納後に KeyMsg を流し、Value() が変わる」こと
   を固定する。表示検査（View に欄が出るか）では捕まらない。

### Bubble Tea の `Program.Send` を Update の呼び出しスタックから呼ぶと UI ごと固まる — Update 内で走るコールバックは一見それと分からない

**事象:** TUI が入力を一切受け付けなくなり、Ctrl+C も Ctrl+D も効かず、外から
kill するしかない状態になった。**同じ機構で 2 回起きている** — 1 回目は slash
コマンド（`/clear`）からフック実行を経て `prog.Send` に至る経路、2 回目は別の
slash コマンドが画像を画面へ送る経路（2026-09、エージェントの TUI）。

**なぜ:** Bubble Tea v1 の `msgs` チャネルはバッファ無しで、そこから読むのは
Update を回している goroutine だけである。Update の呼び出しスタックの中から
`Send` すると、自分が返るまで誰も読まないものを待つことになる。以後のキー入力も
同じチャネルに詰まるので、raw mode では Ctrl+C すら「ただのキー」として詰まる。

見つけにくいのは、**Update の中で走るコールバックがそう見えない**ことにある。
slash ハンドラ・設定変更の適用・フック実行は、いずれも「UI とは別の層」として
書かれていながら、実体は `Update` から同期に呼ばれる。同じ関数が起動時
（program がまだ無い）やターン中（別 goroutine）には正常に動くので、コードを
読むと「Send は動いている」に見える。

**適用方法:**
- Update から同期に呼ばれうるコールバックに Program を渡さない。通知は
  **コールバックの戻り値**で返す（slash 出力に同梱すれば順序も決定的）。
- どうしても送るなら `go prog.Send(...)` にする。順序保証は失うので、「届いたか」
  を戻り値で名乗らないこと。呼び出し側が使えるのは「送り先があるか」までである。
- レビュー観点: `prog.Send` の**呼び出し元を全数列挙**し、それぞれに「この関数は
  Update から同期に呼ばれうるか」を問う。1 つでも「はい」があれば固まる。
- 回帰テストは**戻らない sender** を束ねて「呼び出し側が戻ること」を固定する
  （同期送信版はタイムアウトで落ちる）。単体テストは全部緑のまま UI だけが死ぬ
  クラスなので、この形の固定が無いと次も実機まで分からない。

### Go の `flag.FlagSet.Output()` は stderr — 人が読むレポートも明示的に stdout へ

**事象:** サブコマンドの整形レポートを `printReport(fs.Output(), …)` と書いた
ツールで、`--json` 出力は stdout に出るのに、テキスト版だけが stderr に出ていた
（使用量集計 CLI、2026-09）。単体テストは `io.Writer` を注入していたので緑のまま。
独立検証者が `2>/dev/null` を付けて実行し、何も出ないことで発見した。

**なぜ:** `flag.FlagSet.Output()` は usage / エラー用の writer で、既定は
**os.Stderr**。「FlagSet が持っている writer」は出力先として手近に見えるが、
用途が違う。テストが writer を注入する設計だと、本番の 1 呼び出し箇所だけが
検査から漏れる（「依存注入した機能は本番の 1 呼び出し箇所が最弱点」の一例）。

**適用方法:**
- レポート・データはすべて `os.Stdout` を明示して渡す。`fs.Output()` は
  usage とフラグエラー専用と決めておく。
- リリース前の実機シミュレーションに `<cmd> 2>/dev/null` を 1 本入れる —
  stdout に出るべきものが消えないかを機械的に見る。
- util-series の「stdout は data、UI/診断は stderr」の規約に照らすと、
  `--json` と同じ内容のテキスト版は data 側。

### 子プロセスの「誰のために動くか」は推測せず、起動行のパラメータで手渡す

**事象:** ランタイム（Claude Code / gem-agent）が spawn する MCP サーバに、自分が
仕えるセッションを知らせる必要があった。最初は子プロセスの環境変数
（`CLAUDE_CODE_SESSION_ID` / `GEMAGENT_WORK_DIR`）からランタイムを推測したが、
Claude Code のシェルから起動した gem-agent の MCP 子は**外側の Claude Code
セッション**を拾った — 環境変数は入れ子起動で継承される。親 pid で「最も近い
ランタイム」を選ぶ第 2 版も、このケースを塞いで次のケースを発明するだけだった。

**適用方法:**
- 子プロセスの CLI に `--agent <名前>` `--session <id>` `--project <dir>` のような
  **明示パラメータ**を持たせ、登録行（mcp.json / hook 設定）で渡す。子のコードは
  ランタイム固有の変数名を一切知らない。
- 値の**展開はランタイム側に任せる**: 自プロセスで `Setenv` 済みの変数を設定
  ファイルの `${VAR}` で展開できるランタイム（gem-agent の mcp.json）にはリテラルで
  渡す。**子にだけ渡す値は展開できない**ランタイム（Claude Code は
  `CLAUDE_CODE_SESSION_ID` を子に設定するが `.mcp.json` の `${…}` は自プロセス環境
  から展開する — 実測: `${CLAUDE_PROJECT_DIR}` はリテラルのまま、入れ子では外側の
  セッション id）には `--session-env <VAR>` のように**変数名**を渡し、子が自分の
  環境から読む。
- 解決できない値（空、未展開の `${…}`、`$VAR`、空白入り）は黙って採用せず
  「unknown」として動作を縮退し、結果と usage で告げる。未展開の `$VAR` を採用すると
  その登録行から起動した全インスタンスが 1 つの共有識別子になる。
- ランタイム側は、子が必要とする事実（セッション id・プロジェクトディレクトリ・
  作業ディレクトリ）を**同じ要素の組**で export し、識別子の一意性を保証する
  （gem-agent ADR-0071: タイムスタンプ id はプロジェクト内でしか一意でなかったので
  UUID に変更）。
- 実測手順: 引数と環境を dump するだけの probe サーバを登録して `-p` で走らせる。
  展開の有無と値の出所は、これでしか分からない。

### SQLite FTS5 の既定トークナイザは日本語を 1 トークンにする — trigram にし、3 文字未満は走査で答える

**事象:** FTS5 を既定（unicode61）で作ると、空白と句読点でしか語を切らない。
「gem-agent からの返信テスト」は「からの返信テスト」が 1 トークンになり、
「返信テスト」で MATCH しても 0 件。鉤括弧で区切られた語だけ当たるので、
英語のテストでは気付けず、日本語の実運用で初めて露見した。

**適用方法:**
- 日本語を検索対象にする FTS5 表は `tokenize='trigram'` で作る（SQLite 3.34+、
  modernc.org/sqlite でも使える）。どの文字体系でも 3 文字以上の部分文字列に当たり、
  大文字小文字は単純な Unicode 写像で畳む。既存表は DROP → CREATE →
  `INSERT INTO t(t) VALUES('rebuild')` で content 表から再構築（external-content
  表ならトリガーも作り直す）。
- trigram は 3 文字未満の語に**決して当たらない**。素の問い合わせにそうした語が
  あればアプリ側で走査に切り替える。走査の大文字小文字畳みは **Go 側で**
  `strings.ToLower` する — SQLite の `LIKE` と `lower()` は ICU 無しでは ASCII しか
  畳まず、経路によって答えが変わる。
- 部分一致は長い語の内側にも当たる（"swarm" の中の "warm"）。結果に本文を出し、
  読み手に検証させる。
- テストは日本語の本文で書く。英語だけのテストは既定トークナイザの欠陥を通す。

## 相手が返す義務のない応答を、次の送信の条件にしない

**何が起きたか:** リモートデスクトップのクライアントがゲストにモニタ構成を送り、最初の 1 通が
応答されるまで次を送らない実装になっていた。その上を走るトランスポートは、当該メッセージを
ハイパーバイザ側で消費し、設計上応答を返さない。結果として最初の要求が接続の寿命いっぱい送信側を
掛け金で止め、以後のリサイズはキューに入って捨てられた。その間もセッションは「リサイズ可能」と
報告し続けるので、操作者には無言の故障になる。再接続すると解けるため、手動試験では捕まらなかった
（spice-client、2026-09-18）。

**適用方法:** 応答で開いたままにする「送信窓 1」が安全なのは、プロトコルがその応答を**要求している**
場合だけである。任意である場合や、複数あるトランスポートの 1 つが省く場合、窓にはもう 1 つの閉じ方が
要る。タイムアウト、新しい版が古い版を無意味にする要求に対する上書き規則、あるいは窓を設けないこと。
レビューで探す形は、「in flight」フィールドの解除経路がちょうど 1 本しかない状態機械と、その
フィールドが詰まっている間も機能を広告し続ける capability フラグである。

残すべきものを残した修正は、窓を廃止することではなく in flight に期限を付けることだった。合体は
ドラッグ中も相手を守り続け、生存性は肝心の場合、つまり古い要求の後ろで新しい要求が待っている場合に
戻る。安全にするための細部が 2 つある。失効した窓でキューが空なら何も送らないこと。さもないと
生存性が、相手が既に持っている状態の再送ループになる。もう 1 つ、失効後に届いた応答はその時点で
in flight のものを acknowledge するので、イベントを外に出すなら「最新が勝つ」と述べ、対応関係が
保たれたふりをしないこと。

## goroutine で読んだ端末問い合わせは reader を残す — そしてそれが次の入力を取る

**症状:** 起動時の能力プローブが `/dev/tty` に問い合わせを書き、応答を goroutine で読み、判定が
出た時点で return していた。goroutine は `tty.Read` でブロックしたまま残った。macOS の `/dev/tty` は
kqueue に載らないので Go はブロッキングのディスクリプタとして開き、すでに read に入っている読み取りは
`Close` では起きない（close は read が返るまで遅延される）。Apple Terminal で 3 回中 3 回実測:
`Close` が返った 300 ms 後、残った reader が、*次の*問い合わせ——`theme = "auto"` の背景色検出——が
待っていた OSC 11 応答を受け取り、その問い合わせは既定値へ落ちた。暗色プロファイルでは既定値が偶然
正しく、何もおかしく見えなかった。テーマ固定なら同じ read がオペレーターの最初の打鍵を飲み込む。
これは 2 つ目の欠陥も隠していた: パーサは最初の応答で止まり、その後ろの device-attributes 応答を
読んでいなかった。残った reader がそれも飲み込んでいたので気づかれなかっただけである。

**なぜ:** 端末の応答にはタグが無い。読んでいる者がそれを受け取り、先に始めてブロックしている
`read(2)` がたいてい勝つ。問い合わせの終わりは「答えが出たら return」ではなく「自分の何も、もう
読んでいない」である。

**どう適用するか:**
- 応答は呼び出し側の goroutine で読み、待ちはすべてディスクリプタへの `select(2)` で区切る。
  `poll(2)` ではない: macOS は `/dev/tty` で使えない。ディスクリプタは `FD_SETSIZE` で守る
  —— `FdSet.Set` は無検査で添字を引く。
- 問い合わせが求めた**最後の**応答まで読む。他人の問い合わせへの応答は絶対オフセットで読み飛ばす
  （再スライスして再帰した実装は、既に通り過ぎた応答を忘れた）。
- 疑似端末でテストし、性質そのものを述べる: プローブが返った後に端末が送ったバイトは、次の reader が
  読める。このテストは旧コードに対して全判定で失敗した。スイートの他の何も端末に触れていなかった。
- 実機では、偶然では正しくなり得ない観測量で確かめる —— 次の問い合わせが解釈した色（`#161821`）
  対フォールバック（`#000000`）。「暗いか明るいか」ではない。

## 時間の予算は、その仕事の持ち主が一度だけ宣言する

**症状:** ハンドシェイクは startup timeout の下で走り、その内側の呼び出しヘルパが per-call timeout を
上から重ねていた。するとすべてのタイムアウトが per-call の値で報告され——自分の 30 秒で諦めた
ハンドシェイクが「timed out after 1m0s」と言い、オペレーターを誤った設定へ向かわせる——しかも短い方の
期限が勝つので、call より*長く*設定した startup 予算は、リファレンスが両者を「別々」と呼んでいるのに、
call の値で黙って切られた。最初の修正が正しい値を名指したのは `initialize` だけだった: 最初の
`tools/list` は素の `context.WithTimeout` で張られた同じ外側の期限の下で走り、相変わらず call の予算の
せいにした。

**どう適用するか:** 予算を値として context に載せ、2 つ目を足すことをヘルパに拒ませる（`withBudget`:
既に予算を宣言している context はそれを保つ）。エラー文は context にある予算を名指し、構造体の
フィールドを名指さない。外側のフェーズが期限を張るところは、必ず同じヘルパを通す —— 連鎖のどこかに
素の `WithTimeout` が 1 つあれば、誤った値が戻ってくる。

## 検査済みの数値でも Duration がゼロになり得る — そしてゼロは決して「とても短い」を意味しない

**症状:** NaN を拒むために範囲を内側形に直した後も、`--timeout 1e-10` は通った: 0 より大きく、しかも
0 ナノ秒である。`time.Duration(1e-10 * 1e9)` は 0 で、設定ローダーはそれを「上書きなし」、
`http.Client` は「タイムアウトなし」と読む。書ける最小の値が、最大として振る舞った。

**どう適用するか:** 変換を 1 つの関数にまとめ、結果が `<= 0` なら拒否させ、すべての単位・すべての入口
（フラグ・環境変数・ファイル）で使う。同じ掃討からもう 1 つ: 見つかったツールで直した教訓は、コピー元の
兄弟 6 本でも、同じツールの*もう一方の*入口でも直っていなかった（設定は直り、フラグは直っていなかった）。
範囲検査を直したら、その日のうちにフリート全体を古い形で grep する。

## 手元にあるパスはテキストではない — テキストからパスを探す文法に通し直さない

**症状:** `/show <path>` コマンドが、引数の前に `@` を付けて、チャット入力用の `@参照` パーサへ渡して
いた。そのパーサは最初の空白で参照を終える。流れる文章を読むのだから、それで正しい。
`/show Screenshot 2026-09-21 at 10.00.00.png` —— macOS がすべてのスクリーンショットに付ける名前 —— は
「Screenshot」を探した。コマンド自身のテストは偽の resolver を渡していたので、証明できたのは「空白が、
それを失う層*まで*届く」ことだけだった。

**どう適用するか:** resolver にパスを受け取る入口を与え、テキスト文法の側がそれを呼ぶようにする。逆では
ない。端末が届ける形を受け入れる —— 1 組の引用符、あるいはバックスラッシュ付きの空白（ファイルを
ウィンドウへドラッグすると入力される形）—— そして何も展開しない。

## 推測した値は、事実と別の印を付けて記録する — 比べるのは事実だけ

**事象:** image-forge に「LoRA / ControlNet の学習元のアーキテクチャがモデルと違えば、生成前に拒む」確認を入れた
（2026-09-22）。登録簿のアーキテクチャには、カタログの値、`--arch` で指定した値、名前からの推測
（`profile.Detect`。何にも当たらなければ SDXL）が区別なく入っていた。推測を事実として比べると、名前に
`sd15` を含まない SD1.5 モデル（例: `dreamshaper_8`）が SDXL と記録され、SD1.5 用の LoRA がすべて拒まれる。
同じ値で候補を絞っていた GUI は、前からそれを一覧から消していた。`--arch` も検証されず、`pony` や `SDXL` が
そのまま「事実」になっていた。

**なぜ:** 既定値つきの推測は、区別の印が無ければ事実と見分けられない。記録した時点では無害でも、後から
その値で拒否や絞り込みをする機能が来た時点で、推測が判定を下す。

**どう適用するか:**
- 値と一緒に出どころ（例: `catalog` / `flag` / `detected`）を記録し、拒否・絞り込みに使うのは事実だけにする。
  出どころを記録する前の登録は、事実だと確かめられるもの（カタログ自身の項目）だけを信用する。
- 出どころを決める処理は 1 か所にまとめ、書く側（登録）もテストする。読む側だけのテストでは、登録がすべてを
  事実と記録しても通る。
- 利用者が与える値は検証する。検証の無い自由記述は、比べる瞬間に「事実」として扱われる。
- 一覧の出力にも印を載せる（`arch_trusted`）。フロントエンドが同じ規則で絞り込めるように。

### 排他的な時刻境界を粗い精度へ変換するときは、下限と上限を同じ向きに丸めない

**事象:** scatのSlack専用化（2026-09）で、RFC3339の小数秒を受け取り、マイクロ秒精度の
API境界へ変換した。終了時刻 `.123456789` を `.123456` に切り捨てて排他的な上限として
送ると、元の終了時刻より前にある `.123456` のメッセージが欠落した。
独立レビューで発見し、合成データによる回帰テストで確認した。実サービスでの新しい観測ではない。

**なぜ:** 入力時刻の精度と、データが存在する格子の精度が異なる。排他的な比較を維持したまま
両端を切り捨てると、下限では適切でも上限では集合が狭くなる。

**適用方法:**
- マイクロ秒格子上の値を `start < value < end` で選ぶなら、startは切り下げ、endは必要な場合だけ
  切り上げる。ちょうど格子上の時刻は変更しない。
- `.999999999` の上限を次の秒へ繰り上げるケースを含め、境界直前・境界上・境界直後をテストする。
- timestampの識別子をfloat64へ変換しない。秒と小数部分を整数として扱う。
- 期間が親を選ぶのか全メッセージを選ぶのかは別の仕様であり、丸め修正で黙って変更しない。

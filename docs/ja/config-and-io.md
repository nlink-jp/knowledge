# 設定・識別子・CLI 入出力

設定ファイルの読み込み、識別子の canonical 化、ファイルシステム、OAuth、
ターミナル入出力に関する知見。
各項目は「事象 → なぜ → 適用方法」。

---

## 識別子・データ形式

### wire 形式の不一致は「ソースの canonical 化」と「境界の正規化」の両方で直す

**事象:** LLM に送る tool 名の形式（kebab vs snake）が一部バックエンドで受理されず
dispatch に失敗した。「境界正規化のみ」（ソースは kebab のまま）はソースが嘘をつく状態に
なり却下。「ソースリネームのみ」は古いセッション履歴・scaffold 済みユーザーデータ・
外部サーバーの publish 名が壊れる。

**適用方法:**
- **コントロールできるもの（ソース）**はコード上の綴りを wire と一致する canonical 形に
  リネームする。ソースが嘘をつく状態は読者の認知負荷を恒久的に増やす。
- **コントロールできないもの（外部入力）**は単一の `canonicalize()` helper を registry
  境界（lookup / dispatch ingress / schema emit / 永続化設定のロード）で適用して透過する。
- どちらか片方では不十分。「dispatcher だけ alias 受け入れ」は schema が嘘をつき続ける
  負債になる。

### canonical 形を変えたら、ユーザー設定ファイルもロード時に migrate する

**事象:** ルックアップ側だけ canonical 化した結果、過去に保存されたユーザー設定
（override map / disabled list の key が旧形式）が hit せず**静かに無視される**状態に
なった。ユーザーは「設定した記憶があるのに効いていない」silent failure を踏む。

**適用方法:**
- 識別子変更を計画したら、grep で「その識別子を key として永続化している箇所」を全て
  列挙する（config、セッションメタデータ、export/import 形式等）。
- migration は**ロード時 1 回の in-place rewrite** が最小実装（次の save で canonical 形が
  書き戻される）。旧・新 key が並存する縮退ケースは canonical 優先で OK。
- 注意: 構築済みオブジェクトに直接設定値を流すテストは migration 経路を通らない。
  両方の入力形を検証するテストにする。

### マシンローカルな ID をクロスマシン可搬データに持たせない

**事象:** export/import されるデータに、タイムスタンプ由来のセッション ID
（`sess-<unixMilli>`）への参照が含まれていた。マシン間では壁時計のミリ秒空間を共有する
ため**ほぼ確実に衝突**し、将来その参照を使う機能が「別セッションに作用」する潜在バグに
なる。しかも該当フィールドは write-only の死蔵だった。

**適用方法:**
- **YAGNI**: read 0 件の provenance フィールドはスキーマから削除する。残す/消すは
  フィールド単位で実 set/read を grep 確認。
- どうしても残すなら import 境界で**外来 ID を無条件クリア**する（ローカル一覧と照合して
  残す案は偽リンクを作るのでより悪い）。
- export は `kind` + `schema_version` のエンベロープで包んで誤ファイルを fail-fast 拒否。
  import はマージ・重複スキップを既定に（非破壊・冪等）。
- 機械生成 JSON は素の Unmarshal（strict なし）なら旧キーは無視され次回 save で消える =
  マイグレーション不要。

### 長形式で保存すると、取り込み直しが冪等になる

**事象:** 外部サービスの履歴を後から取り込んで穴を埋めたい。エクスポート範囲は重複しがちで、
二重投入や取りこぼしが起きやすい。

**なぜ:** 「1行 = 1 レコード、その主キーがレコードの同一性そのもの」という形にすると、
`INSERT OR IGNORE` がそのまま「足りない分だけ入れる」動作になる。逆に「1行に複数項目を
カラムとして並べる」形だと、部分的な重複をアプリ側で判定するはめになる。

**適用方法:**
- 時系列は `(対象, 項目, 時刻) → 値` の長形式にする。主キーがそのまま冪等性を与える。
- 副次的な効能として、**未知の項目が増えても schema 変更なしに載る**。外部サービスが
  フィールドを増やしても、取り込み側は壊れない。
- 取り込みコマンドには `--dry-run` を付け、「何件が新規で何件が既存か」を実行前に出す。
  実装はトランザクションを張って rollback するだけでよく、推定でなく実数が得られる。

## 設定ファイル

### 手書き JSON/TOML は strict decode で読む

**事象:** ユーザーの設定ファイルにフィールド名のタイポ（`callbackSchema` — 正しくは
`callbackScheme`）があり、デフォルトの Unmarshal が黙って無視してデフォルト値に
フォールバック。「HTTPS を指定したのに http で来る」という症状の原因特定に時間を要した。

**適用方法:** ユーザーが手書きする設定は Go なら `json.Decoder` +
`DisallowUnknownFields()`、Python pydantic なら `ConfigDict(extra="forbid")` で読む。
テストで「typo フィールドが弾かれること」を 1 ケース入れる。
**機械生成データは逆に素の Unmarshal**（後方互換のため旧フィールドを無視させる —
上記「マシンローカル ID」の項参照）。使い分けが重要。

### 「保存先ディレクトリ」設定を変えても、絶対パスで永続化済みの参照は追随しない

**事象:** 導入済みの資産ファイル群を別ボリュームへ移し、設定の保存先ディレクトリ
（`models_dir` / `output_dir` / `cache_dir` 等）を新しい場所に書き換えた。しかし
**絶対パスを記録した registry / index / manifest** は旧パスのまま残り、既存エントリが
全て存在しないディレクトリを指す状態になった。

**なぜ:** 保存先の設定は「**これから**書き込む先」を決めるだけで、既に書かれた記録には
触れない。両者は別物なのに、利用者からは一つの「モデルの置き場所」に見える。

**適用方法:**
- 「保存先を変える設定」を作った時点で「既存分をどう移すか」まで設計する。README には
  移行手順を 3 ステップ（ファイル移動 → 設定変更 → reconcile）で明記する。
- **reconcile コマンドをセットで用意する。** dry-run 既定 + `--apply` で書き込み。
  張り替えるのは「記録パスが**存在せず**、かつ新ディレクトリに**同名ファイルが存在
  する**」ときだけ。現行パスで解決できるものは触らない（意図的に別ディレクトリへ置いた
  資産を壊さない）。候補が無いものは推測せず「未解決」として報告する。
- 対象ディレクトリを上書きする `--to DIR` を付けておくと、同じコマンドが**取り消し手段**
  になる（旧ディレクトリを指して再実行するだけ）。
- reconcile はレコードの書き換えに限定し、**バイト列の移動はしない**（利用者の `mv` の
  領分）。ファイル未移動のまま dry-run すれば「全件未解決」と正しく報告される。
- **ロード時の暗黙リベースは採らない。** basename で解決する以上、同名の別ファイルを
  無言で掴む余地があり、しかもディスク上の記録と実際に使われた値が食い違ったまま残る。
  黙って自己修復する状態は、自分の破損を報告する状態より読み解きにくい。明示コマンド +
  正直な一覧を選ぶ。
- 記録されたファイル欄を列挙する処理は 1 箇所（get/set アクセサを返す `fileRefs()` 的な
  もの）に集約する。列挙・不在検査・張り替えが別々に走査すると、フィールド追加時に
  片方だけ漏れる。実在判定を関数として注入すれば全て合成 FS でテストできる。

### 一覧・ピッカー・カタログは、参照先の実在を検査してから返す

**事象:** 導入済み一覧が registry を読むだけで **stat しなかった**ため、参照先ファイルが
不在でも全件が「導入済み・健全」と表示された。CLI 表・`--json`・MCP ツール・GUI 管理画面が
同じ未検査ビューを共有しており、実際にファイルを開く処理に入って初めて旧パスで失敗する。
「管理画面は認識しているのに、使おうとすると失敗する」という原因の分かりにくい症状になる。

**なぜ:** 検査していない状態を「健全」として提示したから。表示の情報源（記録）と真実
（ディスク）が別物であることを、どのレイヤも確認していなかった。前項のパス追随の欠如と
この不在非表示は**独立した 2 つの欠陥**で、重なると発覚が生成・実行時まで遅れる。

**適用方法:**
- 一覧系は返す前に参照先を stat する。不在は行に出す（`STATUS` 列 + 不在ファイルと対処
  コマンドを名指しするフッター）。外付けボリューム未マウントも同じ形 — ファイルは消えて
  いないが、一覧が「ある」と言ってはいけない。
- front-end へは bool ではなく**不在パスのリスト**（`missing_files`）を返す。原因表示まで
  作れる。空なら省略し、**キー欠落は「健全」に倒す** — 旧バージョンのクライアントでも
  壊れない。
- **front-end はロードできないものをピッカーから外すが、管理画面には残す**（見えないと
  直せない・消せない）。消えた理由の説明文も要る。「利用可能」と表示するものは必ず
  ロードできること。
- 実行時の解決層でも早期に弾き、不在ファイル・現在の設定値・対処コマンドを名指しする。
  下層ライブラリの低レベルエラーをそのまま見せない。
- 一覧が**単一の共有ビュー**から作られていれば CLI / JSON / MCP / GUI が同時に直る。
  表示面ごとにビューを組むと検査漏れが再発する。
- コストは呼び出しごとに O(files) の stat。不在・未マウントのパスは ENOENT で即座に
  失敗するため、縮退ケースほど速い。

### macOS の設定ファイルは Application Support と ~/.config の両方を探す

**事象:** ユーザーが `~/.config/<app>/config.toml` に認証情報を置いたのに、アプリは
`~/Library/Application Support/<app>/` しか見ておらず、「認証情報なし」と言い続けた。

**なぜ:** macOS には2つの慣習が併存し、CLI 利用者は macOS でも `~/.config` を第一の
置き場と考える。**設定ファイルが存在するのに黙って読まれない**のは、無いと言われるより
はるかに悪い（存在するのだから設定は済んだと考えてしまう）。

**適用方法:**
- 読み取りは優先順に探索する: `XDG_CONFIG_HOME/<app>` → `~/.config/<app>` →
  `~/Library/Application Support/<app>`。最初に存在したものを使う。
- 書き込み先（canonical）は Application Support のままでよい。分岐するのは config だけで、
  データディレクトリ（DB 等）は分けない。
- **診断コマンドは「実際に読んだパス」を表示し、無い場合は探索したパス一覧を出す**。
  この種の事故を一発で診断可能にする唯一の仕掛け。
- テストは `HOME` と `XDG_CONFIG_HOME` の**両方**を差し替える。片方だけだと開発者自身の
  実設定を拾って落ちる。

### 永続化した「判定結果」には再判定の経路を用意する

**事象:** 「このデバイスは対象か」をプローブして真偽値で保存していた。判定ロジックの
誤りを修正しても、**既に分類済みのレコードには届かなかった**。

**なぜ:** 設定値の migration と同じ失敗形だが、対象が「ユーザーの入力」ではなく
「こちらが導出した値」なので見落としやすい。ロジックを直せば直る、と錯覚する。

**適用方法:** 導出値を永続化するなら、**明示的な再判定コマンド／操作**（`--reclassify` 等）を
必ず用意し、それが唯一の移行手段であることをドキュメントに書く。コスト（API コール等）が
かかるなら既定にはせず、明示操作にする。

## ファイルシステム

### ボリューム空き容量を volumeAvailableCapacityForImportantUsage 単独で読まない

**事象:** 展開前に空き容量バジェット検査（ZIP 爆弾対策）を行う macOS アプリで、
SMB 共有上のアーカイブ展開が「空き容量が足りません — 必要: 414 MB / 空き: 0 KB」と
**全件拒否**された。サーバ側には 3 TB 以上の空きがあった。

**なぜ:** `volumeAvailableCapacityForImportantUsage`（purgeable 領域込みの
「実効空き」）が答えを持つのはローカル APFS ボリュームだけで、ネットワーク
マウント（SMB/NFS）では **nil ではなく 0 を返す**。値が「取れた」ように見える
ため、そのまま信じると「空き 0 = 満杯」と誤読する。statfs 由来の
`volumeAvailableCapacity` はネットワーク FS でも正しい値を返す。

**適用方法:**
- important-usage キーは**正の値のときだけ**採用し、0 以下は「回答なし」として
  `volumeAvailableCapacity` へフォールバックする。両方取れたら大きい方
  （ローカル APFS では purgeable 込みの方）。
- 本当に満杯のディスクは statfs も ~0 を返すので、フォールバック後も拒否は
  維持される — 安全側は崩れない。
- どちらも取れないときは検査をスキップする（値を捏造しない）。
- 判定は純粋関数に切り出してユニットテストする（`(0, 3TB) → 3TB`、
  `(0, 0) → 0`、`(nil, nil) → nil`）。

## OAuth

### refresh_token 無しのトークンは無期限扱いにする — 人為的な期限を捏造しない

**事象:** トークン交換レスポンスに `expires_in` が無いとき「now + 1 時間」の期限を捏造
していた。実際はプロバイダ（トークンローテーション無効の Slack 等）が無期限トークンを
発行していたため、1 時間後に「期限切れ + refresh 不能」でエラーになり、無期限トークンが
死んだ扱いになって毎時再ログインを強いた。

**適用方法:**
- `expires_in` 無し + `refresh_token` 無し → `expires_at = 0`（期限不明）として保存し、
  そのまま使う。実失効は上流の **401 で検知**してそこでエラー化する。
- `expires_in` 無し + `refresh_token` 有り の場合だけ「1 時間後に再確認」等の探索値が妥当。
- 「`expires_at` が保存時刻ちょうど +1h」は捏造期限を疑うサイン。

### プロバイダによっては http:// ループバック redirect_uri を拒否する

**事象:** RFC 8252 は `http://127.0.0.1:<port>/callback` を推奨するが、一部プロバイダの
アプリ登録 UI は `https://` 以外を完全拒否する（仕様違反ではない — RFC はクライアント側の
推奨であってプロバイダに受け入れ義務を課していない）。

**適用方法:** HTTPS ループバック経路を用意する:
1. ephemeral 自己署名証明書を生成（IP SAN: 127.0.0.1 + ::1、DNS SAN: localhost、
   ECDSA P-256、短い有効期限、メモリ内のみ）。
2. `tls.NewListener` で TCP リスナーをラップ。
3. redirect_uri は `https://localhost:<port>/callback`（IP リテラルも拒否する UI がある
   ため DNS 名で）。
4. 「ブラウザ警告は想定内、1 回クリックスルーで OK」とユーザー向けに明記する。

## ターミナル・入力 UI

### 複数行ペーストは単行読み取りだとシェルに漏れる

**事象:** 対話プロンプトで `bufio.Scanner` の単行読み取りをしていたところ、ユーザーが
複数行テキストをペーストすると 2 行目以降がシェルに漏れ、**コマンドとして実行され始めた**。

**適用方法:**
- 対話入力は「空行で終了」の複数行読み取りモードにする。
- 長い入力は `--input` フラグでファイルから読めるようにする。
- Scanner のバッファはデフォルト 64KB から拡大しておく。

### 入力履歴ナビゲーションは「ナビ中フラグ」必須

**事象:** ArrowUp/Down の履歴ナビを実装した際、通常入力中に行末で ArrowDown を押すと
履歴ナビ動作が誤発火し、draft（空文字）で入力が上書きされて**入力中の内容が消えた**。

**適用方法:**
- ArrowDown ハンドラの先頭で「履歴ナビ中でなければ return」を入れる。
- ナビ中のときだけ keypress を consume し、それ以外はデフォルト動作（カーソル移動等）に
  委ねる。
- 一般化: history navigation / autocomplete / IME 連携など「特定状態の時だけキーを奪う」
  UI は、状態フラグの確認を最初に入れる。

### UI 言語の混在は翻訳ではなく「完全二面カタログ + 完全性テスト」で直す

**事象:** CLI の対話 UI（ヘルプ・ヒント・ダイアログ）が日英混在になった。個々の文字列は
その時々の言語で追加されており、どれも単体では誤りでない。混在を一度手で直しても、
次の機能がまた片言語で文字列を足せば元に戻る — 問題は誤訳ではなく「2 言語に同じ面を
覆わせる強制力の不在」。

**適用方法:**
- 文字列 1 本につき 1 フィールドの `Messages` 構造体を 1 つ定義し、言語ごとの完全な
  リテラルを 2 面用意する（gem-agent `internal/uitext`）。
- **リフレクションテストで「どちらかのカタログに空フィールドがあれば失敗」させる。**
  このテストこそが修正の本体 — 新しい文字列は両言語に入るか CI に落ちるかになる。
- `%d`/`%s` を含むフィールドは fmt 動詞の並びが両カタログで一致することもテストする
  （ずれてもコンパイルは通り、片言語だけ実行時に壊れる）。
- 言語解決は POSIX 慣行（`LC_ALL` → `LC_MESSAGES` → `LANG` の最初の非空値、`ja` 接頭辞
  判定、`C`/`POSIX` は英語）。起動時に 1 回だけ解決する — 途中切替はスクロールバックを
  二分する。
- **対象外を先に宣言する**: grep されるログ体裁の行・`--help`（CLI 慣行）・モデル向け
  テキスト・ライブラリ由来のエラー連鎖は英語のまま。全部を訳そうとすると英語の連鎖に
  訳語の接頭辞が付き、除去したかった混在が戻る。

### 他プロセスが読むマーカー/フラグファイルは temp+rename で置く（os.WriteFile は create→write の 2 段階）

**事象:** プロジェクト所有者を記録する `.project` マーカーを `os.WriteFile` で書いて
いたところ、同一プロジェクトの並列起動の約半数が「path-escape collision」で誤って
起動拒否された。WriteFile は O_CREATE|O_TRUNC で**空ファイルを作ってから**内容を書く
ため、その隙間に別プロセスが読むと「所有者 = 空」に見える。

**適用方法:**
- 別プロセスが読み得るマーカー/フラグ/小状態ファイルは、同一ディレクトリの temp
  ファイルに書き切ってから `os.Rename`。rename は原子的なので、読み手には「無い」か
  「全文」しか見えない — どちらも安全に解釈できる 2 状態にしておく。
- **空ファイルは「所有者不明」として欠如と同義に扱い、次の書き手が修復する**
  （旧実装のクラッシュ残骸への耐性）。
- 検査→書き込みの TOCTOU が残っても、それが「best-effort の識別子であってロックでは
  ない」なら後勝ち rename で十分 — その割り切りはコメントに明記する。
